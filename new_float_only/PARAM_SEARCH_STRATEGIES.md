# `new_float_only` 参数搜索策略比较

本文讨论 [`ofec_alpha_beta_sweep_float.cpp`](/home/zsr71/projects/newcode/new_float_only/apps/ofec_alpha_beta_sweep_float.cpp) 当前使用的参数扫描方式，以及有哪些更快的替代方案。

## 1. 当前方法是什么

当前 `ofec_alpha_beta_sweep_float` 采用的是：

1. 先用 `Start / End / Count` 生成多个参数网格
2. 把这些网格做笛卡尔积，得到很多个 `pattern`
3. `stage1` 用较少的 `NUM_INFO_BITS` 快扫所有 pattern
4. 只保留前 `K` 个 pattern
5. `stage2` 用更大的 `NUM_INFO_BITS` 精扫这批 top pattern

它的特点是：

- 结果稳定
- 实现简单
- 很容易解释和复现
- 但会浪费不少算力在明显不好的参数组合上

所以它适合作为基线，但不一定是最快的方案。

## 2. 可选的更快方案

下面按“实现成本”和“潜在提速收益”来比较。

### 2.1 多阶段淘汰

做法：

1. `stage0` 用极少量 bits 和少量 seed，跑全部 pattern
2. 淘汰掉明显差的 50% 到 80%
3. `stage1` 对剩余 pattern 增加 bits 或 seed
4. 再淘汰
5. 最后只对极少量候选做高成本精扫

优点：

- 非常适合单次评估成本高的问题
- 在当前两阶段框架上最好扩展
- 保持结果解释性强

缺点：

- stage 太多时，参数管理会变复杂
- 若早期噪声太大，可能误杀潜在好参数

适合当前工程的原因：

- 你现在已经有 `stage1 / stage2`
- 扩成 `stage0 / stage1 / stage2 / final` 非常自然

### 2.2 粗网格 + 局部细化

做法：

1. 先用较粗的网格全局扫一遍
2. 找到前若干个最优区域
3. 只在这些局部区域重新生成更细的网格
4. 再做局部精扫

优点：

- 比全局高分辨率网格快很多
- 结果比纯随机采样更好解释
- 非常适合你现在这种参数是单调序列、可用 `low/high/gamma` 参数化的场景

缺点：

- 需要设计“局部细化”的规则
- 如果全局粗网格太粗，可能漏掉好区域

适合当前工程的原因：

- 你现在已经把参数抽象成：
  - `alpha_low / alpha_high / gamma_alpha`
  - `beta_low / beta_high / gamma_beta`
- 非常适合围绕 top-K 的这些值缩小区间、重新细扫

### 2.3 随机采样

做法：

- 不做笛卡尔积全枚举
- 直接在参数空间内随机抽样若干组参数

优点：

- 在高维空间里通常比密集网格更省
- 实现很简单

缺点：

- 可解释性不如网格
- 结果依赖随机样本质量
- 如果样本数太少，容易不稳定

适合当前工程的原因：

- 如果以后 `gamma_alpha/gamma_beta` 也放开多个候选点，参数维数会更高
- 那时随机采样会比全网格更省

### 2.4 Latin Hypercube / Sobol 采样

做法：

- 不是纯随机
- 而是在整个参数空间内更均匀地铺样本点

优点：

- 比普通随机采样覆盖更均匀
- 样本效率通常更高

缺点：

- 实现复杂度比纯网格和纯随机更高
- 结果不如网格直观

适合当前工程的原因：

- 如果以后参数维数继续上升，这类方法会比全网格更划算

### 2.5 坏候选提前终止

做法：

1. 一个 pattern 不一次性跑完全部 bits / 全部 seed
2. 先跑一小部分预算
3. 如果它当前 BER 已经明显差于已有 top-K 阈值
4. 就直接停止，不再给它更多预算

优点：

- 对明显差的 pattern 能省很多时间
- 和当前的 seed/task scheduler 兼容

缺点：

- 需要一个稳妥的淘汰阈值
- 过早停止可能误杀

适合当前工程的原因：

- 当前代码已经有：
  - pattern
  - seed schedule
  - stage
- 所以可以继续细分预算，逐步观察再淘汰

### 2.6 Bayesian Optimization / 模型引导搜索

做法：

- 用前面已经评估过的参数和 BER 结果拟合一个代理模型
- 再由代理模型决定下一批最值得评估的点

优点：

- 如果单次评估极贵，理论上样本效率可以很高

缺点：

- 实现复杂
- 对噪声敏感
- 对当前这个工程来说过重

适合当前工程的原因：

- 暂时不太适合
- 除非后面参数维度和单次评估成本都继续大幅增加

## 3. 和当前方法相比，哪些最值得优先做

如果只考虑“少改代码、提速明显”，优先级建议如下。

### 第一优先级：多阶段淘汰

原因：

- 你已经有两阶段框架
- 改动最小
- 收益通常直接

例如：

1. `stage0`: 极少 bits，全部 pattern
2. `stage1`: 中等 bits，保留前 1/4
3. `stage2`: 更多 bits，保留前 1/2
4. `final`: 大 bits，全量 seed

### 第二优先级：粗网格 + 局部细化

原因：

- 和你现在的 `Start / End / Count` 参数化非常匹配
- 容易解释
- 容易复用现有实现

做法可以是：

1. 第一轮粗扫
2. 取前若干最优 pattern
3. 围绕它们的 `low/high/gamma` 缩小范围
4. 再自动生成第二轮局部高分辨率网格

### 第三优先级：坏候选提前终止

原因：

- 能继续压缩总计算量
- 但实现会比前两种稍微复杂一点

## 4. 对当前 `new_float_only` 的推荐路线

如果目标是：

- 不大改框架
- 但明显比现在更快

推荐路线是：

1. 保留当前 `Start / End / Count` 的参数输入方式
2. 保留当前公共 task scheduler
3. 先把“两阶段”扩展成“多阶段淘汰”
4. 然后再加“粗网格 + 局部细化”

原因：

- 这两项都和你当前代码结构最匹配
- 都不需要引入复杂外部依赖
- 还能保持结果易于理解

## 5. 一个实际建议方案

可以把后续版本改成下面这样：

### 第 1 轮：全局粗扫

- 较粗网格
- 1 个 seed
- 少量 bits
- 保留前 20% 到 30%

### 第 2 轮：局部细化

- 对 top 区域缩小参数范围
- 增加网格密度
- 继续 1 个 seed 或 2 个 seed
- 保留前 10% 到 20%

### 第 3 轮：中等精度确认

- 增加 bits
- 增加 seed
- 去掉明显不稳定的候选

### 第 4 轮：最终精扫

- 用目标工作点的 bits 和 seed
- 给出最终推荐参数

## 6. 一句话建议

如果你问“下一步最值得加什么”，我的建议是：

> 先做“多阶段淘汰”，再做“粗网格 + 局部细化”。

这是当前 `new_float_only` 代码结构下，提速收益和实现复杂度最平衡的路线。
