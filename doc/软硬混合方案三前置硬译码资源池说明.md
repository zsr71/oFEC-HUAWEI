# 软硬混合方案三前置硬译码资源池说明

本文说明方案三的第三个变体：把 Chase 软解码里的前置硬判决 BCH 译码阶段拆出来，放到 MUX / Chase 之前，形成一个独立的前置硬译码资源池。本文只描述方案思想、流程和硬件调度关系，不涉及具体代码实现。

## 1. 三个方案三变体的关系

围绕 `S0/S1/S3` 分类、`TwoCandidate` 处理和前置硬译码资源，目前可以把方案三拆成三个变体。

| 变体 | 核心思想 | TwoCandidate 处理 | 前端资源特点 |
| --- | --- | --- | --- |
| 三拍版 | fast classifier 后，对 TwoCandidate 再做 hard confirm | 送 BCH / locator 确认，成功 hard-finish，失败进 Chase | 需要 TwoCandidate confirm 资源 |
| 两拍版 | 为缩短时序，TwoCandidate 不确认 | TwoCandidate 直接进 Chase | 前端只做快速分类，不做两错确认 |
| 前置硬译码资源池版 | 把 Chase 第一阶段 hard decode 拆出来前移 | 被选中的行直接进 hard decoder，成功 hard-finish，失败进 Chase 后续流程 | 需要 N 个前置 hard decoder |

前两个变体主要围绕 syndrome 快速分类和 `TwoCandidate` 的去向展开。前置硬译码资源池版则更进一步：它不只是改变 `TwoCandidate`，而是把完整 BCH hard decode 作为一种前端可调度资源。

## 2. 设计动机

Chase 软解码的第一步通常也是从当前 LLR 做硬判决，然后尝试 BCH 硬译码。若硬判码字本身或少量翻转后能形成合法码字，后续 Chase 搜索可以围绕这些候选展开。

既然 Chase 内部本来就需要硬判决和硬译码，那么可以把这一步拆出来，放在 MUX / Chase 之前：

```text
非 early-stop 行
  -> 先竞争前置 hard decoder 资源
  -> hard decode 成功：直接 HardFinish
  -> hard decode 失败：再进入 Chase 的 LLR 排序 / test pattern 搜索流程
```

这样做的目标是：

- 提前完成一部分可硬纠行。
- 减少后续 Chase 搜索压力。
- 把 hard decode 资源显式建模成可调度资源。
- 避免在 Chase 内部对同一批行重复做前置硬译码。

## 3. 核心原则

前置硬译码资源池版的核心原则是：

> 把 hard decode 作为 MUX 前的一类独立资源，而不是 Chase 内部不可见的一步。

例如每个 tile 有 32 行需要处理，硬件前端配置 15 个 hard decoder，则本轮最多只有 15 行可以尝试前置硬译码。

这时系统里有两类资源：

- `SIHO` / hard decoder 资源：控制多少行可以先尝试硬译码。
- `SISO` / Chase 资源：控制多少行可以进入软解码。

两类资源的作用不同：

```text
SIHO_ACTIVE = 前置 hard decode 尝试预算
SISO_ACTIVE = Chase / soft decode 调度预算
```

前置 hard decode 成功的行不再占用 SISO 资源。失败的行才进入后续软解码候选池。

## 4. 整体流程

前置硬译码资源池版可以按下面流程理解：

```text
输入当前 tile 的 32 行码字
  -> early-stop 判定
  -> 从非 early-stop 行中选择最多 N 行进入 hard decoder pool
  -> hard decoder 返回结果
  -> hard decode 成功行标记为 HardFinish
  -> hard decode 失败行进入 Chase candidate
  -> 未获得 hard decoder 资源的行进入 Chase candidate 或等待后续策略
  -> MUX 在 Chase candidate 中按 SISO_ACTIVE 分配 Chase 资源
  -> Chase 对获得资源的行执行 LLR 排序 / test pattern 搜索
  -> 合并输出
```

其中 `N` 是前置 hard decoder 数量，例如：

```text
N = 15
```

表示一个 tile 内最多 15 行可以先尝试前置硬译码。

## 5. 判断表

前置 hard decoder 返回后，可以按结果分类。

| hard decoder 结果 | 分类 | 处理 |
| --- | --- | --- |
| syndrome 原本为零，或硬译码确认 0 错 | `HardFinish / Clean` | 直接生成硬完成输出 |
| 硬译码确认 1 错并成功修正 | `HardFinish / OneMain` | 直接生成硬完成输出 |
| 硬译码确认 2 错并成功修正 | `HardFinish / TwoMain` | 直接生成硬完成输出 |
| hard decoder 失败 | `HardFail` | 进入 Chase candidate |
| 没有获得 hard decoder 资源 | `SoftCandidate` | 进入 Chase candidate，或根据策略延后 |

在这个变体里，`TwoMain` 不再是 syndrome 快速分类后单独确认出来的结果，而是 hard decoder pool 的成功结果之一。

也就是说：

```text
0 错 / 1 错 / 2 错硬译码成功
  -> 都可以直接 HardFinish

硬译码失败
  -> 进入 Chase 后续流程
```

## 6. 硬件时序示例

假设每个 tile 有 32 行，前端有 15 个 hard decoder。

一种保守时序可以是：

```text
第 1 拍：
  计算 early-stop / syndrome / 基础候选信息。

第 2 拍：
  从非 early-stop 行中选择最多 15 行进入 hard decoder pool。
  未进入 hard decoder pool 的行暂时记为 soft candidate。

第 3 拍或 hard decoder 返回拍：
  hard decoder 成功：
    进入 hard_finish_mask。
  hard decoder 失败：
    进入 chase_candidate_mask。
  未尝试 hard decode 的行：
    进入 chase_candidate_mask，或按资源策略延后。

后续：
  MUX 根据 chase_candidate_mask 和 SISO_ACTIVE 选择真正进入 Chase 的行。
```

如果 hard decoder 可以一拍返回，那么整体时序可以更短。如果 hard decoder 多拍返回，则 MUX / Chase 调度需要等待返回，或者设计成流水队列。

关键点是：这个变体的调度延迟由 hard decoder latency 决定，而不是由 `TwoCandidate` 单独决定。

## 7. 和 Chase 的关系

这个变体可以理解为：

```text
把 Chase 的第一步 hard decision + BCH hard decode 前移
```

原始 Chase 流程大致是：

```text
LLR 输入
  -> 硬判决
  -> BCH hard decode
  -> LLR 排序
  -> 生成 test patterns
  -> 搜索候选码字
  -> 计算软输出 / 外信息
```

前置硬译码资源池版把前两步拆出来：

```text
前置阶段：
  LLR 输入
    -> 硬判决
    -> BCH hard decode
    -> 成功则 HardFinish

Chase 阶段：
  hard decode 失败或未尝试的行
    -> LLR 排序
    -> test pattern 搜索
    -> 计算软输出 / 外信息
```

这样后续 Chase 不需要再把已经 hard-finish 的行纳入搜索，也可以避免对这些行重复执行前置硬译码。

## 8. 需要注意的算法语义

这个变体有一个重要前提：

> hard decode 成功是否足以让该行直接 HardFinish。

在标准 Chase 中，硬判 hard decode 成功通常表示找到了一个合法候选码字。但 Chase 软输出不只关心一个合法候选，还可能需要多个候选之间的 metric 差值来生成更细的外信息。

因此，如果 hard decode 成功后直接 HardFinish，本质上是一个算法策略选择：

- 优点是减少 Chase 搜索。
- 代价是这行不再通过 Chase 多候选比较生成软外信息。

这需要通过 BER 和外信息稳定性验证。

如果系统认为 0/1/2 错硬译码成功已经足够可靠，那么可以直接 HardFinish。若担心 miscorrection 或软信息质量下降，可以加入可靠度保护，例如：

- 只允许 0 错 / 1 错直接 HardFinish。
- 2 错成功但低可靠度时仍送 Chase。
- 对 hard decoder 成功结果增加 syndrome / parity 复核。
- 对待翻转位置的 LLR 绝对值设置门限。

## 9. 资源调度策略

当前变体的核心调度问题是：当非 early-stop 行数超过 hard decoder 数量时，应该选哪些行进入 hard decoder pool。

可选策略包括：

| 策略 | 说明 |
| --- | --- |
| 顺序优先 | 按行号选择前 N 个非 early-stop 行，硬件简单 |
| 低可靠度优先 | 优先选择 LLR 较不可靠的行，更可能需要纠错 |
| syndrome 优先 | 优先选择 syndrome 非零但看起来可硬纠的行 |
| 历史优先 | 结合前几级 tile 的失败记录或未调度记录 |

第一版建议使用简单策略，例如顺序优先或已有 MUX 优先级，先验证结构收益。

更复杂的优先级可以后续再加入。

## 10. 与两拍版 / 三拍版的对比

| 对比项 | 两拍版 | 三拍版 | 前置硬译码资源池版 |
| --- | --- | --- | --- |
| 前端主要动作 | `S0/S1/S3` 快速分类 | 快速分类 + TwoCandidate confirm | 对选中行执行完整 hard decode |
| TwoCandidate | 直接进 Chase | confirm 成功 hard-finish，失败 Chase | 若被选中则 hard decode；未选中则 soft candidate |
| 是否需要 hard decoder pool | 不需要 | 只需要服务 TwoCandidate 或 locator | 需要 N 个前置 hard decoder |
| Chase 负载 | 较高 | 较低 | 取决于 hard decoder 数量和选择策略 |
| 控制复杂度 | 最低 | 中等 | 中等到较高 |
| 资源建模 | 主要建模 SISO | 建模 TwoCandidate confirm | 同时建模 SIHO 和 SISO |
| 适合阶段 | 第一版硬件简化 | Chase 压力优化 | 明确有 hard decoder 资源预算的硬件实现 |

## 11. 适用场景

前置硬译码资源池版适合：

- 硬件中已经计划配置若干 BCH hard decoder。
- 希望显式建模 hard decoder 数量，例如每 tile 只有 15 个 hard decoder。
- 希望减少 Chase 内部搜索负载。
- 可以接受 hard decoder 成功后直接 HardFinish 的算法策略。
- 希望把 SIHO 和 SISO 两类资源分开调度。

不太适合：

- 硬件前端不希望配置额外 hard decoder。
- 系统必须严格保留 Chase 的多候选软输出质量。
- hard decoder latency 较长且调度队列设计尚未明确。

## 12. PPT 可用总结

前置硬译码资源池版可以总结为：

> 这个变体把 Chase 的第一步硬判决 BCH 译码拆出来，放到 MUX / Chase 之前作为独立资源池。每个 tile 中，非 early-stop 行先竞争有限数量的 hard decoder；硬译码成功的行直接 HardFinish，失败或未获得 hard decoder 资源的行再进入 Chase 候选池。它的本质是同时建模 SIHO 和 SISO 两类资源，用前置 hard decode 减少 Chase 搜索压力。

一句话版本：

> 前置硬译码资源池版不是只改 TwoCandidate，而是把 Chase 的 hard-decode 前端拆出来，作为 MUX 前可调度的硬件资源。
