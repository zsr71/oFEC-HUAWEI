# Level 5/6 共享 SRAM 双窗口独立浮动方案草案

## 1. 文档状态

- 方案状态：逻辑设计草案 v0.4；
- 当前阶段：先定义方案本体，不讨论硬件 cycle、端口冲突或具体 RTL 实现；
- 基础方案：原 Level 5/6 共享解码与 44 行联合 Buffered FIFO 方案；
- 本文新增：将一个绑定移动的 44 行联合窗口拆成两个可以独立浮动的 22 行窗口；
- 状态组织：采用“方案 B”，即一份连续 SRAM 物理流、两个阶段指针以及每个数据单元的分级控制状态。

本文只将已经确认的内容写为确定规则。尚未确定的调度和状态转移细节统一列在文末，不在本版中进行推断。

## 2. 设计目标

原 Buffered FIFO 方案把 Level 6 的 22 行窗口和 Level 5 的 22 行窗口绑定成一个 44 行联合窗口。当某一级出现较多 pending code 时，两个窗口必须一起移动，另一级无法利用其自身较轻的负载独立前进或恢复位置。

本方案将联合窗口拆成：

- 一个严格对应 Level 5 的 22-block-row 解码窗口；
- 一个严格对应 Level 6 的 22-block-row 解码窗口。

两个窗口位于同一块连续 SRAM 中，可以分别改变位置。目标是在不改变物理输入、输出节拍的前提下，使两级分别吸收各自的瞬时解码需求 burst。例如，当 Level 6 因 pending 停留时，Level 5 可以继续处理后续数据并独立移动，而不再被 Level 6 的窗口位置完全绑定。

## 3. 术语与计量单位

### 3.1 物理 block row 与 code

当前参数中，一个 block row 包含 16 个 decoder/codeword row，因此：

```text
2 block rows = 32 code
```

每个时刻 `t`，SRAM 底部新进入 2 个 block row，即 32 个新 code；SRAM 顶部同时输出 2 个 block row，即 32 个旧 code。

### 3.2 物理数据单元 `B_i`

本文将每次从 SRAM 底部进入的 2 个 block row 定义为一个物理数据单元：

```text
B_i = 第 i 个进入 SRAM 的 2-BR / 32-code 数据单元
```

因此：

```text
t=0：B0 从 SRAM 底部进入
t=1：B1 从 SRAM 底部进入
t=2：B2 从 SRAM 底部进入
...
```

`B_i` 始终表示一组 2-BR/32-code 物理数据，不表示原方案中的 64-code 联合调度集合。

### 3.3 分级阶段对象

同一个物理数据单元依次经历两个阶段：

```text
L5(B_i)：B_i 的 Level 5 处理阶段
L6(B_i)：B_i 的 Level 6 处理阶段
```

数据处理先后关系固定为：

```text
B_i 进入 SRAM
    -> L5(B_i)
    -> L6(B_i)
    -> 从 SRAM 顶部输出
```

### 3.4 64-code 共享调度集合

原 Level 5/6 共享调度器一次面对：

```text
Level 5 当前 2 BR：32 code
Level 6 当前 2 BR：32 code
合计：64 code
```

因此，`64-code` 是一次 Level 5/6 共享调度的逻辑集合，不是每个时刻从 SRAM 底部进入的数据量。

在双窗口方案中，两个窗口的位置可以不同，所以同一时刻的共享调度集合可能是：

```text
L5(B_j) 的 32 code + L6(B_i) 的 32 code，且 i != j
```

### 3.5 宏观时刻 `t` 与内部逻辑微步 `r`

`t` 是物理吞吐量的计量单位。每个正常流 `t` 只发生一次顶部 2 行输出、整体 2 行上推和底部 2 行输入，并且只拥有一份总计 8 个普通 group-entry 的共享预算。

为了描述同一个 `t` 内的多轮普通调度、FullEarlyStop 清理、写回和阶段对象切换，在 `t` 内进一步定义逻辑微步 `r`：

```text
(t,0) -> (t,1) -> ... -> (t,r_final) -> (t+1,0)
```

逻辑微步不是新的物理时刻。在同一个 `t` 的相邻微步之间：

- SRAM 不整体上推；
- 顶部不产生新的物理输出；
- 底部不输入新的 `B_i`；
- 普通 group-entry 预算不重置。

一个普通联合调度微步可以按照原共享 scheduler 的同一调度快照使用一个或多个 entry。若第 `r` 个普通调度微步使用 `E_{r,t}` 个 entry，则：

```text
E_{r,t} >= 1
sum_r E_{r,t} <= 8
```

因此一个 `t` 内最多自然形成 8 个消耗普通资源的调度微步，但通常少于 8 个。FullEarlyStop 清理、写回提交、对象切换和边界裁决属于零 entry 状态微步，不占用这 8 个普通 entry。

对每一级还需要区分两个量：

```text
C_l,t：时刻 t 内已经结束的阶段对象数
A_l,t：这些结束中，已经在 t 内成功提交“窗口向下推进 2 行”的次数
```

阶段完成与窗口推进不是同一件事。若当前对象已经结束，但下一对象尚未进入 SRAM、受另一窗口阻挡或暂时不满足两级先后关系，则本级保留一个“已完成、下一对象尚未暴露”的延迟推进状态并停止本 `t` 的继续服务。由于同一级不允许越过这个状态继续完成更多对象，始终有：

```text
A_l,t <= C_l,t <= A_l,t + 1
```

## 4. 连续 SRAM 组织

### 4.1 总容量

定义：

- `R_buf`：两级窗口可以共同使用的额外 buffer 行数；
- `R_l5=22`：Level 5 窗口长度；
- `R_l6=22`：Level 6 窗口长度。

连续 SRAM 总行数固定为：

```text
R_mem = R_buf + R_l5 + R_l6
      = R_buf + 44
```

SRAM 中的 LLR、prior、history 和 extrinsic 始终只有一份。逻辑状态不得为某个 FIFO 项另外保存一份完整的 Level 5/Level 6 tile 数据快照。

### 4.2 基准布局

以 SRAM 顶部为 row 0、底部为 row `R_mem-1`。当两个窗口均处于基准位置时：

```text
[0, R_buf)              buffer
[R_buf, R_buf+22)       Level 6 窗口
[R_buf+22, R_buf+44)    Level 5 窗口
```

例如 `R_buf=32`：

```text
[0,32)    buffer
[32,54)   Level 6 窗口
[54,76)   Level 5 窗口
```

物理地址由上到下为 Level 6、Level 5；数据处理顺序由 SRAM 底部向顶部为 Level 5、Level 6。因此“永远先 Level 5、再 Level 6”描述的是数据处理顺序，不是物理 row 编号的书写顺序。

### 4.3 双窗口定义

分别定义两个窗口在宏观时刻开始处的起点：

```text
S5_t：时刻 t 的 Level 5 窗口起点
S6_t：时刻 t 的 Level 6 窗口起点
```

同一个 `t` 内还需要维护微步级窗口起点：

```text
S5_{t,r}：时刻 t 内第 r 个逻辑微步的 Level 5 窗口起点
S6_{t,r}：时刻 t 内第 r 个逻辑微步的 Level 6 窗口起点

S5_t = S5_{t,0}
S6_t = S6_{t,0}
```

窗口范围为：

```text
W5_t = [S5_t, S5_t+22)
W6_t = [S6_t, S6_t+22)
```

初始基准位置为：

```text
S6_0 = R_buf
S5_0 = R_buf + 22
```

### 4.4 窗口合法性约束

任意宏观时刻和任意内部逻辑微步均必须满足：

```text
0 <= S6_t
S5_t + 22 <= R_mem
S6_t + 22 <= S5_t

0 <= S6_{t,r}
S5_{t,r} + 22 <= R_mem
S6_{t,r} + 22 <= S5_{t,r}
```

其中：

- 第一项保证 Level 6 不越过 SRAM 顶部；
- 第二项保证 Level 5 不越过 SRAM 底部；
- 第三项保证两个 22 行窗口不重叠。

窗口起点与 2-BR 物理推进单位保持同相位对齐。若 `R_buf` 采用偶数行，则可直接写为：

```text
S5_t mod 2 = 0
S6_t mod 2 = 0
```

### 4.5 动态 buffer 分布

`R_buf` 表示两个窗口之外的总额外空间，并不永久对应 SRAM 中某一段固定区域。当两个窗口独立移动时，buffer 可以动态分布在：

```text
Level 6 窗口上方：[0, S6_t)
两个窗口之间：[S6_t+22, S5_t)
Level 5 窗口下方：[S5_t+22, R_mem)
```

三段长度之和始终为：

```text
R_buf
```

## 5. 一个宏观时刻的完整事件顺序

本文统一把 `t` 定义为 `B_t` 已经完成底部写入、两个窗口即将开始本时刻服务的状态。帧首初始化完成后，每个正常流时刻严格按照以下顺序执行：

1. `B_t` 已位于 SRAM 底部 `[R_mem-2,R_mem)`，当前 SRAM row-to-`B_i` 映射和 `S5_{t,0}/S6_{t,0}` 生效；
2. Level 1--4 完成其原有处理和必要写回；
3. Level 5/6 从唯一 SRAM 读取当前窗口对象；
4. 清理两级当前连续可见的 FullEarlyStop 对象；
5. 使用本 `t` 剩余的普通 entry 执行一轮原五六级共享调度；
6. 完成本轮全部执行和必要 SRAM 写回；
7. 分别判断两级当前阶段对象是否结束；
8. 结束的一侧提出转向本级下一物理对象的请求，未结束的一侧保留当前对象；
9. 在提交任何对象切换之前，联合检查 SRAM 边界、双窗口不重叠和 Level 5 先于 Level 6；
10. 合法且下一对象当前已经位于 SRAM 时，提交新的微步级窗口位置、增加 `A_l,t`，并从写回后的唯一 SRAM 重新读取当前对象；下一对象尚不可暴露时，保留延迟推进状态并停止本级继续服务；发生第 11 节定义的必要跟随冲突时执行边界退出；
11. 重复步骤 4--10，直到普通 8-entry 预算耗尽、没有普通对象、物理边界阻止继续推进或无法产生状态进展；
12. 普通预算耗尽后，仍可清理合法可见的 FullEarlyStop 链；
13. 提交本 `t` 的最终窗口和阶段状态；
14. 在 `t -> t+1` 的物理边界，SRAM 顶部 `[0,2)` 输出，原 `[2,R_mem)` 整体上移到 `[0,R_mem-2)`，`B_{t+1}` 写入底部 `[R_mem-2,R_mem)`；
15. 根据本 `t` 的阶段结束数计算两级宏观候选位置，联合处理延迟推进、必要跟随和第 11 节边界，形成 `S5_{t+1,0}/S6_{t+1,0}`。

因此，`B_t` 可以在时刻 `t` 被 Level 5 看见，但 `B_{t+1}` 不能在时刻 `t` 的内部微步中被提前读取。顶部输出、整体上推和底部输入在每个 `t -> t+1` 边界只发生一次。

解码完成量、窗口位置和 pending 数量不能暂停或改变这一物理节拍。

物理推进只改变数据当前所在的物理 row，不改变：

- `B_i` 的逻辑身份；
- `B_i` 内部 32 个 code 的固定编号；
- `B_i` 已经经历的 Level 5/Level 6 阶段；
- 已完成 code 的控制状态；
- SRAM 中已经完成的有效写回结果。

## 6. 每个 22 行窗口的解码对象

22 个 block row 是该级形成解码输入、history 读取和写回映射所需的完整 tile 上下文，并不表示一次同时解码 `22*16` 个 code。

当前逻辑微步真正形成该级 32-code 调度输入的是窗口底部 2 个 block row：

```text
Level 5 实际解码区：D5_{t,r} = [S5_{t,r}+20, S5_{t,r}+22)
Level 6 实际解码区：D6_{t,r} = [S6_{t,r}+20, S6_{t,r}+22)
```

当前阶段对象必须由 SRAM 的实时 row-to-`B_i` 映射确定：

```text
H5_{t,r} = 位于 D5_{t,r} 的物理数据单元
H6_{t,r} = 位于 D6_{t,r} 的物理数据单元
```

调度器不得只根据一个可能过期的逻辑队首 ID，读取与当前物理窗口不一致的 `B_i`。

## 7. 方案 B：一份物理流与两个阶段指针

### 7.1 权威状态

本方案不使用两条独立软件 FIFO 作为服务对象的权威来源。权威关系定义为：

```text
数据和数据顺序的真源：连续物理 SRAM
当前可服务位置的真源：Level 5/Level 6 两个物理解码窗口
待执行工作的真源：每个 B_i 的分级控制状态
```

FIFO 顺序由 SRAM 中的物理先后顺序和两个阶段指针自然形成。

### 7.2 Level 5 阶段指针

Level 5 至少维护：

```text
S5_{t,r}                当前逻辑微步的 22 行窗口起点
H5_{t,r}                从 D5_{t,r} 物理映射得到的当前 B_i
StageState[B_i].level5  L5(B_i) 的 32-code 状态
```

### 7.3 Level 6 阶段指针

Level 6 至少维护：

```text
S6_{t,r}                当前逻辑微步的 22 行窗口起点
H6_{t,r}                从 D6_{t,r} 物理映射得到的当前 B_i
StageState[B_i].level6  L6(B_i) 的 32-code 状态
```

### 7.4 每个数据单元的控制状态

每个 `B_i` 应分别保存 Level 5 和 Level 6 的控制状态，但不保存 SRAM 数据副本。每一级的 32-code 状态至少需要表达：

- EarlyStop 结果；
- Hybrid 分类；
- HISO/SISO 资源资格；
- mux 后的资源分配结果；
- 是否已经获得解码资源；
- `pending`；
- `AlreadyDecoded`；
- `writeback_complete`；
- `forced-evicted`；
- 当前阶段是否已经结束。

一个 code 只有在对应阶段动作及其必要 SRAM 写回完成后，才能将该阶段的 `AlreadyDecoded` 和 `writeback_complete` 置为真。

## 8. 两级先后关系

对于任意 `B_i`，Level 5 必须先于 Level 6：

```text
L5(B_i) 尚未达到允许离开 Level 5 的终态
    => L6(B_i) 不得开始普通解码
```

Level 5 的允许离开终态包括正常完成、FullEarlyStop 完成和碰撞边界 forced-evicted。forced-evicted 不是正常完成，只表示 Level 5 不再等待剩余 pending；对应物理数据必须继续随 SRAM 流动，实际到达 Level 6 窗口后才可开始 `L6(B_i)`。

Level 5 和 Level 6 可以在同一个 `t` 中分别服务不同的数据单元。例如：

```text
Level 5 服务 L5(B16)
Level 6 服务 L6(B5)
```

该并行关系不违反先后顺序，前提是 `B5` 已经结束其 Level 5 阶段。

## 9. 独立浮动的基本语义

同一个 `t` 内 SRAM 的物理内容不整体移动。对任意一级 `l in {5,6}`：

- 当前阶段对象结束并且下一对象已经合法可见时，该级微步窗口向 SRAM 底部方向推进 2 行，并增加本级 `A_l,t`；
- 当前阶段对象仍有 pending 时，该级微步窗口保持不动并继续指向同一对象；
- 当前阶段对象已经结束、但下一对象尚未合法可见时，微步窗口保持不动，记录延迟推进状态，并停止本级在当前 `t` 内继续服务；
- 每次推进前都必须确认下一对象已经位于 SRAM、满足 Level 5 到 Level 6 的先后关系，并且推进后的两个窗口仍合法且不重叠；
- 完成状态和窗口推进是两个必须分别提交的事件：阶段对象已经结束，不代表可以在违反物理约束的情况下提前读取下一对象；
- 两级的阶段完成量和微步窗口位置分别维护，不再要求 `S5_{t,r}=S6_{t,r}+22`。

在 `t -> t+1` 的边界，SRAM 固定向顶部移动 2 行。若某一级在 `t` 内没有结束当前阶段对象，则该级窗口需要同时向顶部移动 2 行，才能在 `t+1` 继续跟随同一个物理对象；若在 `t` 内结束并合法跨过一个阶段对象，则微步内的 `+2` 与物理边界的 `-2` 相互抵消；若最后一个阶段对象已经结束但推进被延迟，则通过宏观候选位置在边界上完成向下一对象的切换。

在不存在 forced-evicted 时，用以下公式汇总每一级的宏观自然候选位置：

```text
S5_candidate = S5_t - 2 + 2*C5_t
S6_candidate = S6_t - 2 + 2*C6_t
```

其中：

```text
C5_t = 时刻 t 内结束的 Level 5 阶段对象数
C6_t = 时刻 t 内结束的 Level 6 阶段对象数
```

其中，在 `t` 内已经提交的 `A_l,t` 次推进已经反映在最终微步窗口位置中；若 `C_l,t=A_l,t+1`，则最后一次完成对应的对象切换尚未提交，必须在宏观边界联合裁决。该公式不能代替微步级状态转移，也不能授权读取尚未合法暴露的对象。每次对象切换前仍必须满足 SRAM 边界、两个窗口不重叠以及第 11 节的边界规则。正常完成和 FullEarlyStop 完成均计入本级 `C5_t/C6_t`；forced-evicted 不计入正常完成数，而是作为宏观边界的显式位置覆盖，结束当前阶段等待并使阶段指针转入下一合法状态。

## 10. 与原共享调度器的关系

本方案改变窗口和阶段状态的组织，不在当前版本中重新定义原有单次共享调度器的内部算法。当前仍保留以下基础：

- Level 5 提供 32 个 code；
- Level 6 提供 32 个 code；
- 按原映射拼成 64-code 调度输入；
- 沿用原有 EarlyStop、Hybrid 分类、HISO/SISO 资格；
- 沿用 4-code group 组织；
- 沿用最多 8 个普通 group-entry 的共享资源约束；
- 沿用 Level 5 优先的既有顺序；
- 未获得资源的 code 不产生新结果，不执行新的外信息写回，并保留为 pending；
- 已完成 code 在后续服务中通过 `AlreadyDecoded` 跳过。

双窗口独立后，64-code 调度输入的两半可能来自不同的 `B_i`，因此原来的“联合 64-code batch 整体完成、整体退休”语义不再适用。Level 5 和 Level 6 必须分别判断自己的 32-code 阶段对象是否完成，并分别更新阶段指针。

### 10.1 单个 `t` 内的多轮普通联合调度

每个 `t` 只有一份总计 8 个 group-entry 的普通服务预算，但不人为限制只能执行一轮或两轮普通联合调度。普通联合调度的一轮对应一个消耗普通资源的逻辑微步；同一轮的 entry 由原共享 scheduler 基于同一个输入快照统一决定。设第 `r` 轮实际使用 `E_{r,t}` 个 entry，则始终满足：

```text
sum_r E_{r,t} <= 8
```

每一轮按以下规则执行：

1. 从 `D5_{t,r}`、`D6_{t,r}` 的实时物理映射取得本轮 Level 5 和 Level 6 阶段对象；
2. 将两级当前仍需服务的 code 按原映射组成最多 64-code 的联合候选集合；
3. 使用原五六级共享 scheduler，并把本轮可用上限设置为当前剩余 entry 数；
4. 两级共享这份剩余预算，沿用原调度顺序和 Level 5 优先规则；
5. 完成本轮全部 EarlyStopAction、HISO/SISO 执行和必要 SRAM 写回；
6. 分别判断两级当前阶段对象是否完成；
7. 已完成的一侧提出向 SRAM 底部方向推进 2 行、转向本级下一物理对象的请求，未完成的一侧继续保留当前对象；
8. 在提交推进前联合检查下一对象是否有效、两级先后关系、SRAM 边界和双窗口不重叠；
9. 只有检查通过后才更新 `S5_{t,r+1}/S6_{t,r+1}`；若检查不通过，则停止该侧继续换入或按第 11 节处理 forced-evicted；
10. 若仍有普通 entry，则从写回后的唯一 SRAM 和新的微步窗口位置重新读取当前对象，重新组成下一轮候选集合。

同一轮中分配的多个 entry 可以在过程展示中逐项展开，但不能把前一个 entry 的写回用于改变同一轮后续 entry 的选择；只有整轮执行和必要写回全部完成后，才进入下一个状态微步并重新调用 scheduler。

因此，相邻普通轮次中的 64-code 候选集合可以不同。例如：

```text
第 1 轮：L5(B16) + L6(B5)，使用 3 entry，两侧均完成
第 2 轮：L5(B17) + L6(B6)，使用 2 entry，两侧均完成
第 3 轮：L5(B18) + L6(B7)，使用 1 entry，仅 Level 5 完成
第 4 轮：L5(B19) + L6(B7)，使用剩余 2 entry

总使用量：3 + 2 + 1 + 2 = 8 entry
```

这里第 3 轮以后，Level 5 只有在窗口向下推进 2 行且通过全部物理检查后，才能从 `B18` 换入 `B19`；Level 6 则继续保留未完成的 `L6(B7)`。同一级不能越过本级尚未完成的普通对象。

普通轮次数量没有额外设置“最多两轮”的限制，但它受到 8-entry 总预算的自然约束：每个有效普通轮次必须至少消耗 1 个 entry，因此单个 `t` 内最多自然形成 8 个普通轮次。若当前对象是普通对象但一轮没有消耗任何 entry，也没有产生阶段状态变化，则不得空转进入下一轮，以避免无进展循环。

### 10.2 任意轮次之间的分级全 EarlyStop 清理

Level 5 和 Level 6 分别、独立地清理本级当前连续出现的全 EarlyStop 阶段对象。清理动作发生在：

1. 第一个普通轮次之前；
2. 任意两个普通轮次之间；
3. 最后一个普通轮次写回之后；
4. 普通 8-entry 预算已经耗尽之后。

每次清理时，对某一级重复执行：

```text
检查当前物理对象
    -> 若本级 32 code 全部 EarlyStop：
         执行原方案的 EarlyStopAction 和必要写回
         完成本级阶段对象
         请求转向本级下一物理对象
         联合检查下一微步窗口位置
         检查通过后提交推进并继续检查
    -> 若遇到普通对象、没有更多合法对象或受物理边界限制：
         停止本级本次清理
```

全 EarlyStop 不消耗普通 group-entry，也不计作一个普通联合调度轮次，同一个 `t` 内连续清理的数量不设置人为上限；但每结束一个对象都必须在暴露下一对象前执行微步级物理检查，不得越过本级遇到的第一个普通对象，也不得读取尚未进入 SRAM、尚未到达本级窗口或不满足 Level 5 到 Level 6 先后关系的未来对象。若当前阶段已经完成但下一对象暂时不可合法暴露，则保留“本阶段已结束”的控制状态并停止本级清理，不得先服务下一对象再在 `t` 末裁剪窗口位置。

例如：

```text
第 1 轮普通调度后剩余 5 entry
    Level 5 连续清理 L5(B17)、L5(B18) 两个 FullEarlyStop
    Level 6 连续清理 L6(B6) 一个 FullEarlyStop
    遇到普通 L5(B19) 和普通 L6(B7)

第 2 轮：L5(B19) + L6(B7)，使用 2 entry，剩余 3 entry
    Level 5 再清理新暴露的 L5(B20) FullEarlyStop
    Level 6 遇到普通对象，保持不动

第 3 轮：用重新取得的两级当前对象继续联合调度
```

即使某一轮已经耗尽第 8 个普通 entry，该轮写回后仍应继续清理新暴露的全 EarlyStop 链；清理到第一个普通对象时停止，并将该普通对象留到下一 `t`。

正常完成和 FullEarlyStop 完成均属于本级在该 `t` 内结束的阶段对象，分别计入 `C5_t` 或 `C6_t`。forced-evicted 不计入正常完成数，而是按边界规则结束当前阶段等待并保持窗口合法。

## 11. 两种强制顶出边界

本方案只允许两种由物理容量造成的强制顶出情况。

### 11.1 Level 6 到达 SRAM 顶部

边界条件为：

```text
S6_{t,r_final} = 0
```

若当前 `L6(B_i)` 在获得本时刻允许的正常服务后仍存在 pending，则在 `t -> t+1` 的物理上推后，为了继续跟随同一个 `B_i`，Level 6 窗口理论上需要移到 `-2`，这超出 SRAM 边界。

此时：

1. `L6(B_i)` 尚未产生新结果的 code 保持原有外信息；
2. 这些 code 不执行新的外信息写回；
3. 当前 Level 6 阶段对象记录为 `forced-evicted`；
4. forced-evicted 只结束 `B_i` 继续等待 Level 6 资源的阶段状态，不从唯一 SRAM 中删除其物理两行；
5. `B_i` 继续随每个时刻固定的两行节拍向 SRAM 顶部移动；
6. 只有 `B_i` 的物理两行以后真正到达 `[0,2)` 时才对外输出；
7. Level 6 阶段指针在下一合法状态转向物理顺序中的后续对象；
8. forced-evicted 不伪装成正常解码完成，也不计入 `C6_t`。

边界退出后，下一时刻 Level 6 窗口保持在顶部合法位置：

```text
S6_{t+1,0} = 0
```

特别地，当 Level 6 窗口位于 `[0,22)` 时，其实际阶段对象位于 `D6=[20,22)`；本时刻物理输出位置则是 `[0,2)`。两者不是同一组物理行，因此“Level 6 到达顶部边界”表示阶段服务机会耗尽，不表示当前 `L6(B_i)` 在该时刻立即从 SRAM 输出。

### 11.2 Level 5 追到 Level 6

两个窗口刚好相邻的条件为：

```text
S5_{t,r_final} = S6_{t,r_final} + 22
```

窗口相邻本身不触发 forced-evicted。同一个 `t` 内，如果 Level 6 已完成当前阶段，但其下一对象因为 Level 5 窗口阻挡而不能合法暴露，则先把 Level 6 记为延迟推进并停止本级继续服务；不能仅为了在本 `t` 内继续追赶而强制弹出 Level 5。

真正的碰撞边界在 `t -> t+1` 的固定物理推进前判定。必须联合计算两级下一宏观时刻的自然候选位置；只有 Level 5 为继续跟随 pending 对象所需的位置，与 Level 6 完成当前阶段后转向后续对象所需的位置确实重叠，才构成碰撞边界。

典型情况是：两个窗口当前相邻，Level 6 当前阶段对象已经结束，而 Level 5 当前阶段对象在获得本时刻允许的服务后仍有 pending。此时下一宏观时刻的 Level 6 对象切换与 Level 5 对原对象的必要跟随无法同时满足不重叠约束。

相反，如果两个相邻窗口的当前对象都仍有 pending，则在 `t -> t+1` 的物理边界可以一起向顶部移动 2 行：

```text
当前：W6=[10,32)，W5=[32,54)
下一时刻：W6=[8,30)，W5=[30,52)
```

两个窗口仍然相邻但不重叠，此时不得强制弹出 Level 5。

在不考虑 SRAM 顶部边界、且每级本时刻至多结束一个阶段对象的基本情况下，相邻窗口的四种组合为：

| Level 6 当前阶段 | Level 5 当前阶段 | 下一宏观时刻的自然结果 |
|---|---|---|
| pending | pending | 两窗口同步向顶部移动 2 行，仍相邻 |
| pending | 完成 | Level 6 向顶部跟随，Level 5 切换下一对象，间距增大 |
| 完成 | 完成 | 两级都切换下一对象，窗口仍相邻 |
| 完成 | pending | 自然候选位置重叠，触发 Level 5 边界退出 |

连续 FullEarlyStop 或多轮普通服务不改变这一判断方法，只是把一个 `t` 展开为更多内部微步；每次微步先检查可选推进，最终仍以 `t -> t+1` 的联合候选位置判定是否触发边界退出。

发生上述真正碰撞时：

1. 两个窗口不得重叠；
2. Level 6 当前窗口和 SRAM 数据不因该冲突被覆盖；
3. `L5(B_j)` 尚未产生新结果的 code 保持原有外信息；
4. 这些 code 不执行新的外信息写回；
5. 当前 Level 5 阶段对象记录为 `forced-evicted`；
6. Level 5 阶段指针在下一合法状态转向物理顺序中的后续对象；
7. forced-evicted 不伪装成正常解码完成。

在典型碰撞中，Level 5 的边界退出代替了原本非法的 `-2` 必要跟随。下一时刻 Level 5 窗口保持在本时刻最终合法起点，从而切换到物理上推后进入该位置的后续对象：

```text
S5_{t+1,0} = S5_{t,r_final}
```

该位置仍须与联合裁决后的 `S6_{t+1,0}` 一起满足不重叠约束。

这里的强制弹出只结束 `B_j` 的 Level 5 等待状态，不从连续 SRAM 中删除 `B_j` 的物理两行。`B_j` 仍随固定物理节拍向顶部流动，后续到达 Level 6 窗口时，Level 6 直接读取 SRAM 中实际保留的数据并按正常规则处理：Level 5 已完成 code 使用已经写回的结果，Level 5 未获得资源的 code 使用保持不变的原有外信息。

这一语义与原 44 行联合窗口到达 buffer 顶部时的 forced-evicted 一致：当前阶段不再继续等待，未产生的新结果不写回，物理数据流和固定两行吞吐不暂停。forced-evicted 不计入正常完成数 `C5_t/C6_t`，但对应阶段对象从本级当前等待状态中退出，窗口保持在合法边界并在后续时刻服务下一个物理对象。

两个窗口只是因为完成较快而尝试在同一个 `t` 内继续暴露后续对象时，应在每次推进前进行合法性检查。已经完成的一侧若暂时不能合法暴露下一对象，应记录延迟推进并停止继续服务，不得先读取下一对象再在 `t` 末裁剪位置，也不得为可选追赶强制弹出另一侧。forced-evicted 只用于宏观物理推进边界上，对象切换与 pending 对象的必要跟随确实无法同时满足，或者 Level 6 pending 对象已经无法继续向 SRAM 顶部跟随的情况。

### 11.3 双窗口位置的联合裁决顺序

两个窗口在每个内部微步以及 `t -> t+1` 边界的位置，都按照以下优先级统一裁决。

第一优先级是物理合法性，任何状态提交点都必须满足：

```text
0 <= S6_{t,r}
S6_{t,r} + 22 <= S5_{t,r}
S5_{t,r} + 22 <= R_mem
```

自然候选位置可以用于发现冲突，但任何已提交的微步状态、写回后的状态以及下一时刻开始状态都不得出现窗口重叠。

第二优先级是宏观物理边界上的阶段对齐。对每一级，pending 对象必须向顶部跟随 2 行才能继续指向原对象；已经结束的阶段则必须切换到物理上推后进入服务位置的后续对象。这两类都是固定数据流下的必要请求，不属于可选恢复。

第三优先级才是同一个 `t` 内为了继续利用剩余 entry 而提前暴露更多后续对象。该推进属于可延迟动作：只能使用满足 SRAM 边界和双窗口不重叠约束的空间，不能先越过物理边界服务后续对象，再依赖最终裁剪掩盖非法的中间状态。

每次状态推进的裁决过程为：

1. 以当前 `S5_{t,r}/S6_{t,r}` 和当前物理对象为起点，分别形成两级本次状态推进的请求；
2. 同一个 `t` 内，当前对象结束的一侧可以请求提前转向后续对象，pending 的一侧保持窗口；该可选推进受阻时只记录延迟推进；
3. 联合验证候选位置、下一对象有效性、Level 5 到 Level 6 的先后关系和所有窗口不变量；
4. 到 `t -> t+1` 边界时，分别形成“pending 跟随原对象”或“已结束阶段转向后续对象”的必要候选位置；
5. 两个相邻窗口若都跟随 pending 对象，则保留二者同步向顶部移动，不触发 forced-evicted；
6. 若 Level 6 pending 对象的必要跟随仍将越过 SRAM 顶部，则强制结束 Level 6 当前阶段等待，并把窗口保持在顶部合法边界；
7. 若 Level 6 已结束阶段的必要对象切换与 Level 5 pending 对象的必要跟随无法同时满足，则按照已确定的碰撞策略强制结束 Level 5 当前阶段等待；
8. forced-evicted 不作为正常完成计入 `C5_t/C6_t`；
9. 两种边界若在同一个 `t` 同时成立，可以分别处理，但每个中间状态和最终状态都必须满足全部不变量。

因此，正式原则是：先保证窗口在每个微步都不重叠、不越界，再保证未完成对象能够继续跟随，最后才推进到更多后续对象；只有合法阶段推进与 pending 对象的必要跟随确实无法共存时才强制结束相应阶段等待。

## 12. 物理—逻辑一致性不变量

后续软件模型和实现必须持续检查以下不变量。

### 12.1 唯一数据副本

Level 5/Level 6 使用同一份 SRAM 数据。阶段状态可以单独保存，但 LLR、history 和 extrinsic 不得因队列或等待而复制成彼此独立的数据版本。

### 12.2 服务对象与窗口一致

```text
H5_{t,r} == BatchAt(D5_{t,r})
H6_{t,r} == BatchAt(D6_{t,r})
```

阶段指针、诊断日志中的 batch ID 和实际 SRAM row 映射必须一致。

### 12.3 两级有序

同一级内部按 SRAM 物理流顺序服务，后进入的数据不得主动越过较早且仍合法等待的数据。`L6(B_i)` 不得早于 `L5(B_i)` 的允许终态开始。

### 12.4 窗口合法且不重叠

```text
0 <= S6_{t,r}
S6_{t,r}+22 <= S5_{t,r}
S5_{t,r}+22 <= R_mem
```

### 12.5 状态与写回一致

`AlreadyDecoded`、`writeback_complete` 和 SRAM 中的实际写回顺序必须一致。窗口或阶段指针不能在必要写回完成前越过当前对象。

### 12.6 固定物理吞吐

每个正常流 `t` 均严格执行顶部输出 2 行、整体上推 2 行和底部输入 2 行。内部完成量不能被解释为同一时刻对外输出多个数据单元。

### 12.7 完成与推进一致

对每一级、每个 `t` 均必须满足：

```text
A_l,t <= C_l,t <= A_l,t + 1
```

若 `C_l,t=A_l,t+1`，必须存在且只能存在一个“阶段已结束、下一对象尚未暴露”的延迟推进状态。该级在完成宏观边界裁决前不得继续服务更后的对象。

## 13. 基本运行示例

以下示例演示宏观时刻、内部微步、窗口运动和已确认的边界规则。示例尚不覆盖帧首填充、帧尾 drain 和 P1 状态保存细节。

设：

```text
R_buf = 32
R_mem = 76
初始 W6 = [32,54)
初始 W5 = [54,76)
```

### 13.1 两级均正常完成一个阶段对象

假设时刻 `t=0`：

```text
Level 5 当前对象正常完成
Level 6 当前对象正常完成
C5_0 = 1
C6_0 = 1
```

在 `t=0` 内，两级完成写回。Level 6 若下一对象已经合法可见，可以在内部微步推进；Level 5 位于 SRAM 底部时，下一对象 `B1` 尚未进入 SRAM，因此记录一次延迟推进，不能把窗口移到 SRAM 之外。到 `t=0 -> t=1` 边界，`B1` 写入底部，两级根据各自完成数完成对象切换，宏观位置保持不变：

```text
W6_1 = [32,54)
W5_1 = [54,76)
```

### 13.2 Level 6 pending，Level 5 正常前进

假设时刻 `t=0`：

```text
Level 6 当前对象未完成：C6_0 = 0
Level 5 当前对象完成：  C5_0 = 1
```

Level 5 位于底部，完成后先记录延迟推进；Level 6 因 pending 继续跟随原对象。则下一时刻：

```text
W6_1 = [30,52)  继续跟随原 Level 6 对象
W5_1 = [54,76)  转向下一 Level 5 对象
```

两个窗口之间形成：

```text
[52,54) = 2 行动态 buffer
```

这正是本方案相对于 44 行联合窗口方案的核心变化：Level 6 回退不再强制 Level 5 一起回退。

### 13.3 Level 5 pending，逐步追近 Level 6

假设某时刻：

```text
W6_t = [10,32)
W5_t = [38,60)
两窗口间隔 6 行
```

若 Level 6 每个时刻完成一个对象并转向后续对象，而 Level 5 连续未完成，则：

```text
t：    W6=[10,32)，W5=[38,60)，间隔6行
t+1：  W6=[10,32)，W5=[36,58)，间隔4行
t+2：  W6=[10,32)，W5=[34,56)，间隔2行
t+3：  W6=[10,32)，W5=[32,54)，窗口相邻
```

若 `t+3` 的 Level 6 当前阶段对象再次结束并转向后续对象，而 Level 5 当前对象在本时刻允许的服务后仍未完成，则宏观自然候选位置分别为 `[10,32)` 和 `[30,52)`，存在 `[30,32)` 两行重叠。两者无法同时合法提交，因此触发 Level 5 碰撞边界，对当前 `L5(B_j)` 执行 forced-evicted；任何微步都不进入重叠状态。

### 13.4 两窗口相邻且两级都 pending

假设某时刻：

```text
W6_t = [10,32)
W5_t = [32,54)
```

若 Level 5、Level 6 当前阶段对象在本时刻服务后都仍有 pending，则同一个 `t` 内两个窗口都保持当前微步位置。到 `t -> t+1` 的物理边界，两级为跟随各自原对象同时向顶部移动 2 行：

```text
W6_{t+1} = [8,30)
W5_{t+1} = [30,52)
```

两窗口仍然相邻且不重叠，因此不触发 Level 5 forced-evicted。这个案例说明“当前相邻”不是边界退出的充分条件；必须以联合候选位置是否真的重叠为准。

### 13.5 Level 6 到达顶部

假设：

```text
W6_t = [0,22)
```

若当前 `L6(B_i)` 在本时刻允许的服务后仍未完成，则 Level 6 已无法继续向顶部跟随。当前阶段对象按原策略 forced-evicted，但其实际阶段对象位于 `[20,22)`，不会因此立即作为 `[0,2)` 的顶部数据输出；其物理两行继续随 SRAM 流动。顶部物理输出和底部物理输入仍保持 2 行节拍。

### 13.6 同一个 `t` 内的轮次级对象切换

假设当前微步为：

```text
W6_{t,0} = [20,42)，H6_{t,0}=B5
W5_{t,0} = [50,72)，H5_{t,0}=B20
剩余普通预算 = 8 entry
```

第 1 轮基于同一个 64-code 快照使用 3 个 entry，`L5(B20)` 完成而 `L6(B5)` 仍有 pending。写回完成后：

```text
Level 5 请求推进到 W5=[52,74)，暴露 L5(B21)
Level 6 保持 W6=[20,42)，继续指向 L6(B5)
```

候选位置合法且不重叠，因此提交：

```text
W6_{t,1} = [20,42)，H6_{t,1}=B5
W5_{t,1} = [52,74)，H5_{t,1}=B21
剩余普通预算 = 5 entry
```

第 2 轮必须从写回后的唯一 SRAM 重新读取 `L5(B21)+L6(B5)`，再调用原共享 scheduler。若 Level 5 的推进会越过 SRAM 底部、与 Level 6 重叠或指向无效对象，则不能提交该位置，也不能在第 2 轮服务 `B21`。

## 14. 与上一代 44 行联合窗口方案的差异

| 项目 | 上一代 Buffered FIFO | 本双窗口方案 |
|---|---|---|
| SRAM 总行数 | `R_buf+44` | `R_buf+44` |
| 数据副本 | 一份连续 SRAM | 一份连续 SRAM |
| 解码窗口 | 一个 44 行联合窗口 | 两个独立的 22 行窗口 |
| 窗口起点 | 一个 `S_t` | `S5_t`、`S6_t` |
| 两级相对位置 | 永远相邻 | 可以分离，但不能重叠 |
| 服务状态 | 一个 64-code 联合 batch | 两个独立的 32-code 阶段对象 |
| 当前对象 | 一个联合 FIFO 队首 | 由两个窗口的 SRAM 映射分别确定 |
| 完成语义 | 64 code 联合完成 | Level 5/Level 6 分级完成 |
| 同一 `t` 内窗口状态 | 仅维护一个时刻级 `S_t` | 维护 `S5_{t,r}`、`S6_{t,r}` 微步状态 |
| Level 6 pending 时 | Level 5 被绑定移动 | Level 5 可以独立前进 |
| 边界 | 44 行窗口到 SRAM 顶部 | L6 到顶部；L5 追到 L6 |
| 每 `t` 物理输入/输出 | 2 BR / 32 code | 2 BR / 32 code |

## 15. 问题清单与当前结论

P0-1 至 P0-4 已经解决并固化为规则；后续 P1 问题仍待讨论。P1 问题解决后，再形成完整运行案例和代码实施方案。

### P0-1：共享普通服务预算如何作用于两个独立阶段对象（已解决）

确定规则如下：

1. 每个 `t` 共享总计 8 个普通 group-entry；
2. 完全沿用原五六级共享 scheduler、原调度顺序和 Level 5 优先规则；
3. entry 可在本轮 Level 5/Level 6 当前对象之间共享；
4. 一轮完成并写回后，只要仍有剩余 entry，就允许已完成的一侧换入本级下一对象，未完成的一侧保留原对象，再次组成联合候选集合；
5. 普通轮数不人为限制为两轮，持续到 8-entry 预算耗尽、没有普通对象或无法产生进展；
6. 所有普通轮次的 entry 使用量之和不得超过 8；
7. 同一普通轮的多个 entry 由原 scheduler 基于同一个快照统一决定，不能用前一个 entry 的执行结果改变本轮后续 entry；
8. 任意后一轮都必须在前一轮写回和微步级窗口裁决完成后，从唯一 SRAM 重新读取当前窗口对象；
9. 每次换入下一对象前都必须验证 `S5_{t,r}/S6_{t,r}` 的边界、不重叠、对象有效性和两级先后关系。
10. 当前对象已经结束但下一对象尚未合法可见时，记录延迟推进并停止本级本 `t` 的继续服务；不能越界读取未来对象。

### P0-2：分级全 EarlyStop 快路径（已解决）

确定规则如下：

1. Level 5 和 Level 6 均可独立连续追赶本级全 EarlyStop 对象；
2. 同一个 `t` 内不设置人为追赶数量上限；
3. 全 EarlyStop 不占普通 group-entry，也不占普通联合调度轮次；
4. 清理发生在第一个普通轮次前、任意两轮之间、最后一轮后以及普通预算耗尽后；
5. 一侧清理全 EarlyStop 时，另一侧保持或按自身状态独立处理；
6. 每一级遇到第一个普通对象、没有更多合法对象或受物理边界限制时停止清理；
7. 每结束一个 FullEarlyStop 对象，都必须先完成必要写回并通过微步级窗口检查，才能暴露下一个对象；
8. FullEarlyStop 完成计入本级 `C5_t/C6_t`，并执行原方案规定的 EarlyStopAction 和必要写回。

### P0-3：Level 5 追到 Level 6 时如何处理（已解决）

确定规则如下：

1. Level 5 和 Level 6 的两个 22 行窗口在任何时刻都不得重叠；
2. 两窗口相邻本身不触发强制弹出，必须先联合计算两级的下一合法位置；
3. 两级都 pending 时允许同步向顶部移动，保持相邻且不重叠；
4. 同一个 `t` 内 Level 6 的可选继续推进受 Level 5 阻挡时，只记录延迟推进，不为继续追赶而强制弹出 Level 5；
5. 典型冲突是到 `t -> t+1` 边界时，Level 6 当前阶段已经结束而 Level 5 当前对象仍有 pending；只有下一宏观时刻的联合候选位置确实重叠，才按原 buffer 边界语义强制结束 Level 5 当前阶段等待；
6. 已完成并写回的 code 保留结果，未产生新结果的 code 保持原外信息且不写回；
7. 强制弹出不删除唯一 SRAM 中的物理数据，该数据继续随 SRAM 向顶部流动，后续到达 Level 6 时仍按正常规则处理；
8. forced-evicted 不计作 Level 5 正常完成，也不改变统一的全帧 BER 口径。

### P0-4：两个窗口同时更新时的边界裁决顺序（已解决）

确定规则如下：

1. 第一优先级：保证两个窗口始终合法、永不重叠；
2. 第二优先级：在物理时刻边界完成各级必要的阶段对齐，包括 pending 跟随原对象和已结束阶段转向后续对象；
3. 第三优先级：在同一个 `t` 内利用剩余 entry 提前转向更多后续对象；
4. 每次微步推进前都检查物理约束，不能先服务非法位置上的对象，再在 `t` 末裁剪；
5. 仅有可选的连续推进受阻时，停止该侧继续换入，不把它误记为 forced-evicted；
6. 两个相邻窗口都 pending 时允许同步跟随，不触发强制弹出；
7. Level 6 pending 对象的必要跟随仍将越过 SRAM 顶部时，强制结束 Level 6 当前阶段等待；
8. 到宏观物理边界时，Level 6 完成后的对象切换与 Level 5 pending 对象的必要跟随无法共存，才强制结束 Level 5 当前阶段等待；
9. forced-evicted 不计入正常完成数，相关物理数据继续保留在 SRAM 中；
10. 每个微步以及最终提交的 `S5_{t+1,0}`、`S6_{t+1,0}` 都必须满足全部物理不变量。

### P1-1：分级分类结果的保存与重用

需要确认每一级第一次成为当前阶段对象时保存哪些结果，以及跨 `t` 时哪些字段保持不变、哪些需要根据唯一 SRAM 的最新数据重新计算。至少应明确 EarlyStop、Hybrid 分类、资源资格、mux 分配结果和 `AlreadyDecoded` 的更新时刻。

### P1-2：帧首填充与 Level 6 启动

帧首只有 Level 5 先获得新数据，Level 6 需要等待对应数据物理推进并完成 Level 5 阶段。需要定义：

- 两个窗口的初始化有效状态；
- `B0` 何时第一次到达 Level 5 实际解码区；
- `B0` 何时具备 Level 6 服务资格；
- 无有效 Level 6 对象的时刻如何参与共享调度。

### P1-3：帧尾 drain

输入停止后，需要定义：

- SRAM 是否继续以虚拟两行推进；
- Level 5/Level 6 如何分别排空 pending；
- 没有新输入时窗口公式中的固定 `-2` 是否保留；
- 两级完成和最终输出的停止条件；
- BER 尾部裁剪是否仍需要随 `R_buf` 调整。

### P1-4：完成量与统计口径

需要严格区分并定义：

```text
C5_t：Level 5 内部结束的阶段对象数
C6_t：Level 6 内部结束的阶段对象数
Normal / FullEarlyStop / ForcedEvicted
顶部物理输出量：固定 2 BR/32 code
```

已经确定 forced-evicted 不计入正常完成量，但会结束本级当前对象的等待状态；窗口保持在合法边界，并在后续时刻按物理顺序转向下一对象。P1-4 后续只需确定日志字段、汇总方式及各统计量的对外名称。

## 16. 后续验证要求

在修改完整解码代码前，应先建立只验证逻辑状态的可执行模型，至少覆盖：

1. 两级每个时刻都正常完成；
2. Level 6 连续 pending、Level 5 正常前进；
3. Level 5 连续 pending、逐步追到 Level 6；
4. Level 6 连续 pending、到达 SRAM 顶部；
5. 两级分别出现全 EarlyStop 的追赶过程；
6. 两窗口同时反向运动时的联合边界处理；
7. Level 5 forced-evicted 后的数据继续流动；
8. 帧首填充与帧尾 drain；
9. 所有时刻均保持顶部输出 2 行、底部输入 2 行；
10. `BatchAt(D5_{t,r})`、`BatchAt(D6_{t,r})` 与每个微步日志中的当前对象完全一致；
11. 两窗口永不重叠，且不发生无标记的数据跳过；
12. SRAM 中每个数据单元始终只有一份 LLR/history/extrinsic 数据；
13. 两窗口相邻且两级都 pending 时同步跟随，不发生误弹出；
14. 两窗口相邻、Level 6 完成而 Level 5 pending 时，只在宏观边界触发 Level 5 forced-evicted；
15. Level 5 位于 SRAM 底部并完成时，使用延迟推进等待下一输入，不越界读取未来对象；
16. 每一级始终满足 `A_l,t <= C_l,t <= A_l,t+1`。

建议每个 `t` 至少记录：

- `S5_before/S5_after`；

- 共享 8-entry 的分配结果；
- `C5_t/C6_t`；
- `A5_t/A6_t` 以及是否存在延迟推进；
- 两级的退休原因；
- Level 5/Level 6 forced-evicted 次数；
- 两窗口之间的剩余行数；
- Level 6 距离 SRAM 顶部的剩余行数；
- 顶部输出与底部输入的 `B_i`/row 映射。

## 17. 当前结论

本方案已经确定的核心是：

> 在 `R_buf+44` 行的唯一连续 SRAM 中，Level 5 和 Level 6 各使用一个 22 行解码窗口。两个窗口分别由物理位置绑定的阶段指针控制，可以独立浮动但不能重叠；每个 2-BR/32-code 数据单元严格先经过 Level 5、再经过 Level 6。每个时刻底部固定输入 2 行、顶部固定输出 2 行。同一 `t` 内通过微步级位置描述多轮服务，受阻的可选追赶只记录延迟推进；到宏观物理边界时，若 Level 6 pending 已无法越过 SRAM 顶部，或 Level 6 完成后的对象切换与 Level 5 pending 的必要跟随无法共存，才执行保持原外信息、不产生新写回的 forced-evicted。

方案当前已经确定多轮共享 8-entry 普通服务、两级独立 FullEarlyStop 追赶、Level 5 追到 Level 6 时的强制弹出，以及双窗口位置的联合裁决顺序。P0 逻辑问题已经闭合，下一步继续解决 P1 的状态保存、帧首启动、帧尾排空和统计口径问题。
