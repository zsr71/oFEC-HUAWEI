# Level 5/6 共享 SRAM 双窗口独立浮动方案草案

## 1. 文档状态

- 方案状态：逻辑设计草案 v0.1；
- 当前阶段：先定义方案本体，不讨论硬件 cycle、端口冲突或具体 RTL 实现；
- 基础方案：原 Level 5/6 共享解码与 44 行联合 Buffered FIFO 方案；
- 本文新增：将一个绑定移动的 44 行联合窗口拆成两个可以独立浮动的 22 行窗口；
- 状态组织：采用“方案 B”，即一份连续 SRAM 物理流、两个阶段指针以及每个数据单元的分级控制状态。

本文只将已经确认的内容写为确定规则。尚未确定的调度和状态转移细节统一列在文末，不在本版中进行推断。

## 2. 设计目标

原 Buffered FIFO 方案把 Level 6 的 22 行窗口和 Level 5 的 22 行窗口绑定成一个 44 行联合窗口。当某一级出现较多 pending code 时，两个窗口必须一起移动，另一级无法利用其自身较轻的负载独立前进或恢复位置。

本方案将联合窗口拆成：

- 一个严格对应 Level 5 的 22-block-row 解码窗口；
- 一个严格对应 Level 6 的 22-block-row 解码窗口。

两个窗口位于同一块连续 SRAM 中，可以分别改变位置。目标是在不改变物理输入、输出节拍的前提下，使两级分别吸收各自的瞬时解码需求 burst。例如，当 Level 6 因 pending 停留时，Level 5 可以继续处理后续数据并独立移动，而不再被 Level 6 的窗口位置完全绑定。

## 3. 术语与计量单位

### 3.1 物理 block row 与 code

当前参数中，一个 block row 包含 16 个 decoder/codeword row，因此：

```text
2 block rows = 32 code
```

每个时刻 `t`，SRAM 底部新进入 2 个 block row，即 32 个新 code；SRAM 顶部同时输出 2 个 block row，即 32 个旧 code。

### 3.2 物理数据单元 `B_i`

本文将每次从 SRAM 底部进入的 2 个 block row 定义为一个物理数据单元：

```text
B_i = 第 i 个进入 SRAM 的 2-BR / 32-code 数据单元
```

因此：

```text
t=0：B0 从 SRAM 底部进入
t=1：B1 从 SRAM 底部进入
t=2：B2 从 SRAM 底部进入
...
```

`B_i` 始终表示一组 2-BR/32-code 物理数据，不表示原方案中的 64-code 联合调度集合。

### 3.3 分级阶段对象

同一个物理数据单元依次经历两个阶段：

```text
L5(B_i)：B_i 的 Level 5 处理阶段
L6(B_i)：B_i 的 Level 6 处理阶段
```

数据处理先后关系固定为：

```text
B_i 进入 SRAM
    -> L5(B_i)
    -> L6(B_i)
    -> 从 SRAM 顶部输出
```

### 3.4 64-code 共享调度集合

原 Level 5/6 共享调度器一次面对：

```text
Level 5 当前 2 BR：32 code
Level 6 当前 2 BR：32 code
合计：64 code
```

因此，`64-code` 是一次 Level 5/6 共享调度的逻辑集合，不是每个时刻从 SRAM 底部进入的数据量。

在双窗口方案中，两个窗口的位置可以不同，所以同一时刻的共享调度集合可能是：

```text
L5(B_j) 的 32 code + L6(B_i) 的 32 code，且 i != j
```

## 4. 连续 SRAM 组织

### 4.1 总容量

定义：

- `R_buf`：两级窗口可以共同使用的额外 buffer 行数；
- `R_l5=22`：Level 5 窗口长度；
- `R_l6=22`：Level 6 窗口长度。

连续 SRAM 总行数固定为：

```text
R_mem = R_buf + R_l5 + R_l6
      = R_buf + 44
```

SRAM 中的 LLR、prior、history 和 extrinsic 始终只有一份。逻辑状态不得为某个 FIFO 项另外保存一份完整的 Level 5/Level 6 tile 数据快照。

### 4.2 基准布局

以 SRAM 顶部为 row 0、底部为 row `R_mem-1`。当两个窗口均处于基准位置时：

```text
[0, R_buf)              buffer
[R_buf, R_buf+22)       Level 6 窗口
[R_buf+22, R_buf+44)    Level 5 窗口
```

例如 `R_buf=32`：

```text
[0,32)    buffer
[32,54)   Level 6 窗口
[54,76)   Level 5 窗口
```

物理地址由上到下为 Level 6、Level 5；数据处理顺序由 SRAM 底部向顶部为 Level 5、Level 6。因此“永远先 Level 5、再 Level 6”描述的是数据处理顺序，不是物理 row 编号的书写顺序。

### 4.3 双窗口定义

分别定义两个窗口起点：

```text
S5_t：时刻 t 的 Level 5 窗口起点
S6_t：时刻 t 的 Level 6 窗口起点
```

窗口范围为：

```text
W5_t = [S5_t, S5_t+22)
W6_t = [S6_t, S6_t+22)
```

初始基准位置为：

```text
S6_0 = R_buf
S5_0 = R_buf + 22
```

### 4.4 窗口合法性约束

任意时刻均必须满足：

```text
0 <= S6_t
S5_t + 22 <= R_mem
S6_t + 22 <= S5_t
```

其中：

- 第一项保证 Level 6 不越过 SRAM 顶部；
- 第二项保证 Level 5 不越过 SRAM 底部；
- 第三项保证两个 22 行窗口不重叠。

窗口起点与 2-BR 物理推进单位保持同相位对齐。若 `R_buf` 采用偶数行，则可直接写为：

```text
S5_t mod 2 = 0
S6_t mod 2 = 0
```

### 4.5 动态 buffer 分布

`R_buf` 表示两个窗口之外的总额外空间，并不永久对应 SRAM 中某一段固定区域。当两个窗口独立移动时，buffer 可以动态分布在：

```text
Level 6 窗口上方：[0, S6_t)
两个窗口之间：[S6_t+22, S5_t)
Level 5 窗口下方：[S5_t+22, R_mem)
```

三段长度之和始终为：

```text
R_buf
```

## 5. 每个时刻的物理 SRAM 动作

无论两个窗口是否完成、是否存在 pending 或是否触发边界，每个正常流时刻 `t` 的物理动作固定为：

1. SRAM 顶部 `[0,2)` 的 2 个旧 block row 输出；
2. 原 `[2,R_mem)` 的内容整体向顶部移动到 `[0,R_mem-2)`；
3. 一个新的 `B_t` 写入底部 `[R_mem-2,R_mem)`；
4. 输入量固定为 2 BR/32 code；
5. 输出量固定为 2 BR/32 code。

解码完成量、窗口位置和 pending 数量不能暂停或改变这一物理节拍。

物理推进只改变数据当前所在的物理 row，不改变：

- `B_i` 的逻辑身份；
- `B_i` 内部 32 个 code 的固定编号；
- `B_i` 已经经历的 Level 5/Level 6 阶段；
- 已完成 code 的控制状态；
- SRAM 中已经完成的有效写回结果。

## 6. 每个 22 行窗口的解码对象

22 个 block row 是该级形成解码输入、history 读取和写回映射所需的完整 tile 上下文，并不表示一次同时解码 `22*16` 个 code。

当前时刻真正形成该级 32-code 调度输入的是窗口底部 2 个 block row：

```text
Level 5 实际解码区：D5_t = [S5_t+20, S5_t+22)
Level 6 实际解码区：D6_t = [S6_t+20, S6_t+22)
```

当前阶段对象必须由 SRAM 的实时 row-to-`B_i` 映射确定：

```text
H5_t = 位于 D5_t 的物理数据单元
H6_t = 位于 D6_t 的物理数据单元
```

调度器不得只根据一个可能过期的逻辑队首 ID，读取与当前物理窗口不一致的 `B_i`。

## 7. 方案 B：一份物理流与两个阶段指针

### 7.1 权威状态

本方案不使用两条独立软件 FIFO 作为服务对象的权威来源。权威关系定义为：

```text
数据和数据顺序的真源：连续物理 SRAM
当前可服务位置的真源：Level 5/Level 6 两个物理解码窗口
待执行工作的真源：每个 B_i 的分级控制状态
```

FIFO 顺序由 SRAM 中的物理先后顺序和两个阶段指针自然形成。

### 7.2 Level 5 阶段指针

Level 5 至少维护：

```text
S5_t                    当前 22 行窗口起点
H5_t                    从 D5_t 物理映射得到的当前 B_i
StageState[B_i].level5  L5(B_i) 的 32-code 状态
```

### 7.3 Level 6 阶段指针

Level 6 至少维护：

```text
S6_t                    当前 22 行窗口起点
H6_t                    从 D6_t 物理映射得到的当前 B_i
StageState[B_i].level6  L6(B_i) 的 32-code 状态
```

### 7.4 每个数据单元的控制状态

每个 `B_i` 应分别保存 Level 5 和 Level 6 的控制状态，但不保存 SRAM 数据副本。每一级的 32-code 状态至少需要表达：

- EarlyStop 结果；
- Hybrid 分类；
- HISO/SISO 资源资格；
- mux 后的资源分配结果；
- 是否已经获得解码资源；
- `pending`；
- `AlreadyDecoded`；
- `writeback_complete`；
- `forced-evicted`；
- 当前阶段是否已经结束。

一个 code 只有在对应阶段动作及其必要 SRAM 写回完成后，才能将该阶段的 `AlreadyDecoded` 和 `writeback_complete` 置为真。

## 8. 两级先后关系

对于任意 `B_i`，Level 5 必须先于 Level 6：

```text
L5(B_i) 尚未达到允许离开 Level 5 的终态
    => L6(B_i) 不得开始普通解码
```

Level 5 和 Level 6 可以在同一个 `t` 中分别服务不同的数据单元。例如：

```text
Level 5 服务 L5(B8)
Level 6 服务 L6(B5)
```

该并行关系不违反先后顺序，前提是 `B5` 已经结束其 Level 5 阶段。

## 9. 独立浮动的基本语义

每个时刻物理数据固定向顶部移动 2 行。对任意一级 `l in {5,6}`：

- 当前 `B_i` 未完成时，该级窗口需要向顶部移动 2 行，才能在下一时刻继续跟随同一个 `B_i`；
- 当前 `B_i` 完成一个阶段对象时，物理上推与转向后续对象相互抵消，该级窗口可以保持在同一物理位置；
- 当该级在同一个时刻通过允许的快路径完成多个阶段对象时，该级窗口可以向基准方向恢复；
- 两级的完成量和窗口位置分别维护，不再要求 `S5_t=S6_t+22`；
- 一个窗口保持或回退时，另一个窗口可以依据自身状态独立移动。

在不考虑耦合边界时，可以先用以下候选式描述每一级的自然运动：

```text
S5_candidate = S5_t - 2 + 2*C5_t
S6_candidate = S6_t - 2 + 2*C6_t
```

其中：

```text
C5_t = 时刻 t 内结束的 Level 5 阶段对象数
C6_t = 时刻 t 内结束的 Level 6 阶段对象数
```

候选位置不能直接作为最终位置；还必须满足 SRAM 边界、两个窗口不重叠以及本文第 11 节的强制顶出规则。`C5_t/C6_t` 是否包含分级全 EarlyStop 快路径、是否包含 forced-evicted，将在调度规则确定后给出严格定义。

## 10. 与原共享调度器的关系

本方案改变窗口和阶段状态的组织，不在当前版本中重新定义原有单次共享调度器的内部算法。当前仍保留以下基础：

- Level 5 提供 32 个 code；
- Level 6 提供 32 个 code；
- 按原映射拼成 64-code 调度输入；
- 沿用原有 EarlyStop、Hybrid 分类、HISO/SISO 资格；
- 沿用 4-code group 组织；
- 沿用最多 8 个普通 group-entry 的共享资源约束；
- 沿用 Level 5 优先的既有顺序；
- 未获得资源的 code 不产生新结果，不执行新的外信息写回，并保留为 pending；
- 已完成 code 在后续服务中通过 `AlreadyDecoded` 跳过。

双窗口独立后，64-code 调度输入的两半可能来自不同的 `B_i`，因此原来的“联合 64-code batch 整体完成、整体退休”语义不再适用。Level 5 和 Level 6 必须分别判断自己的 32-code 阶段对象是否完成，并分别更新阶段指针。

## 11. 两种强制顶出边界

本方案只允许两种由物理容量造成的强制顶出情况。

### 11.1 Level 6 到达 SRAM 顶部

边界条件为：

```text
S6_t = 0
```

若当前 `L6(B_i)` 在获得本时刻允许的正常服务后仍存在 pending，则下一时刻为了跟随同一个 `B_i`，理论上需要把 Level 6 窗口移到 `-2`，这超出 SRAM 边界。

此时：

1. 顶部仍按固定节拍输出 2 个 block row；
2. `L6(B_i)` 尚未产生新结果的 code 保持原有外信息；
3. 这些 code 不执行新的外信息写回；
4. 当前 Level 6 阶段对象记录为 `forced-evicted`；
5. Level 6 在下一时刻转向物理顺序中的后续对象；
6. forced-evicted 不伪装成正常解码完成。

### 11.2 Level 5 追到 Level 6

两个窗口刚好相邻的条件为：

```text
S5_t = S6_t + 22
```

若当前 `L5(B_j)` 在获得本时刻允许的正常服务后仍存在 pending，则下一时刻为了继续跟随它，Level 5 需要向顶部移动 2 行，从而与 Level 6 窗口重叠。

此时：

1. 两个窗口不得重叠；
2. Level 6 当前窗口和 SRAM 数据不因该冲突被覆盖；
3. `L5(B_j)` 尚未产生新结果的 code 保持原有外信息；
4. 这些 code 不执行新的外信息写回；
5. 当前 Level 5 阶段对象记录为 `forced-evicted`；
6. Level 5 在下一时刻转向物理顺序中的后续对象；
7. forced-evicted 不伪装成正常解码完成。

两个窗口只是因为完成较快而向基准位置恢复时，应对恢复位置进行合法裁剪，不应仅因一次向下恢复受到另一窗口限制就触发 forced-evicted。强制顶出只用于“当前未完成对象需要继续向顶部跟随，但已经没有物理空间”的情况。

## 12. 物理—逻辑一致性不变量

后续软件模型和实现必须持续检查以下不变量。

### 12.1 唯一数据副本

Level 5/Level 6 使用同一份 SRAM 数据。阶段状态可以单独保存，但 LLR、history 和 extrinsic 不得因队列或等待而复制成彼此独立的数据版本。

### 12.2 服务对象与窗口一致

```text
H5_t == BatchAt(D5_t)
H6_t == BatchAt(D6_t)
```

阶段指针、诊断日志中的 batch ID 和实际 SRAM row 映射必须一致。

### 12.3 两级有序

同一级内部按 SRAM 物理流顺序服务，后进入的数据不得主动越过较早且仍合法等待的数据。`L6(B_i)` 不得早于 `L5(B_i)` 的允许终态开始。

### 12.4 窗口合法且不重叠

```text
0 <= S6_t
S6_t+22 <= S5_t
S5_t+22 <= R_mem
```

### 12.5 状态与写回一致

`AlreadyDecoded`、`writeback_complete` 和 SRAM 中的实际写回顺序必须一致。窗口或阶段指针不能在必要写回完成前越过当前对象。

### 12.6 固定物理吞吐

每个正常流 `t` 均严格执行顶部输出 2 行、整体上推 2 行和底部输入 2 行。内部完成量不能被解释为同一时刻对外输出多个数据单元。

## 13. 基本运行示例

以下示例只演示已经确认的独立窗口运动，不替代文末尚待确定的共享资源细节。

设：

```text
R_buf = 32
R_mem = 76
初始 W6 = [32,54)
初始 W5 = [54,76)
```

### 13.1 两级均正常完成一个阶段对象

假设时刻 `t=0`：

```text
Level 5 当前对象正常完成
Level 6 当前对象正常完成
C5_0 = 1
C6_0 = 1
```

经过固定两行物理上推后，两个窗口均保持在原物理位置，并在 `t=1` 指向各自物理顺序中的下一对象：

```text
W6_1 = [32,54)
W5_1 = [54,76)
```

### 13.2 Level 6 pending，Level 5 正常前进

假设时刻 `t=0`：

```text
Level 6 当前对象未完成：C6_0 = 0
Level 5 当前对象完成：  C5_0 = 1
```

则下一时刻：

```text
W6_1 = [30,52)  继续跟随原 Level 6 对象
W5_1 = [54,76)  转向下一 Level 5 对象
```

两个窗口之间形成：

```text
[52,54) = 2 行动态 buffer
```

这正是本方案相对于 44 行联合窗口方案的核心变化：Level 6 回退不再强制 Level 5 一起回退。

### 13.3 Level 5 pending，逐步追近 Level 6

假设某时刻：

```text
W6_t = [10,32)
W5_t = [38,60)
两窗口间隔 6 行
```

若 Level 6 每个时刻完成一个对象并保持，而 Level 5 连续未完成，则：

```text
t：    W6=[10,32)，W5=[38,60)，间隔6行
t+1：  W6=[10,32)，W5=[36,58)，间隔4行
t+2：  W6=[10,32)，W5=[34,56)，间隔2行
t+3：  W6=[10,32)，W5=[32,54)，窗口相邻
```

若 `t+3` 的 Level 5 当前对象在本时刻允许的服务后仍未完成，则下一步继续回退会产生 `[30,52)` 与 `[10,32)` 的两行重叠。因此触发 Level 5 碰撞边界，对当前 `L5(B_j)` 执行 forced-evicted 策略，Level 5 窗口不进入非法重叠位置。

### 13.4 Level 6 到达顶部

假设：

```text
W6_t = [0,22)
```

若当前 `L6(B_i)` 在本时刻允许的服务后仍未完成，则 Level 6 已无法继续向顶部跟随。当前阶段对象按原策略 forced-evicted，顶部物理输出和底部物理输入仍保持 2 行节拍。

## 14. 与上一代 44 行联合窗口方案的差异

| 项目 | 上一代 Buffered FIFO | 本双窗口方案 |
|---|---|---|
| SRAM 总行数 | `R_buf+44` | `R_buf+44` |
| 数据副本 | 一份连续 SRAM | 一份连续 SRAM |
| 解码窗口 | 一个 44 行联合窗口 | 两个独立的 22 行窗口 |
| 窗口起点 | 一个 `S_t` | `S5_t`、`S6_t` |
| 两级相对位置 | 永远相邻 | 可以分离，但不能重叠 |
| 服务状态 | 一个 64-code 联合 batch | 两个独立的 32-code 阶段对象 |
| 当前对象 | 一个联合 FIFO 队首 | 由两个窗口的 SRAM 映射分别确定 |
| 完成语义 | 64 code 联合完成 | Level 5/Level 6 分级完成 |
| Level 6 pending 时 | Level 5 被绑定移动 | Level 5 可以独立前进 |
| 边界 | 44 行窗口到 SRAM 顶部 | L6 到顶部；L5 追到 L6 |
| 每 `t` 物理输入/输出 | 2 BR / 32 code | 2 BR / 32 code |

## 15. 当前尚待解决的问题

以下问题尚未由当前讨论确定。解决这些问题后，才能形成完整的状态转移公式、运行案例和代码实施方案。

### P0-1：共享普通服务预算如何作用于两个独立阶段对象

原方案将 Level 5 的 32 code 和 Level 6 的 32 code 合成 64-code 集合，共享最多 8 个 group-entry。新方案中两半可能来自不同的 `B_i`，需要确认：

1. 每个 `t` 是否仍只形成一次 64-code 联合调度；
2. 是否仍严格共享总计 8 个 group-entry；
3. “Level 5 优先”是否完全沿用原 scheduler 的顺序；
4. 某一级没有候选或提前完成时，空闲 entry 是否允许给另一级使用；
5. 本时刻是否允许再次组合新的阶段对象进行第二次普通调度。

### P0-2：分级全 EarlyStop 快路径

原方案只有整个 64-code 联合 batch 全 EarlyStop 才能在同一 `t` 快速退休。拆成两个阶段后，需要确认：

1. 只要 `L5(B_i)` 的 32 code 全 EarlyStop，Level 5 是否可以单独追赶下一对象；
2. 只要 `L6(B_j)` 的 32 code 全 EarlyStop，Level 6 是否可以单独追赶下一对象；
3. 同一 `t` 内每一级允许连续跨过多少个全 EarlyStop 对象；
4. 一侧连续追赶时，另一侧是否保持当前阶段对象不变；
5. 分级全 EarlyStop 如何计入 `C5_t/C6_t`。

### P0-3：Level 5 forced-evicted 后能否进入 Level 6

当 Level 5 因追到 Level 6 而 forced-evicted 时，`B_i` 仍物理存在于 SRAM 中，并将继续向顶部流动。需要确认：

1. `B_i` 是否仍允许进入 Level 6；
2. 若允许，Level 6 是否直接使用 Level 5 强制结束时保留的 SRAM 数据；
3. 此时 `L5(B_i)` 对 `L6(B_i)` 来说属于哪一种“允许终态”；
4. BER 和诊断中如何分别记录 Level 5 forced-evicted 与最终 Level 6 结果。

### P0-4：两个窗口同时更新时的边界裁决顺序

`S5_candidate` 与 `S6_candidate` 由各自完成量产生，但二者必须共同满足不重叠约束。需要确认：

1. 是先更新 Level 6，再以其新位置限制 Level 5，还是进行一次联合状态转移；
2. Level 6 向下恢复、Level 5 向上跟随同时发生时如何裁剪；
3. 判断“Level 5 顶到 Level 6”使用当前时刻位置还是候选下一时刻位置；
4. forced-evicted 是否给对应阶段提供一次等效的指针推进信用；
5. 如何保证裁剪不会跳过 SRAM 中尚未服务的数据单元。

### P1-1：分级分类结果的保存与重用

需要确认每一级第一次成为当前阶段对象时保存哪些结果，以及跨 `t` 时哪些字段保持不变、哪些需要根据唯一 SRAM 的最新数据重新计算。至少应明确 EarlyStop、Hybrid 分类、资源资格、mux 分配结果和 `AlreadyDecoded` 的更新时刻。

### P1-2：帧首填充与 Level 6 启动

帧首只有 Level 5 先获得新数据，Level 6 需要等待对应数据物理推进并完成 Level 5 阶段。需要定义：

- 两个窗口的初始化有效状态；
- `B0` 何时第一次到达 Level 5 实际解码区；
- `B0` 何时具备 Level 6 服务资格；
- 无有效 Level 6 对象的时刻如何参与共享调度。

### P1-3：帧尾 drain

输入停止后，需要定义：

- SRAM 是否继续以虚拟两行推进；
- Level 5/Level 6 如何分别排空 pending；
- 没有新输入时窗口公式中的固定 `-2` 是否保留；
- 两级完成和最终输出的停止条件；
- BER 尾部裁剪是否仍需要随 `R_buf` 调整。

### P1-4：完成量与统计口径

需要严格区分并定义：

```text
C5_t：Level 5 内部结束的阶段对象数
C6_t：Level 6 内部结束的阶段对象数
Normal / FullEarlyStop / ForcedEvicted
顶部物理输出量：固定 2 BR/32 code
```

特别需要确认 forced-evicted 是否不计入正常完成量，但在窗口位置转移中具有“转向下一对象”的效果。

## 16. 后续验证要求

在修改完整解码代码前，应先建立只验证逻辑状态的可执行模型，至少覆盖：

1. 两级每个时刻都正常完成；
2. Level 6 连续 pending、Level 5 正常前进；
3. Level 5 连续 pending、逐步追到 Level 6；
4. Level 6 连续 pending、到达 SRAM 顶部；
5. 两级分别出现全 EarlyStop 的追赶过程；
6. 两窗口同时反向运动时的联合边界处理；
7. Level 5 forced-evicted 后的数据继续流动；
8. 帧首填充与帧尾 drain；
9. 所有时刻均保持顶部输出 2 行、底部输入 2 行；
10. `BatchAt(D5_t)`、`BatchAt(D6_t)` 与日志中的当前对象完全一致；
11. 两窗口永不重叠，且不发生无标记的数据跳过；
12. SRAM 中每个数据单元始终只有一份 LLR/history/extrinsic 数据。

建议每个 `t` 至少记录：

- `S5_before/S5_after`；
- `S6_before/S6_after`；
- `D5_t/D6_t`；
- `H5_t/H6_t`；
- 当前两个 32-code 阶段对象的 pending/AlreadyDecoded 数量；
- 共享 8-entry 的分配结果；
- `C5_t/C6_t`；
- 两级的退休原因；
- Level 5/Level 6 forced-evicted 次数；
- 两窗口之间的剩余行数；
- Level 6 距离 SRAM 顶部的剩余行数；
- 顶部输出与底部输入的 `B_i`/row 映射。

## 17. 当前结论

本方案已经确定的核心是：

> 在 `R_buf+44` 行的唯一连续 SRAM 中，Level 5 和 Level 6 各使用一个 22 行解码窗口。两个窗口分别由物理位置绑定的阶段指针控制，可以独立浮动但不能重叠；每个 2-BR/32-code 数据单元严格先经过 Level 5、再经过 Level 6。每个时刻底部固定输入 2 行、顶部固定输出 2 行。Level 6 到达 SRAM 顶部或 Level 5 追到 Level 6 且仍需继续跟随 pending 对象时，采用保持原外信息、不产生新写回的 forced-evicted 策略。

方案当前尚未闭合的核心是两个独立阶段对象如何共享原有 8-entry 普通服务、分级全 EarlyStop 如何追赶、Level 5 强制顶出后如何进入 Level 6，以及两个候选窗口位置同时更新时的精确裁决顺序。
