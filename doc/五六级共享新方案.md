# 五六级共享新方案

## 1. 方案目标

在五、六级共享解码中，某些时刻可能出现 64-code batch 的 EarlyStop 率突然降低，导致需要 HISO/SISO 正常解码的 code 数量突增，形成瞬时需求 burst。

本方案通过保存未获得解码资源的 pending code，并允许其在后续时刻继续按照原五六级共享调度流程解码，将瞬时需求摊到后续时刻；在出现全 EarlyStop 的低负载时刻，再通过同一时刻内的快路径完成多个 batch，使解码窗口恢复到基准位置。

本文只定义方案的逻辑语义。具体软件字段、数据结构、硬件周期、端口和流水线实现不属于本文范围。

## 2. 基本定义

### 2.1 可调物理参数

buffer 行数不是方案固定常量。定义：

- `R_buf`：buffer block-row 行数，是可配置的非负整数，可按 SRAM 容量和目标 burst 吸收能力设置；
- `R_l6=22`：Level 6 在联合窗口中的行数；
- `R_l5=22`：Level 5 在联合窗口中的行数；
- `R_win=R_l6+R_l5=44`：联合解码窗口宽度；
- `R_mem=R_buf+R_win`：连续 SRAM 总行数。

`R_buf` 在一次方案运行中作为已配置参数保持不变，不随 `t` 动态变化；不同实验或具体实现可以选择不同值。增大 `R_buf` 只增加可保存的回退深度和连续 SRAM 容量，不改变每个普通 batch 每个 `t` 最多 8 个 group-entry 的服务规则，也不能解决长期平均需求超过平均服务能力的问题。

本文和交互演示使用 `R_buf=32` 作为默认示例，因此默认总容量是 `32+22+22=76` 行。除非某个案例明确写出默认值，否则窗口和边界公式均使用可调参数 `R_buf`。

- `B0`、`B1`、`B2`：按照到达顺序编号的 64-code batch。
- `t=0`、`t=1`、`t=2`：连续的批次/调度时刻。
- `C_t`：时刻 `t` 内部正常完成并退休的 batch 数；全 EarlyStop 快路径完成的 batch 也计入 `C_t`，forced-evicted 不计入；它不表示对外输出 batch 数。
- `pending`：本时刻未获得 HISO/SISO 解码资源、需要后续重新调度的 code。
- `AlreadyDecoded`：已经完成解码和必要联合写回、后续不再进入 mux/scheduler 的 code。
- `forced-evicted`：窗口到达边界后仍未完成、为保持固定物理吞吐而被强制顶出的 code。

每个 `t` 到达一个新的 64-code batch。新 batch 追加到 FIFO 尾部，服务始终从 FIFO 队首开始。

## 3. 主流程摘要

```text
新 batch B_t 到达并进入 FIFO 尾部
        |
        v
取 FIFO 队首 batch
        |
        v
应用 64-code AlreadyDecoded 完成屏蔽
未完成 code 沿用原 EarlyStop / Hybrid / mux 状态
        |
        +--> 64 个 code 全部 EarlyStop
        |        |
        |        +--> 快速完成当前 batch
        |             同一 t 继续检查下一个队首
        |
        +--> 存在普通解码 code
                 |
                 +--> 沿用原 scheduler，最多 8 个 group-entry
                 +--> 获得资源的 code 完整解码和写回
                 +--> 未获得资源的 code 保持 pending
                 +--> 普通 batch 剩余资源不跨 batch 转交

当前 t 服务结束
        |
        +--> 统计内部正常完成数 C_t
        +--> 更新 S_{t+1}=clip(S_t-2+2*C_t,0,R_buf)
        +--> 顶部输出两行、整体上推两行、底部写入两行
        +--> S_t=0 且仍有 pending 时，执行 forced-evicted 边界处理
```

## 4. 物理内存与窗口

系统使用一块连续的 block-row 内存，不为每个 batch 单独分配 RAM。通用布局如下，实际 buffer 行数由配置参数 `R_buf` 决定：

```text
[0, R_buf)       buffer 区，共 R_buf 个 block row
[R_buf, R_buf+22)       Level 6 区，共 22 个 block row
[R_buf+22, R_buf+44)     Level 5 区，共 22 个 block row
```

联合解码窗口宽度固定为 44 个 block row。窗口起点记为 `S_t`，合法范围为 `[0, R_buf]`：

```text
Level 6: [S_t,     S_t + 22)
Level 5: [S_t + 22, S_t + 44)
```

每个时刻边界执行固定的物理推进：

1. 顶部两行输出；
2. 原有 row 整体向上移动两行；
3. 底部写入新到达 batch 的两行。

物理推进不改变 batch 的逻辑 ID、code ID、group ID 或 FIFO 顺序。每个 `t` 固定上推两行，因此 buffer 最多提供 `floor(R_buf/2)` 个完整两行回退步长；不另外定义独立的时间窗口长度。

## 5. 一个时刻的服务流程

### 5.1 队首选择

正常区间严格 FIFO：当前最早未完成的 batch 必须先获得服务，后续 batch 不能越过它。只有队首完成、全 EarlyStop 快速退休或在 `S_t=0` 被强制顶出后，队列才转向下一个 batch。

### 5.2 在原方案上增加 `AlreadyDecoded` 屏蔽

当前 batch 的 64 个 code 仍然完整沿用原五六级共享方案的状态和处理顺序：EarlyStop 判断、对非 EarlyStop code 执行 Hybrid classify-only、生成资源资格、进入原有 4-code 分组和最多 8 个 group-entry 的 mux/scheduler。新方案不重新定义 EarlyStop、Hybrid 分类、HISO/SISO 资格或 `Unscheduled` 的含义。

新方案在原流程进入 mux/scheduler 前只增加一个 code 粒度的 `AlreadyDecoded[i]` 覆盖位：

```text
AlreadyDecoded[i] = true
    -> code i 已在当前 batch 的更早服务时刻完成
    -> 本 t 不再进入 EarlyStop/Hybrid、group 负载统计、mux 或 HISO/SISO
    -> 不再次执行解码，也不再次写回

AlreadyDecoded[i] = false
    -> code i 仍未完成
    -> 按保存的原五六级分类、资源资格和调度语义继续处理
```

EarlyStop code 也包含在后续的 `AlreadyDecoded` 完成集合中，但有明确的时序区别：在它第一次被处理的当前 `t` 内，它仍按原方案的 `EarlyStop` 路径执行；该路径完成后，从下一次调度开始将其 `AlreadyDecoded` 位置为 true。对于全 64-code EarlyStop batch，64 个 code 在同一 `t` 内全部完成，batch 直接退休，通常不再进入下一 `t`；如果保留 batch 的完成位图，其 64 个位置均视为已完成。

因此，`AlreadyDecoded` 是覆盖在原方案状态之上的新增完成标记，不是用来替代原 EarlyStop/Hybrid 分类的新分类枚举。`pending` 也不是新增的 mux 前分类：它表示该 code 在上一 `t` 的原调度结果中未获得 HISO/SISO 资源。到下一 `t` 时，该 code 保持 `AlreadyDecoded=false`，并按保存的原分类和资源资格重新进入原 scheduler。

已经通过 EarlyStop、HISO 或 SISO 完成的 code 都将 `AlreadyDecoded` 置为 true。跨时刻等待期间不刷新原始输入和分类；只有仍未完成的 code 继续参加调度。

### 5.3 原调度器

应用 `AlreadyDecoded` 屏蔽后，其余未完成 code 完全按照原五六级共享方案进入原有 mux 和 group scheduler：

- 每个普通 batch 每个 `t` 最多获得 8 个 group-entry；
- group 选择、HISO/SISO 资格和 mux 分配规则保持原方案不变；
- 获得 HISO/SISO 资源的 code 按原五六级流程完整执行联合解码和写回；
- 本轮未获得资源的 code 在 mux 后标记为 pending，下一 `t` 重新参与同一调度流程；
- `AlreadyDecoded` code 不再重复分类、分组、解码或写回。

### 5.4 全 EarlyStop 快路径

如果当前队首 batch 的 64 个 code 全部 EarlyStop：

- 不进入普通 HISO/SISO 解码；
- 不生成新的 extrinsic；
- 不执行新的外信息写回，原外信息保持不变；
- 立即完成并退休该 batch；
- 同一 `t` 内立即检查下一个队首 batch。

同一 `t` 内连续完成的全 EarlyStop batch 数量不设理论上限，直到 FIFO 为空或遇到第一个需要普通 HISO/SISO 解码的 batch。

全 EarlyStop 是唯一允许跨 batch 追赶的特殊路径。普通 batch 提前完成后的剩余 group-entry、HISO 或 SISO 机会不转交给下一个普通 batch。

## 6. 完成、输出与窗口更新

### 6.1 Batch 正常完成

一个 batch 在以下条件同时满足时正常完成：

- 64 个 code 均已完成；
- 原五六级联合解码流程及必要的 extrinsic/history 写回已完成。

正常完成和全 EarlyStop 快路径完成的 batch 计入 `C_t`。`C_t` 只表示五六级内部在本 `t` 完成了多少个 batch，不表示本 `t` 对外输出了多少个 batch。

### 6.2 物理输出节拍

无论 `C_t` 是 0、1 还是大于 1，物理内存每个 `t` 仍只输出顶部两行并推进两行。

当 `C_t>1` 时，额外完成的 batch 仍保留在连续内存中，等待后续物理上推到顶部再输出。此时发生的是解码窗口向基准位置恢复，而不是对外接口在一个 `t` 内输出多个 batch。

### 6.3 窗口状态转移

窗口起点按下式更新：

```text
S_{t+1} = clip(S_t - 2 + 2*C_t, 0, R_buf)
```

其含义为：

- `C_t=0`：窗口回退两行，继续跟随当前 pending batch；
- `C_t=1`：固定上推两行与完成一个 batch 的推进相互抵消，窗口保持；
- `C_t>=2`：窗口按 `2*(C_t-1)` 向基准位置恢复。

`C_t` 用于窗口状态转移和方案分析，不要求调度器运行时额外观察或反馈 `C_t`。

## 7. `S_t=0` 边界

当 `S_t=0` 且顶部所属 batch 仍有 pending 时，系统不暂停输入、不建立额外保存区，也不继续等待该 batch：

1. 顶部两行仍按固定节拍输出；
2. 全部 row 继续上推两行，底部继续写入新输入；
3. 被顶出的 pending code 标记为 `forced-evicted`，永久退出后续调度；
4. 原外信息保持不变，不生成新的 extrinsic，不执行新的外信息写回；
5. 该强制退休不计入 `C_t`、吞吐量匹配或译码质量统计；
6. 下一时刻服务随物理上推进进入窗口的下一个 FIFO batch。

`forced-evicted` 与正常完成、EarlyStop 完成严格区分。它是保持固定物理吞吐的边界动作，不代表产生了有效的新解码结果。

## 8. 方案不采用的行为

- 不允许后续 batch 越过未完成的 FIFO 队首；
- 不把普通 batch 的剩余资源转交给下一个普通 batch；
- 不根据未来 batch 的 EarlyStop 率、pending 数量或负载做前瞻调度；
- 不在等待期间刷新 pending code 的输入、history 或任务参数；
- 不把已完成 code 重新送入 mux/scheduler；
- 不定义获得 HISO/SISO 资源后的失败重试或 `decode-failed` 方案状态；
- 不把强制顶出的两行计入内部正常完成量或译码质量统计。

## 9. 逻辑不变量

方案运行过程中必须保持：

1. batch 正常服务顺序始终为 `B0 -> B1 -> B2 -> ...`；
2. 每个 code 在正常路径至多完成和写回一次；
3. 只有 pending code 可以在下一 `t` 重新进入普通调度；
4. `AlreadyDecoded` code 永久退出后续普通调度；
5. Level 5/Level 6 始终保持窗口内固定的 22+22 相对布局；
6. `C_t` 只统计正常完成和全 EarlyStop 快路径完成的 batch，forced-evicted 不计入 `C_t`；
7. 物理两行输出和两行上推节拍不因 `C_t>1` 改变；
8. 窗口起点始终满足 `0 <= S_t <= R_buf`。

## 12. 详细逻辑规范

本章把草稿本中已经确认的结论整理为可直接用于设计评审的规范。除非特别说明，以下规则均属于正常流阶段的强制语义，而不是可选策略。

### 12.1 时刻与吞吐量单位

t 同时表示批次时刻和五、六级调度时刻。它不是硬件 clock cycle，也不是一次单独的 HISO/SISO 调用。一个 t 包含当前队首 batch 的完整逻辑服务，以及可能发生的连续全 EarlyStop 快路径。

系统吞吐量按 64-code batch 的批次节拍观察：每个 t 到达一个新的 batch，物理阵列每个 t 接收两行新数据并输出顶部两行。group-entry、HISO、SISO 只描述一个 batch 内的服务工作量，不改变吞吐量的计量单位。

C_t 是五、六级在 t 内部正常完成并退休的 batch 数，包含全 EarlyStop 快路径完成的 batch，不包含 forced-evicted。C_t 不表示对外输出了多少 batch；对外物理输出始终是每个 t 两行。

### 12.2 FIFO 与服务顺序

在正常区间，FIFO 是唯一的 batch 服务顺序：

1. 新到达的 B_t 追加到 FIFO 尾部；
2. 服务选择最早尚未完成的队首 Bh；
3. Bh 未完成时，任何后续 batch 都不能越过它开始普通解码；
4. Bh 正常完成后，FIFO 转向下一个队首；未使用的普通资源不转交，但仍允许检查新队首是否满足全 EarlyStop 快路径；
5. 新队首只有在 64 个 code 全部 EarlyStop 时才可在同一个 t 内立即完成；如果它是普通 batch，则等待下一 t 获得自己的普通服务预算；
6. S_t=0 时顶部 pending 被 forced-evicted，是固定物理吞吐下的容量边界例外，不属于后续 batch 主动越过队首。

系统不根据未来 batch 的 EarlyStop 率、pending 数量或负载做前瞻，不做跨 batch 的全局负载排序。

### 12.3 一个普通 batch 的服务边界

一个普通 batch 在一个 t 内最多获得 8 个 group-entry 的原有调度机会。服务顺序沿用原五六级共享流程：

```text
Level 1-4 当前窗口处理及原有写回
    -> Level 5/Level 6 读取已写回输入
    -> EarlyStop/Hybrid 分类
    -> 原 mux/group scheduler，最多 8 个 group-entry
    -> 获得 HISO/SISO 资源的 code 执行联合解码
    -> extrinsic/history 写回
    -> 统计本 t 正常完成的 batch
```

普通 batch 提前完成时，未使用的 group-entry、HISO 或 SISO 服务能力不跨 batch 转交。可以继续检查新队首是否为全 EarlyStop：若是，则走不占普通资源的快路径；若不是，则该普通 batch 必须在后续 t 以自己的 64-code 状态进入原 scheduler。

### 12.4 pending 的产生与恢复

pending 只在本轮 mux/group 调度结束后产生。以下“HISO/SISO candidate”只是对原方案资源资格的简称，不是新方案增加的分类。准确的状态转换为：

```text
原始 HISO/SISO candidate
    -> 本轮未获得对应资源
    -> mux 后标记 pending
    -> 下一 t 恢复为原始 HISO/SISO candidate
    -> 获得资源后执行完整联合解码
    -> completed / AlreadyDecoded
```

已经获得 HISO/SISO 资源的 code 不属于 pending；它按原流程完成本次联合解码和写回。本文不定义“获得资源后执行失败并自动回到 pending”的新状态。

### 12.5 code 粒度 exactly-once 规则

完成状态必须保持在 code 粒度：

- AlreadyDecoded code 永久退出后续 mux、group、HISO、SISO 和写回；
- 只有 pending code 可以在下一 t 重新进入普通调度；
- EarlyStop code 直接完成，但保持原外信息，不生成新的 extrinsic，不执行新的外信息写回；
- 正常 code 至多完成一次、正常写回一次；
- 一个 batch 只有在 64 个 code 都完成且必要内部写回完成后才正常退休；
- forced-evicted 是边界退出状态，不得伪装成正常完成或 EarlyStop 完成。

## 13. 完整调度结果与批次缓冲

### 13.1 完整 64-code batch 缓冲

逻辑 FIFO 的队列项是完整的 64-code batch，而不是把 pending code 压缩成跨 batch 的全局 code 队列。每个 batch 始终保留：

- batch ID、到达时刻和 FIFO 顺序；
- 64 个固定 code 位置及原始 group/code 编号；
- 每个 code 的原始 EarlyStop/Hybrid 分类和 HISO/SISO 资格；
- 最近一次 mux 后的资源获得结果；
- completed/AlreadyDecoded、pending、执行和写回状态；
- 原始输入、history、任务参数、地址映射或其无损引用。

部分 code 已完成时，只改变其逻辑状态，不改变 batch 的 64-code 固定布局。即使 B0 只剩一个 pending code，也不能让 B1 越过 B0 或改变 B0 的 code/group 编号。

### 13.2 mux 后 per-code 调度结果

P1-8 所说的“调度结果”不是单纯的分类标签，而是一次 8-entry/mux 调度后的完整 per-code 结果。它至少需要能够回答：

1. code 原本属于 EarlyStop、HISO 还是 SISO 路径；
2. code 是否具备 HISO/SISO 资源资格；
3. 本轮是否实际获得资源；
4. 获得了哪个 group-entry、core 或资源槽位；
5. 没有获得资源时是否为 Unscheduled/pending；
6. 执行是否产生结果，内部写回是否完成。

下一 t 使用这份结果和 completed 位图构造调度输入：completed code 由 `AlreadyDecoded=true` 屏蔽；pending code 保持 `AlreadyDecoded=false`，按保存的原 EarlyStop/Hybrid 分类和资源资格重新进入原 scheduler。这里不建立新的 mux 前分类状态。

### 13.3 跨时刻输入冻结

pending code 等待期间不刷新 Lin/Lch/history、alpha、beta、信道项、量化参数、目标地址或原始 row 映射。后续真正获得资源时，使用原始 batch 版本的输入和参数。连续内存的物理上推只改变物理位置，不改变这些逻辑引用。

## 14. 物理内存、row 映射与窗口移动

### 14.1 SRAM 阵列

物理存储是一块连续的 R_mem-row SRAM，每行包含 8 个 block，其中 R_mem=R_buf+44：

```text
物理 row 0 ... R_buf-1                 buffer 容量，共 R_buf 行
物理 row R_buf ... R_buf+21            S_0=R_buf 时的 Level 6 基准位置，共 22 行
物理 row R_buf+22 ... R_buf+43         S_0=R_buf 时的 Level 5 基准位置，共 22 行
```

后两段是基准位置，不是永久固定区域。对任意 S_t，当前逻辑窗口为：

```text
Level 6 = [S_t,      S_t + 22)
Level 5 = [S_t + 22, S_t + 44)
buffer  = [0, S_t) 和 [S_t + 44, R_mem) 的并集
```

因此 Level 5/Level 6 会随窗口起点移动，而 buffer 总容量始终为 R_buf 行。当前默认 R_buf=32 时，阵列退化为 76 行示例。

### 14.2 固定物理推进

当前 t 的窗口服务和必要写回完成后，固定执行：

1. 顶部 [0,2) 两行输出；
2. 原 [2,R_mem) 上移到 [0,R_mem-2)；
3. 新到达 batch 的两行写入 [R_mem-2,R_mem)。

在 t=0/1/2 的连续输入中，底部新 batch 依次为：

```text
t=0: [R_mem-2,R_mem) 写入 B0
t=1: [R_mem-2,R_mem) 写入 B1，B0 的两行上推到 [R_mem-4,R_mem-2)
t=2: [R_mem-2,R_mem) 写入 B2，B1 位于 [R_mem-4,R_mem-2)，B0 位于 [R_mem-6,R_mem-4)
```

顶部两行输出和底部两行输入不因队首是否完成而暂停。物理推进不改变 batch、code、group 或 FIFO 的逻辑身份。

### 14.3 窗口状态转移

```text
S_{t+1} = clip(S_t - 2 + 2*C_t, 0, R_buf)
```

其中 -2 来自每时刻固定上推，+2*C_t 来自本时刻内部完成 batch 对服务对象的推进：

- C_t=0：窗口回退两行，继续跟随当前 pending 队首；
- C_t=1：完成一个 batch 与固定上推抵消，窗口保持；
- C_t>=2：窗口按 2*(C_t-1) 向基准位置 `R_buf` 恢复；
- S_t=0：不再向 buffer 方向回退，进入 forced-evicted 边界；
- 最大完整回退步数为 floor(R_buf/2)，如果 R_buf 不是 2 的整数倍，剩余单行不形成额外的一次两行回退。

## 15. 快路径、边界和吞吐规则

### 15.1 全 EarlyStop 快路径

全 EarlyStop 是唯一可以在同一个 t 内跨 batch 的路径：

- 64 个 code 必须全部 EarlyStop；
- 不进入普通 Hybrid/HISO/SISO；
- 不消耗普通 8-entry 服务能力；
- 不生成新的 extrinsic，不执行新的外信息写回；
- 立即完成当前 batch 并计入 C_t；
- 同一 t 继续检查下一个 FIFO 队首；
- 连续数量没有理论上限，直到 FIFO 为空或遇到普通 batch。

普通 batch 的剩余 group-entry、HISO、SISO 机会不能转交给后续普通 batch。普通 batch 完成后仍可检查新队首；只有新队首全 EarlyStop 时，才可不使用这些普通机会而在同一个 t 快速完成。

### 15.2 S_t=0 强制顶出

当 S_t=0 且顶部 batch 仍有 pending：

1. 仍输出顶部两行；
2. 仍上推全部 row 两行；
3. 仍在底部写入新 batch 两行；
4. 顶部 pending 转为 forced-evicted 并永久退出；
5. 原外信息保持不变，不生成 extrinsic，不执行新的写回；
6. 不计入 C_t、吞吐量或译码质量；
7. 下一时刻服务随物理上推进进入窗口的下一个 batch。

不暂停输入、不建立额外保存区、不阻止 row 推进，也不引入 E_t 作为方案主状态。forced_evict_count 只可以作为可选观测量。

### 15.3 有限 buffer 吞吐匹配

系统允许短期内部完成缺口，但缺口必须受 R_buf 个 buffer row 和 S_t=0 边界限制。每次 C_t=0 消耗两行回退空间，最多形成 `floor(R_buf/2)` 个完整两行回退步长；后续 C_t>=2 才能恢复窗口。默认 R_buf=32 时，最多为 16 个回退步长。

该约束是有限 buffer 匹配，不是逐时刻严格“一进一出”，也不是没有边界的长期平均匹配。物理输出仍保持每个 t 两行；C_t>1 只表示内部窗口恢复更快，额外完成 batch 留在连续内存中等待后续物理输出。

## 16. 详细运行案例

本节给出可以逐项核对的完整逻辑算例。除 16.6 的容量边界案例外，均使用默认 `R_buf=32`、`R_mem=76`。示例中的具体分类和 code 编号只用于展示新方案如何调用原调度器；组排序、组内 HISO/SISO 选择和 entry slot 分配仍采用原五六级共享方案。

### 16.1 算例公共约定

64 个 code 使用 0-based 稳定编号：

```text
code 0..31  = Level 5 code 0..31
code 32..63 = Level 6 code 0..31

G0  = code 0..3
G1  = code 4..7
...
G15 = code 60..63
```

每个 group-entry 对应原方案中的一个 4-to-1 HISO MUX 和一个 4-to-1 SISO MUX，因此一次 group-entry 最多选择一个 HISO code 和一个不同的 SISO code。一个普通 batch 在一个 `t` 内累计最多使用 8 个 group-entry；原调度器可以在这 8 个 slot 内进行多轮 group 重入。

主算例设 `B0` 的原始状态如下：

| Group        | Code                   | 原方案状态和资源资格         |
| ------------ | ---------------------- | ---------------------------- |
| `G0..G11`  | 每组`4g+0`、`4g+1` | 非 EarlyStop，`HisoOrSiso` |
| `G0..G11`  | 每组`4g+2`、`4g+3` | 非 EarlyStop，`SisoOnly`   |
| `G12..G15` | `code 48..63`        | EarlyStop                    |

因此 `B0` 有 16 个 EarlyStop code 和 48 个普通候选，EarlyStop 率为 25%。每个 `G0..G11` 初始都有 4 个普通候选，初始非空组数 `K=12`。为使 slot 表易于核对，示例采用原调度器在相同负载下按较小 group/code 编号打破平局的结果。

### 16.2 `t=0`：burst 首次产生 pending

时刻开始时：

| 项目               | 值                  |
| ------------------ | ------------------- |
| 新到达 batch       | `B0`              |
| FIFO               | `[B0]`            |
| 当前服务           | `B0`              |
| `S_0`            | `32`              |
| Level 6 区域       | `[32,54)`         |
| Level 5 区域       | `[54,76)`         |
| 底部输入           | `B0 -> [74,76)`   |
| 本时刻顶部输出     | `[0,2)`，固定两行 |
| `AlreadyDecoded` | 64 位全为 false     |

`B0` 先完整执行原方案的 EarlyStop 和 Hybrid classify-only。`G12..G15` 的 16 个 EarlyStop code 直接完成，不进入普通 mux；`G0..G11` 进入原 group scheduler。由于 `K=12>8`，原调度器按组负载排序后只选择前 8 个组，即 `G0..G7`：

| Entry slot |  Group |   HISO 选择 |   SISO 选择 |
| ---------: | -----: | ----------: | ----------: |
|          0 | `G0` |  `code 0` |  `code 2` |
|          1 | `G1` |  `code 4` |  `code 6` |
|          2 | `G2` |  `code 8` | `code 10` |
|          3 | `G3` | `code 12` | `code 14` |
|          4 | `G4` | `code 16` | `code 18` |
|          5 | `G5` | `code 20` | `code 22` |
|          6 | `G6` | `code 24` | `code 26` |
|          7 | `G7` | `code 28` | `code 30` |

本时刻执行和写回完成后：

- `code 48..63`：EarlyStop 完成；
- 上表中的 16 个 code：获得资源并完成原五六级联合解码和必要写回；
- `G0..G7` 中尚未选中的 `4g+1`、`4g+3`：共 16 个 pending；
- `G8..G11` 没有获得 group-entry：4 组共 16 个 pending；
- `B0` 共完成 32 个 code，剩余 32 个 pending，batch 尚未完成；
- 下一 `t` 中这 32 个已完成 code 的 `AlreadyDecoded` 置为 true。

因此：

```text
C_0 = 0
S_1 = clip(32 - 2 + 2*0, 0, 32) = 30
下一解码窗口 = [30,74)
```

时刻边界仍固定输出顶部两行、全部 row 上推两行，并在底部接收下一批次；`B0` 是否完成不改变物理两行节拍。

### 16.3 `t=1`：只重新调度 `B0` 的 pending code

`t=1` 到达 `B1`，但 FIFO 队首仍是 `B0`：

| 项目                  | 值                |
| --------------------- | ----------------- |
| 新到达 batch          | `B1`            |
| FIFO                  | `[B0, B1]`      |
| 当前服务              | `B0`            |
| `S_1`               | `30`            |
| 当前解码窗口          | `[30,74)`       |
| 底部输入              | `B1 -> [74,76)` |
| `B0.AlreadyDecoded` | 32 个 true        |
| `B0` 待调度         | 32 个 pending     |

进入原 scheduler 前，`AlreadyDecoded=true` 的 32 个 code 被直接屏蔽，不再进行 EarlyStop/Hybrid、组负载统计或 mux。剩余 pending 保持原分类和资源资格：

```text
G0..G7  : 每组剩余 2 个，分别为 4g+1、4g+3
G8..G11 : 每组剩余 4 个
```

当前仍有 12 个非空组。按剩余数量降序，`G8..G11` 的负载 4 高于 `G0..G7` 的负载 2；剩余同负载组按原顺序选择。因此 8 个 entry slot 为：

| Entry slot |   Group |   HISO 选择 |   SISO 选择 | 调度后该组剩余 |
| ---------: | ------: | ----------: | ----------: | -------------: |
|          0 |  `G8` | `code 32` | `code 34` |              2 |
|          1 |  `G9` | `code 36` | `code 38` |              2 |
|          2 | `G10` | `code 40` | `code 42` |              2 |
|          3 | `G11` | `code 44` | `code 46` |              2 |
|          4 |  `G0` |  `code 1` |  `code 3` |              0 |
|          5 |  `G1` |  `code 5` |  `code 7` |              0 |
|          6 |  `G2` |  `code 9` | `code 11` |              0 |
|          7 |  `G3` | `code 13` | `code 15` |              0 |

执行完成后，本时刻新增完成 16 个 code。`B0` 累计已有 48 个 `AlreadyDecoded`，仍有 16 个 pending：

```text
G4..G7  : 每组剩余 4g+1、4g+3
G8..G11 : 每组剩余 4g+1、4g+3
```

`B0` 尚未完成，所以 `B1` 不能越过它获得普通服务：

```text
C_1 = 0
S_2 = clip(30 - 2 + 2*0, 0, 32) = 28
下一解码窗口 = [28,72)
```

### 16.4 `t=2`：`B0` 完成，但窗口不立即恢复

`t=2` 到达 `B2`：

| 项目                  | 值                |
| --------------------- | ----------------- |
| FIFO                  | `[B0, B1, B2]`  |
| 当前服务              | `B0`            |
| `S_2`               | `28`            |
| 当前解码窗口          | `[28,72)`       |
| 底部输入              | `B2 -> [74,76)` |
| `B0.AlreadyDecoded` | 48 个 true        |
| `B0` 待调度         | 16 个 pending     |

此时只有 `G4..G11` 非空，每组恰好剩余一个 `HisoOrSiso` 和一个 `SisoOnly` code，`K=8`。原调度器给每组一个 entry：

| Entry slot |   Group |   HISO 选择 |   SISO 选择 |
| ---------: | ------: | ----------: | ----------: |
|          0 |  `G4` | `code 17` | `code 19` |
|          1 |  `G5` | `code 21` | `code 23` |
|          2 |  `G6` | `code 25` | `code 27` |
|          3 |  `G7` | `code 29` | `code 31` |
|          4 |  `G8` | `code 33` | `code 35` |
|          5 |  `G9` | `code 37` | `code 39` |
|          6 | `G10` | `code 41` | `code 43` |
|          7 | `G11` | `code 45` | `code 47` |

16 个 pending 全部完成并完成必要写回，`B0` 的 64 个 code 全部成为 `AlreadyDecoded`，`B0` 正常退休。注意本时刻只完成了一个 batch：

```text
C_2 = 1
S_3 = clip(28 - 2 + 2*1, 0, 32) = 28
```

因此 `t=3` 服务 `B1` 时仍使用 `[28,72)`，而不是立刻恢复到 `[30,74)`。原因是每个 `t` 的固定上推贡献 `-2`，本时刻只完成一个 batch 的服务推进贡献 `+2`，两者正好抵消。

### 16.5 `t=3`、`t=4`：全 EarlyStop 追赶并恢复窗口

假设只有在 batch 成为队首时才检查其实际状态，不读取未来 batch 信息。`B1`、`B2` 均为全 64-code EarlyStop；`B3` 是普通 batch；`B4` 为全 EarlyStop。

#### `t=3`

`B3` 到达后，FIFO 为 `[B1,B2,B3]`，窗口起点仍为 `S_3=28`：

1. 检查队首 `B1`，发现 64 个 code 全部 EarlyStop；`B1` 不进入普通 scheduler，不写回外信息，立即完成，`C_3` 加 1。
2. 队首切换为 `B2`，此时才检查 `B2`；`B2` 同样全 EarlyStop，立即完成，`C_3` 再加 1。
3. 队首切换为 `B3`，此时才检查 `B3`；发现它不是全 EarlyStop，于是停止跨 batch 快路径，并让 `B3` 使用本 `t` 的普通 8-entry 服务能力。

为明确普通服务结果，设 `B3` 只有 `G0..G4` 各有 4 个普通候选，其余 code EarlyStop。原多轮 scheduler 的结果为：

```text
第一轮：G0、G1、G2、G3、G4 各进入一次，共使用 5 个 entry
第二轮：剩余 3 个 entry 交给 G0、G1、G2 再进入一次
结果：G0..G2 完成，G3、G4 各剩 2 个 pending，共 4 个 pending
```

因此 `B3` 在 `t=3` 未完成，但 `B1`、`B2` 已通过快路径完成：

```text
C_3 = 2
S_4 = clip(28 - 2 + 2*2, 0, 32) = 30
```

窗口只恢复两行到 `[30,74)`。虽然五六级内部在 `t=3` 完成了 `B1`、`B2` 两个 batch，但物理上仍只输出 `[0,2)` 两行；两个已完成 batch 的内容继续留在连续内存中，等待后续逐时刻上推到顶部。

#### `t=4`

`B4` 到达后，FIFO 为 `[B3,B4]`。首先继续服务 `B3`：

| Entry slot |  Group |   HISO 选择 |   SISO 选择 |
| ---------: | -----: | ----------: | ----------: |
|          0 | `G3` | `code 13` | `code 15` |
|          1 | `G4` | `code 17` | `code 19` |

`B3` 使用 2 个普通 group-entry 后完成。剩余 6 个普通 entry 不转交给另一个普通 batch。随后检查新的队首 `B4`：

- 如果 `B4` 是普通 batch，即使需求很小，也必须等到 `t=5` 才获得自己的普通预算；
- 本例中 `B4` 的 64 个 code 全部 EarlyStop，因此它仍可走不占普通资源的特殊快路径，在 `t=4` 立即完成。

所以：

```text
C_4 = 2  // B3 正常完成 + B4 全 EarlyStop 完成
S_5 = clip(30 - 2 + 2*2, 0, 32) = 32
```

窗口恢复到基准 `[32,76)`。这个过程同时说明了两条不同规则：普通 batch 的剩余 entry 不跨 batch 转交；全 EarlyStop 快路径不使用这些 entry，因此仍可在同一个 `t` 完成后续队首。

#### `t=0..t=4` 总表

| `t` | 新到达 | 时刻开始队首 | `S_t` / 解码窗口 | 普通服务结果                              | 快路径完成 | `C_t` | `S_{t+1}` |
| ----: | -----: | -----------: | ------------------ | ----------------------------------------- | ---------- | ------: | ----------: |
|     0 | `B0` |       `B0` | `32 / [32,76)`   | `B0` 完成 16 个普通 code，剩 32 pending | 无         |       0 |          30 |
|     1 | `B1` |       `B0` | `30 / [30,74)`   | `B0` 再完成 16 个，剩 16 pending        | 无         |       0 |          28 |
|     2 | `B2` |       `B0` | `28 / [28,72)`   | `B0` 剩余 16 个完成并退休               | 无         |       1 |          28 |
|     3 | `B3` |       `B1` | `28 / [28,72)`   | `B3` 使用 8 entry 后剩 4 pending        | `B1、B2` |       2 |          30 |
|     4 | `B4` |       `B3` | `30 / [30,74)`   | `B3` 使用 2 entry 完成                  | `B4`     |       2 |          32 |

每一行的物理动作都相同：顶部 `[0,2)` 输出、原 `[2,76)` 上推到 `[0,74)`、新 batch 两行写入 `[74,76)`。变化的只是当前逻辑解码窗口、FIFO 队首和内部完成数 `C_t`。

### 16.6 可调 buffer 的 `S_t=0` 边界案例

为了不用列出默认 32-row buffer 下的 16 次回退，本例单独配置 `R_buf=4`，因此：

```text
R_mem = 4 + 44 = 48
S_0 = 4
基准窗口 = [4,48)
底部输入 = [46,48)
最多提供 floor(4/2) = 2 个完整两行回退步长
```

假设 `B0` 连续两个时刻都没有完成：

| `t` | `S_t` | 当前窗口   |                 `C_t` | 更新结果                           |
| ----: | ------: | ---------- | ----------------------: | ---------------------------------- |
|     0 |       4 | `[4,48)` |                       0 | `S_1=2`，继续保留 `B0` pending |
|     1 |       2 | `[2,46)` |                       0 | `S_2=0`，buffer 回退空间耗尽     |
|     2 |       0 | `[0,44)` | 不把强制顶出计入`C_2` | 触发容量边界                       |

在 `t=2`，即使 `B0` 顶部所属内容仍有 pending，也不暂停新输入，不再为 `B0` 扩展等待空间：

1. 顶部 `[0,2)` 仍按固定节拍输出；
2. 原 `[2,48)` 仍上推到 `[0,46)`；
3. 新到达的 `B2` 两行仍写入 `[46,48)`；
4. `B0` 尚未完成的 code 转为 forced-evicted，保持原外信息，不产生 extrinsic，不执行新写回；
5. 强制顶出不计入正常完成量 `C_2`，也不计入译码质量；
6. 窗口保持 `[0,44)`，后续服务对象按 FIFO 转向随物理推进进入窗口的 `B1`。

在本边界时刻若没有其他 batch 通过正常路径完成，则 `C_2=0`，窗口仍满足 `S_3=clip(0-2+2*0,0,4)=0`；强制顶出只维持物理两行节拍，不制造“完成一个 batch”的假象。

如果使用默认 `R_buf=32`，边界规则完全相同，只是正常区间最多有 16 个完整两行回退步长；增大 `R_buf` 只推迟触及该边界的时刻，不改变边界动作。

## 17. 验证与观测要求

### 17.1 必须验证的性质

1. 每个 code 最终只能进入正常完成、EarlyStop 完成或 forced-evicted 之一；
2. 正常 code 至多完成一次、写回一次；
3. batch 正常服务顺序保持 FIFO；
4. 64-code 固定 code/group 编号不因 pending 或窗口移动改变；
5. AlreadyDecoded code 不再进入 mux/scheduler；
6. 只有 mux 后未获资源的 code 才能成为 pending；
7. 每个 t 顶部输出两行、底部输入两行；
8. Level 6/Level 5 始终分别占当前窗口前 22 行和后 22 行；
9. C_t=0/1/2+ 的窗口转移符合公式；
10. 普通 batch 资源余量不跨 batch 转交；
11. 全 EarlyStop 可以在同一 t 连续快路径完成；
12. S_t=0 只触发明确的 forced-evicted 边界，不发生无标记丢失；
13. pending 等待期间原始输入、history、参数和目标地址语义保持冻结；
14. 后续 batch 不使用未来 batch 的前瞻信息。

### 17.2 建议观测指标

- 每个 t 的新到达 batch 数和 C_t；
- max(0,C_t-1) 净追赶量；
- FIFO batch 数、队首 pending code 数和最老等待年龄；
- 当前 S_t、窗口净变化和距 S_t=0 的回退步数；
- 8-entry、HISO、SISO 的普通服务使用量；
- 正常完成、全 EarlyStop 完成和 forced-evicted 分别计数；
- 顶部两行输出和底部两行输入；
- 可选的 forced_evict_count。

forced-evicted 不纳入正常吞吐量匹配和译码质量统计，只作为边界压力观测。

### 17.3 评价场景

第一阶段至少覆盖：单个短时 burst、可由全 EarlyStop 恢复的 burst、连续 C_t=0 直到 S_t=0 的 burst，以及长期平均需求高于抽象服务能力的持续超载。评价维度包括 FIFO backlog 峰值、最老等待年龄、窗口恢复时间、forced-evicted 数量、资源利用率和物理两行节拍是否保持。
