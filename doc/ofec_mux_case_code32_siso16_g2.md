# oFEC 分组 MUX 运行示例：`code=32`、`SISO=16`、`G=2`

## 1. 场景定义
本例固定如下参数：
- `N_code = 32`（即 `state` 长度为 32）
- `siso_active_for_tile = 16`
- `MUX_GROUP_G = 2`

`state` 语义沿用当前实现：
- `state[i] = 0`：该行需要 SISO（NeedSiso）
- `state[i] = 1`：该行已早停（EarlyStopped）
- `state[i] = 2`：该行本轮未分配到 SISO（Unscheduled）

## 2. 当前代码里的执行路径
以单个 tile 为单位，当前流程是：
1. 在 [ofec_tile_impl.ipp](/home/zsr71/projects/newcode/src/rx/ofec/detail/ofec_tile_impl.ipp:86) 计算 `early_stop_stats`。  
2. 在 [ofec_tile_impl.ipp](/home/zsr71/projects/newcode/src/rx/ofec/detail/ofec_tile_impl.ipp:88) 把 `row_passed_flags` 转成 `mux_state`（`1/0`）。  
3. 在 [ofec_tile_impl.ipp](/home/zsr71/projects/newcode/src/rx/ofec/detail/ofec_tile_impl.ipp:90) 调用 `apply_siso_budget_grouped(mux_state, 16, 2)` 做分组裁剪。  
4. row core 在 [ofec_row_decoder_core.cpp](/home/zsr71/projects/newcode/src/rx/ofec/ofec_row_decoder_core.cpp:122) 按 `mux_state` 分流：
- `2`：本轮跳过，不产生输出；
- `1`：走 early-stop process；
- `0`：走正常 Chase。

## 3. `G=2` 时的分组与预算
在 `N_code=32, SISO=16, G=2` 下：
1. code 分 2 组，每组 16 个索引：
- 组0：`[0..15]`
- 组1：`[16..31]`

2. SISO 预算分 2 组，每组 8 个：
- budget0 = 8
- budget1 = 8

规则是“组内裁剪、组间不借用”：
- 每组只统计本组里的 `state==0`；
- 每组最多保留 8 个 `0`；
- 超出的 `0` 改成 `2`。

## 4. 运行示例 A（极端：没有早停）
假设 early-stop 后初始状态是：
- `state[0..31]` 全部为 `0`

执行分组裁剪：
1. 组0有 16 个 `0`，预算 8 -> 后 8 个改成 `2`。  
2. 组1有 16 个 `0`，预算 8 -> 后 8 个改成 `2`。  

最终结果：
- `0` 的数量：16  
- `1` 的数量：0  
- `2` 的数量：16  

解释：
- 32 个需要解码的行里，只有 16 行拿到 SISO；
- 剩余 16 行被标记成 `2`，本轮直接跳过。

## 5. 运行示例 B（有部分早停）
假设初始状态按组如下：
- 组0（索引 `0..15`）：`1` 有 5 个，`0` 有 11 个  
- 组1（索引 `16..31`）：`1` 有 9 个，`0` 有 7 个

执行分组裁剪：
1. 组0预算 8，`0` 有 11 -> 超出 3 个，改为 `2`。  
2. 组1预算 8，`0` 有 7 -> 不超额，不改。  

最终结果统计：
- `1` 总数：`5 + 9 = 14`
- `0` 总数：`8 + 7 = 15`
- `2` 总数：`3 + 0 = 3`

解释：
- 组0出现了“需求大于组内预算”，所以产生 `2`；
- 组1虽然有富余，但不能借给组0（这是 `G=2` 的关键影响）。

## 6. 与 `G=1`（max 全局池化）对比
同样 `N_code=32, SISO=16`：
- `G=1`：在全局 32 行上统一挑 16 行保留为 `0`，灵活性最大。  
- `G=2`：被拆成两组各 8 的硬预算，灵活性降低，容易出现额外 `2`。  

所以在同样 SISO 数下，`G` 增大后，`state==2` 通常更容易上升。

## 7. 同参数下 `G=8` 时怎么分组
仍然使用同一组参数：
- `N_code = 32`
- `siso_active_for_tile = 16`
- `MUX_GROUP_G = 8`

分组结果会变成：
1. code 分 8 组，每组 4 个索引：
- 组0：`[0..3]`
- 组1：`[4..7]`
- 组2：`[8..11]`
- 组3：`[12..15]`
- 组4：`[16..19]`
- 组5：`[20..23]`
- 组6：`[24..27]`
- 组7：`[28..31]`

2. SISO 预算分 8 组，每组 2 个：
- budget 向量为：`[2,2,2,2,2,2,2,2]`

组内裁剪规则不变：
- 每组只处理本组 `state==0`；
- 每组最多保留 2 个 `0`；
- 超出的 `0` 改 `2`。

极端例子（初始 32 个全是 `0`）：
1. 每组有 4 个 `0`，预算 2。  
2. 每组都会有 2 个 `0` 被改成 `2`。  
3. 8 组总共改动 `2*8=16` 个。  

最终统计：
- `0` 的数量：16
- `1` 的数量：0
- `2` 的数量：16

和 `G=2` 的关键差异：
- 总预算同样是 16，但 `G=8` 每组只有 2 个名额；
- 组越细，组间不可借用的影响越明显；
- 在真实非均匀负载下，`G=8` 往往比 `G=2` 更容易产生额外 `state==2`。
