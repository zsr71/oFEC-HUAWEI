# oFEC 软硬混合方案三详细设计

## 0. 当前落地状态（2026-05-07）

方案三已经在当前代码中落地为主线结构，核心对象位于：

- `src/rx/ofec/detail/ofec_tile_dispatch.ipp`
- `src/rx/ofec/detail/ofec_tile_decode.ipp`
- `src/rx/ofec/detail/ofec_tile_impl.ipp`
- `src/rx/ofec/detail/ofec_window_impl.ipp`

当前真实流程是：

```text
process_window_impl
  -> process_tile_impl
    -> prepare_tile_inputs
    -> detect_tile_early_stop
    -> build_tile_dispatch_plan
      -> run_hybrid_prepass
      -> run_mux_on_soft_candidates
    -> decode_tile_with_plan
      -> materialize_early_stop_rows
      -> materialize_hard_finish_rows
      -> build_soft_only_mux_state
      -> run_soft_decode_full_rows
      -> merge_soft_decoder_result
      -> postprocess_by_dispatch_tag
    -> writeback_tile
```

与最初详细设计相比，当前代码有 4 个明确差异：

- 暂未接入 `kSiHoActiveList`，hybrid prepass 目前不受独立 SIHO 预算限制。
- 不再使用 compact `SoftDecodeBatch`，soft path 保持完整行域，通过 soft-only `mux_state` 控制哪些行进入 Chase。
- `HYBRID_ENABLE_LIST` 已经落地，用于按 tile 开关方案三；空列表表示沿用全局 `HYBRID_ENABLE`。
- `HYBRID_USE_FAST_CLASSIFIER=true` 时已接入 `S0/S1/S3` 快速分类器；`TwoMain` 分支仍复用现有 BCH t=2 hard decoder 兜底。

当前 app 配置入口：

- `apps/ofec_single.cpp`
- `apps/ofec_ber_window_probe.cpp`

可配置项：

```cpp
static constexpr bool kHybridEnable = true;
static const std::vector<int> kHybridEnableList = {0,0,0,0,0,1};
static constexpr bool kHybridFastClassifier = true;
static constexpr bool kHybridNormalizeSoftOnly = false;
```

这组配置的实际含义是：只有最后一级 tile 启用方案三，前面 tile 仍走老 soft 路径；fast classifier 只在启用 hybrid 的 tile 上生效。

本文专门展开 [软硬混合当前代码落地设计.md](/home/zsr71/projects/newcode/doc/软硬混合当前代码落地设计.md) 中的“实现方案三”，即：

> 不再让 `mux_state` 同时承担“是否参与 SISO 调度”和“这一行最终执行什么动作”两种语义，而是引入统一的 `RowDispatchPlan`，把 `early-stop`、`hard-finish`、`soft-decode`、`unscheduled` 明确拆开。

本文目标是把方案三从“方向建议”细化成：

1. 面向当前代码的结构改造思路
2. 新的数据结构与模块边界
3. 对现有 `prepare -> early-stop -> MUX -> decode -> writeback` 链路的替换方式
4. 分阶段落地顺序、测试口和风险点

## 1. 为什么方案三值得单独做

前两种落地方案都能验证软硬混合是否有收益，但都有结构上的问题：

### 1.1 方案一的问题

方案一把 hybrid 逻辑塞进 `Decoder_Core_impl(...)` 内部。

优点是改动小，但代价也明确：

- `NeedSiso` 集合不变
- `SISO_ACTIVE_LIST` 的预算竞争不变
- 只能减少 Chase 调用，不能减少 MUX 压力

它只适合作为“先看 BER、先看输出语义”的快验版本。

### 1.2 方案二的问题

方案二虽然能在 MUX 前把“前端已完成行”移出 `NeedSiso`，但通常会引入下面的问题：

- `mux_state` 语义膨胀
- `TileEarlyStopResult` 同时装 early-stop 和 hybrid 信息，结构开始发散
- pre-pass 可能会和 row 阶段再次做一次硬译码，形成重复计算

它是一个可用的中间态，但不是长期最优结构。

### 1.3 方案三要解决的核心矛盾

当前代码里，实际上有两个概念被绑在同一个 `mux_state` 上了：

1. 这行是否还需要参与 SISO 预算竞争
2. 这行最后走什么执行路径

这两个概念在软硬混合之后已经不等价：

- `EarlyStopped`：不占 SISO，但走 early-stop action
- `HardFinished`：不占 SISO，但走真正的硬纠完成路径
- `Unscheduled`：不占 SISO，也不产生输出
- `SoftDecode`：占 SISO，走 Chase

所以方案三的本质不是“再加一种状态”，而是：

> 把“资源竞争状态”和“执行动作”彻底拆开。

## 2. 方案三的总体设计目标

方案三希望同时满足下面 6 个目标：

1. `EarlyStop`、`HardFinish`、`SoftDecode`、`Unscheduled` 语义明确分离
2. MUX 只关心“哪些行还要抢 SISO”，不关心这些行最终为何需要 SISO
3. hybrid pre-pass 成功后的输出可以缓存，不在 row 阶段重复硬译码
4. `writeback_tile(...)` 尽量保持不动
5. Chase core 尽量复用现有实现，不重写译码器主体
6. 后续可以自然加 `Suspicious`、`LLR guard`、更细的 syndrome 分类

## 3. 对当前代码的保留与重构边界

方案三不是“全部推倒重来”，而是只重构 tile 中段。

### 3.1 建议原样保留的部分

- `prepare_tile_inputs(...)`
- `writeback_tile(...)`
- `bch_255_239_decode_hiho_cw_255(...)`
- 现有 Chase 各变体实现
- `perform_hard_decode(...)` 的硬纠输出语义

### 3.2 需要重构的部分

- `process_tile_impl(...)`
- `decode_tile(...)`
- `Decoder_Core_impl(...)` 的调用方式
- `mux_state` 的使用方式
- tile 级统计结构

### 3.3 重构原则

不是改 `writeback` 去适配新结构，而是：

> 在 `decode_tile_with_plan(...)` 阶段把所有执行分支重新合并回一个“完整行域”的 `DecoderCoreResult`，这样写回阶段仍然只认“每一行有没有输出、输出内容是什么”。

这是方案三里最关键的兼容思路。

## 4. 目标结构概览

方案三建议把当前 tile 级主链路改成下面这样：

```text
prepare_tile_inputs
  -> detect_tile_early_stop
  -> run_hybrid_prepass
  -> build_tile_dispatch_plan
  -> run_mux_on_soft_candidates
  -> finalize_dispatch_plan
  -> decode_tile_with_plan
    -> materialize_early_stop_rows
    -> materialize_hard_finish_rows
    -> build_soft_only_mux_state
    -> run_soft_decode_full_rows
    -> merge_soft_decoder_result
    -> postprocess_by_dispatch_tag
  -> writeback_tile
```

与当前链路相比，差异有 3 个：

1. `mux_state` 不再直接驱动 row decoder 的所有动作
2. soft rows 不再压缩成 compact batch，而是在完整行域上用 soft-only `mux_state` 控制哪些行进入 Chase
3. early-stop 和 hard-finish 的输出都在 `decode_tile_with_plan(...)` 中显式合并

注意：`pick_siho_active_for_tile` 是后续预留步骤，当前代码尚未接入独立的 SIHO 预算。

### 4.1 预留设计：`kSiHoActiveList` 与 `kSisoActiveList` 的分工

注意：当前代码只接入了 `kSisoActiveList` 和 `kHybridEnableList`。`kSiHoActiveList` 仍是后续用于约束 hard prepass 尝试次数的设计预留。

方案三建议增加一张新的 per-tile 预算表：

```cpp
static const std::vector<int> kSiHoActiveList = {32, 32, 32, 32, 32, 32};
```

它和现有 `kSisoActiveList` 的分工不同：

- `kSiHoActiveList[t]`
  - 控制第 `t` 个 tile 在 hybrid prepass 阶段最多允许多少行尝试硬解码
  - 约束的是 `perform_hard_decode(...)` 的前置尝试次数
  - 不表示硬纠一定成功，也不表示最终有多少行变成 `HardFinish`
- `kSisoActiveList[t]`
  - 控制第 `t` 个 tile 在 MUX 后最多允许多少行进入 Chase/SISO
  - 约束的是 soft path 的并行/资源预算
  - 只作用于 hybrid prepass 后仍然保留为 `SoftDecode` 的候选行

两张表都建议使用 bottom->top 的 tile 索引语义，和当前 `SISO_ACTIVE_LIST[t]` 保持一致。

推荐语义：

- `kSiHoActiveList[t] >= rows_to_decode`
  - 当前 tile 的 hard prepass 不受预算限制
- `kSiHoActiveList[t] == 0`
  - 当前 tile 不做 hard prepass，所有非 early-stop 行直接保留为 `SoftDecode`
- `0 < kSiHoActiveList[t] < hard_candidate_count`
  - 只挑前 `kSiHoActiveList[t]` 个 hard candidate 尝试硬解码
  - 未被尝试的行不算 `HardFail`，而是直接保留为 `SoftDecode`

这样可以分别评估两类硬件资源约束：

- SIHO/hard prepass 资源不足时，能提前完成的行数会下降
- SISO/Chase 资源不足时，进入 soft path 的行会继续被 MUX 裁剪

## 5. 核心数据结构

### 5.1 `HybridRowClass`

表示 hybrid 判决引擎对每一行的解释结果。

```cpp
enum class HybridRowClass : uint8_t {
  None = 0,
  Clean,
  ParityOnly,
  OneMain,
  OneMainPlusParity,
  TwoMain,
  Suspicious,
  HardFail
};
```

说明：

- `None`：这行没有走 hybrid pre-pass，例如它已经被 early-stop 判成可停
- `HardFail`：前端不能可靠完成，后续仍需 soft path
- `Suspicious`：后续扩展用，第一版可以不启用

### 5.2 `RowDispatchTag`

表示每一行最终执行哪条路径。

```cpp
enum class RowDispatchTag : uint8_t {
  SoftDecode = 0,
  EarlyStopAction,
  HardFinish,
  Unscheduled
};
```

说明：

- 这是“执行计划”
- 不是 MUX 状态
- 不是 syndrome 分类

### 5.3 `RowDispatchEntry`

每一行的完整调度描述。

```cpp
struct RowDispatchEntry {
  RowDispatchTag tag = RowDispatchTag::SoftDecode;
  HybridRowClass hybrid_class = HybridRowClass::None;
  bool early_stop_hit = false;
  bool scheduled_for_soft = false;
};
```

字段解释：

- `tag`
  - 最终执行路径
- `hybrid_class`
  - 若走过 hybrid pre-pass，记录分类结果
- `early_stop_hit`
  - 当前早停判据是否命中
- `scheduled_for_soft`
  - 仅对 `SoftDecode` 行有意义
  - 表示它在 MUX 后是否保住了 SISO 预算

### 5.4 `TileDispatchPlan`

这是方案三的核心对象。

```cpp
template <typename CoreLLR>
struct TileDispatchPlan {
  std::vector<RowDispatchEntry> rows;

  std::vector<int> soft_candidate_rows;
  std::vector<int> soft_scheduled_rows;
  std::vector<int> soft_unscheduled_rows;

  matrix::Matrix<float> hard_finish_lout;
  std::vector<bool> hard_finish_valid;

  std::vector<HybridRowClass> hybrid_classes;

  std::size_t rows_early_stop = 0;
  std::size_t rows_hard_finish = 0;
  std::size_t rows_soft_candidate = 0;
  std::size_t rows_soft_scheduled = 0;
  std::size_t rows_soft_unscheduled = 0;
};
```

设计重点：

- `rows.size()` 始终等于 `rows_to_decode`
- `hard_finish_lout` 也是“完整行域”大小，而不是只存命中行
- 这样后续 merge 时不需要再做复杂回填
- 如果引入 `kSiHoActiveList`，建议额外统计：
  - `rows_hard_candidate`
  - `rows_hard_attempted`
  - `rows_hard_skipped_by_budget`
  - `rows_hard_finish`

这些统计可以区分“没有硬纠成功”与“根本没被 SIHO 预算允许尝试”。

### 5.5 soft-only `mux_state`

当前推荐不再构造 `SoftDecodeBatch`，而是保留完整行域，给 Chase core 传一个 soft-only `mux_state`：

```cpp
std::vector<uint8_t> soft_mux_state(rows_to_decode, Unscheduled);
for (int row : plan.soft_scheduled_rows) {
  soft_mux_state[row] = NeedSiso;
}
```

说明：

- `NeedSiso`
  - 这一行真正进入 Chase
- `Unscheduled`
  - 这一行不在 soft path 中产出结果

这样做的收益：

- 调试信息、`expected_bits`、行号 lookup 全部保持 full row 坐标
- 不需要 compact row 与 full row 的双向映射
- `decode_tile_with_plan(...)` 合并结果时只需要按 full row 回填

### 5.6 硬件拍级时序：TwoCandidate 会延迟 Chase 判定

如果把方案三映射到硬件流水，`S0/S1/S3` 快速分类器不能在同一拍内把所有 Chase 候选都最终确定下来。原因是 `TwoCandidate` 只是“两错候选”，还不是最终 `HardFinish`。

推荐按下面时序理解：

```text
第 1 拍：
  计算 32 行码字的 S0 / S1 / S3。

第 2 拍：
  对 32 行做 fast classification。
  Clean / ParityOnly / OneMain / OneMainPlusParity：
    可以直接形成 hard_finish_mask_fast。
  明显 HardFailCandidate：
    可以直接形成 chase_mask_fast。
  TwoCandidate：
    只能送入 BCH hard decoder 或 two-error locator + Chien confirm。

第 3 拍：
  TwoCandidate confirm 返回。
  confirm 成功：
    形成 two_hard_finish_mask。
  confirm 失败：
    形成 two_chase_mask。
  这时才能得到完整 Chase candidate mask。
```

因此最终 mask 应该在第 3 拍合成：

```text
hard_finish_mask =
    hard_finish_mask_fast | two_hard_finish_mask

chase_candidate_mask =
    chase_mask_fast | two_chase_mask
```

这里有一个关键约束：

```text
TwoCandidate 不能在第 2 拍直接算 HardFinish，
也不建议在第 2 拍提前决定是否进入 Chase。
```

更稳的硬件调度方式是：MUX / Chase 调度等 `TwoCandidate` confirm 结束后统一进行。这样不会把本来能硬完成的 two-error 行提前占用 Chase 资源，也不会漏掉 hard confirm 失败后必须进入 Chase 的行。

如果为了降低延迟，在第 2 拍先调度确定的 Chase 行，第 3 拍再补 two-fail 行，则 MUX 预算会变复杂：第二拍可能已经用完 `SISO_ACTIVE` 名额，第三拍返回的 two-fail 行需要抢占、重排或额外缓冲。第一版硬件实现不建议走这个复杂调度。

## 6. 模块划分建议

### 6.1 `run_hybrid_prepass(...)`

职责：

- 对“尚未 early-stop”的行做前端 hard-finish 尝试
- 记录 `HybridRowClass`
- 若成功，直接生成这行完整的 `lout`

当前代码接口：

```cpp
template <typename LLR>
void run_hybrid_prepass(const TilePrepared<LLR>& prep,
                        const std::vector<bool>& early_stop_row_flags,
                        const Params& p,
                        TileDispatchPlan<typename TilePrepared<LLR>::CoreLLR>* plan);
```

当前内部支持两种引擎：

- `HYBRID_USE_FAST_CLASSIFIER=false`：直接复用现有 BCH 硬译码器。
- `HYBRID_USE_FAST_CLASSIFIER=true`：先跑 `S0/S1/S3` 快速分类，`TwoMain` 再复用 BCH t=2 decoder 兜底。

`siho_active_for_tile` 还没有接入；后续如果接入 `kSiHoActiveList[t]`，它将用于限制本 tile 最多尝试多少行硬解码。

当前行为：

1. 先收集 hard candidates：未 early-stop 且当前仍为 `SoftDecode` 的行
2. 对所有 candidate 尝试 hard prepass
3. 硬纠成功：标记为 `HardFinish`
4. 硬纠失败：标记为 `HardFail`，但仍保留为 `SoftDecode`

后续接入 SIHO 预算后，超出 `siho_active_for_tile` 的 candidate 应直接保留为 `SoftDecode`，不能统计成 `HardFail`，否则会把“资源没给到”和“硬纠真的失败”混在一起。

### 6.2 `build_tile_dispatch_plan(...)`

职责：

1. 初始化所有行默认 `SoftDecode`
2. 把 early-stop 命中行标成 `EarlyStopAction`
3. 调 `run_hybrid_prepass(...)`
4. 对 hybrid 成功行改成 `HardFinish`
5. 生成 `soft_candidate_rows`

建议接口：

```cpp
template <typename CoreLLR>
TileDispatchPlan<CoreLLR> build_tile_dispatch_plan(
    const TilePrepared<typename CoreLLR>& prep,
    const TileEarlyStopResult& early_stop_stats,
    const Params& p);
```

### 6.3 `run_mux_on_soft_candidates(...)`

职责：

- 只让 `SoftDecode` 候选行参与 MUX
- 但必须在“完整行域”上保留组拓扑

建议不要直接把 soft rows 压缩后拿去跑 MUX，因为当前 grouped budget / scheme C 的分组是按原始行号区间来的。

正确做法是：

1. 在完整行域上构造一个 `mux_candidate_state`
2. 只有 soft candidate 行标成 `NeedSiso`
3. 其他行统一映射成一个“非 NeedSiso”占位值
4. 复用当前 MUX 预算和 reconfig 逻辑
5. 再把结果映射回 `TileDispatchPlan`

建议接口：

```cpp
template <typename CoreLLR>
void run_mux_on_soft_candidates(TileDispatchPlan<CoreLLR>* plan,
                                int siso_active_for_tile,
                                const Params& p,
                                const TileEarlyStopResult& early_stop_stats);
```

### 6.4 `build_soft_decode_batch(...)`

职责：

- 已废弃，不再推荐作为方案三主线

原因：

- compact 会引入调试行号、`expected_bits`、trace entry 的额外转换
- 当前 `Decoder_Core_impl(...)` 已经支持通过 `mux_state` 跳过非 `NeedSiso` 行
- 保留完整行域更接近旧路径，也更容易做 `HYBRID_ENABLE=false` 回归比对

替代接口建议：

```cpp
template <typename LLR>
std::vector<uint8_t> build_soft_only_mux_state(
    const TileDispatchPlan<typename TilePrepared<LLR>::CoreLLR>& plan);
```

它只做一件事：

- `plan.soft_scheduled_rows` 中的行标成 `NeedSiso`
- 其他行标成 `Unscheduled`

### 6.5 `decode_tile_with_plan(...)`

职责：

- 把所有分支执行完并合并成一个完整的 `DecoderCoreResult`

它需要做 4 件事：

1. 为 `EarlyStopAction` 行生成 `lout`
2. 直接拷入 `HardFinish` 行缓存好的 `lout`
3. 构造 soft-only `mux_state`，在完整行域上调 Chase core
4. 把 soft core 的 full-row 输出合并回最终 `DecoderCoreResult`

建议接口：

```cpp
template <typename LLR>
chase::DecoderCoreResult<typename LinMatrixAdapter<LLR>::core_type>
decode_tile_with_plan(const TilePrepared<LLR>& prep,
                      const TileDispatchPlan<typename LinMatrixAdapter<LLR>::core_type>& plan,
                      bool normalize_extrinsic,
                      CoreFn<typename LinMatrixAdapter<LLR>::core_type> core_fn);
```

## 7. 方案三下 `process_tile_impl(...)` 的详细流程

下面给出建议的执行顺序。

### 7.1 Step 1: 保持 `prepare_tile_inputs(...)` 不变

这一段仍然负责：

- 准备 `lin_matrix`
- 准备 `lch_matrix`
- 记录 `row_local_lookup`
- 记录 `row_global_lookup`

这部分不需要理解 hybrid，只要继续提供 tile 的“完整行域输入”即可。

### 7.2 Step 2: 保持 `detect_tile_early_stop(...)` 不变

early-stop 仍然是第一道分流。

也就是说：

- 已经通过 early-stop 判据的行
  - 不再进入 hybrid pre-pass
  - 直接在 dispatch plan 里标成 `EarlyStopAction`

这样做有两个好处：

1. 兼容现有 `v1 / v2` 判据
2. 避免让 hybrid 和 early-stop 互相覆盖语义

### 7.3 Step 3: 运行 `build_tile_dispatch_plan(...)`

这一阶段结束后，plan 中每一行已经具备下面四种之一：

- `EarlyStopAction`
- `HardFinish`
- `SoftDecode`
- `Unscheduled`

注意：

- 这个时点的 `Unscheduled` 还不一定最终确定
- 真正由预算导致的 `Unscheduled` 发生在 MUX 之后

### 7.4 Step 4: 在完整行域上跑 MUX

这是方案三最容易写歪的地方。

错误做法：

- 把 soft rows 压缩成小矩阵
- 再在压缩域上跑 grouped budget / scheme C

这样会破坏当前 MUX 的分组边界语义。

正确做法：

1. 构造一个完整大小的 `mux_candidate_state`
2. `SoftDecode` 候选行映射成 `NeedSiso`
3. 其他行映射成“非 NeedSiso 占位值”
4. 复用当前 `apply_siso_budget_grouped(...)` 或 reconfig 调度
5. 将结果写回 `plan.soft_scheduled_rows / soft_unscheduled_rows`

这一层中，`mux_state` 仍然存在，但它只是 MUX 的局部适配格式，不再是全局执行状态。

### 7.5 Step 5: 构造 soft-only `mux_state`

不再把 `soft_scheduled_rows` 压缩成 compact batch，而是在完整行域上构造一个只服务 soft path 的 `mux_state`。

规则：

- `SoftDecode && scheduled_for_soft == true`
  - 标成 `NeedSiso`
- 其他行
  - 标成 `Unscheduled`

这样 Chase core 仍然接收完整的 `prep.lin_matrix / prep.lch_matrix`，但只有 `NeedSiso` 行真正执行 Chase。

这个设计下，调试信息不需要额外转换：

- `active_chase_entries` 仍然使用 full row index
- `expected_bits` 仍然按 full row index 读取
- `row_local_lookup / row_global_lookup` 不需要重建

### 7.6 Step 6: 执行 `decode_tile_with_plan(...)`

合并规则建议如下：

- `EarlyStopAction`
  - 调 `apply_row_early_stop_action(...)`
- `HardFinish`
  - 直接读 `plan.hard_finish_lout`
- `SoftDecode`
  - 从 full-row soft result 回填
- `Unscheduled`
  - `produced_rows[row] = false`

最终返回的 `DecoderCoreResult`：

- `lout.rows() == rows_to_decode`
- `produced_rows.size() == rows_to_decode`

所以 `writeback_tile(...)` 可以不做大改。

## 8. MUX 适配的关键设计

### 8.1 为什么不让 `TileDispatchPlan` 直接替代全部 MUX 输入

因为现有 MUX 工具链默认输入是一个 `state` 数组，很多逻辑都只看：

```cpp
state[i] == NeedSiso
```

例如：

- grouped budget
- priority trim
- scheme C staged schedule

这些逻辑其实并不关心“非 NeedSiso 是什么”，它们只需要：

- 哪些行是 active candidate
- 原始行号顺序和分组边界是什么

所以方案三不需要一上来就重写所有 MUX。

### 8.2 推荐的适配方法

在 `run_mux_on_soft_candidates(...)` 里临时构造：

```cpp
std::vector<uint8_t> mux_candidate_state(rows_to_decode, kMuxInactiveTag);
```

映射规则：

- `plan.rows[i].tag == SoftDecode` -> `NeedSiso`
- 其他 -> `EarlyStopped` 或其他非 `NeedSiso` 占位值

这里用 `EarlyStopped` 作为局部占位值是可接受的，因为：

- MUX 只看 `NeedSiso`
- 这个 state 不会再传给 row decoder

### 8.3 MUX 结果回写

回写规则：

- 若原本是 `SoftDecode` 且 MUX 后仍是 `NeedSiso`
  - `scheduled_for_soft = true`
- 若原本是 `SoftDecode` 且 MUX 后变成 `Unscheduled`
  - `tag = Unscheduled`
  - `scheduled_for_soft = false`

其他类型不受影响。

## 9. `decode_tile_with_plan(...)` 的后处理规则

方案三建议把后处理也显式分开。

### 9.1 归一化规则

推荐默认规则：

- 只对 `SoftDecode` 行做 `normalize_extrinsic_lout(...)`
- `EarlyStopAction` 和 `HardFinish` 不参与归一化

原因：

1. `HardFinish` 需要保持固定后验语义
2. `EarlyStopAction` 本质上也不是 Chase 真实外信息
3. 当前代码虽然对所有 `produced_rows` 一起归一化，但这本身就是结构上不够精细的地方

建议新增参数：

```cpp
bool HYBRID_NORMALIZE_SOFT_ONLY = true;
```

如果为了兼容旧行为，可以保留一个 fallback：

- `false` 时仍对全部 `produced_rows` 做统一归一化

### 9.2 `ALPHA` 规则

建议：

- `SoftDecode` 行：继续走公共 `ALPHA` 缩放
- `EarlyStopAction` 行：继续复用现有动作模式与 `ALPHA` 的关系
- `HardFinish` 行：默认也走公共 `ALPHA` 缩放，除非明确决定要让它表示“最终后验而非 extrinsic”

第一版推荐：

- `HardFinish` 与当前 tile 级硬判回退保持一致
- 也经过公共 `ALPHA` / quantize 链路

这样和现有行为更一致。

### 9.3 量化规则

所有 `produced_rows == true` 的行，最终都继续走现有量化链路：

```cpp
ExtrinsicQuantizer<LLR>::quantize(...)
```

这样 `writeback_tile(...)` 和上层 `work_llr` 语义不需要变化。

## 10. 方案三下 `Decoder_Core_impl(...)` 的建议处理

方案三不建议让 `Decoder_Core_impl(...)` 再理解复杂 dispatch。

当前推荐的做法是：

- 对完整 `prep.lin_matrix / prep.lch_matrix` 调 core
- `early_stop_row_flags = nullptr`
- `mux_state = soft_only_mux_state`

因为此时 `soft_only_mux_state` 已经表达清楚：

- `NeedSiso`：需要真正 soft decode，并且已经保住了 SISO 预算
- `Unscheduled`：当前合并流程里不由 soft path 产出结果

这样做的收益：

1. 行号始终保持 full row 语义
2. trace 和 expected bits 不需要重映射
3. 与旧路径“完整 tile + mux_state”的行为更接近

长期目标仍然可以继续收敛为：

> `Decoder_Core_impl(...)` 重新退化回一个“纯 Chase core wrapper”。

## 11. 新增统计建议

方案三上线后，统计必须改。

### 11.1 `TileProcessResult` 建议增加

```cpp
std::size_t rows_hybrid_finished = 0;
std::size_t rows_hard_candidate = 0;
std::size_t rows_hard_attempted = 0;
std::size_t rows_hard_skipped_by_siho_budget = 0;
std::size_t rows_need_siso_after_dispatch = 0;
std::size_t rows_soft_scheduled = 0;
std::size_t rows_soft_unscheduled = 0;
```

### 11.2 `TileEarlyStopCounter` 建议增加

```cpp
std::size_t row_hybrid_finished = 0;
std::size_t row_hard_candidate = 0;
std::size_t row_hard_attempted = 0;
std::size_t row_hard_skipped_by_siho_budget = 0;
std::size_t row_need_siso_after_dispatch = 0;
std::size_t row_soft_scheduled = 0;
std::size_t row_soft_unscheduled = 0;
```

### 11.3 为什么要同时保留 `before_mux` 和 `after_dispatch`

因为方案三之后会出现 3 个不同口径：

1. `row_need_siso_before_mux`
   - early-stop 之后的 soft 候选总量
2. `row_hard_attempted`
   - 受 `kSiHoActiveList[t]` 约束后，真正尝试过 hard prepass 的数量
3. `row_need_siso_after_dispatch`
   - hybrid pre-pass 之后，真正还需要参与 SISO 预算竞争的数量
4. `row_soft_scheduled`
   - MUX 之后最终真的进 Chase 的数量

这几个数必须分开，不然看不出混合方案到底收益来自哪里：

- 是 SIHO 预算太小，导致很多行根本没有尝试 hard prepass
- 还是 hard prepass 尝试了但成功率低
- 还是 hard prepass 有收益，但 SISO 预算仍然太紧

## 13. 建议的分阶段落地顺序

### 阶段 0：只引入 plan，不改行为

先新增：

- `RowDispatchTag`
- `TileDispatchPlan`

但默认把所有非 early-stop 行都标成 `SoftDecode`，暂时不做 hybrid pre-pass。

这个阶段的目标是：

- 验证 plan 结构接进当前链路后不改结果
- 验证 `decode_tile_with_plan(...)` 合并逻辑正确

### 阶段 1：接入 `HardFinish`，但先复用 E1

此阶段：

- `run_hybrid_prepass(...)` 直接调用现有 BCH 硬译码器
- 不上 `S0/S1/S3` 快速分类器

目标：

- 避免位置映射和 locator 风险
- 先把结构打通

### 阶段 2：分离归一化规则

把后处理改成：

- 只归一化 `SoftDecode`
- `HardFinish` 和 `EarlyStopAction` 独立处理

目标：

- 让混合路径的输出语义更稳定

### 阶段 3：再引入 E2 快速分类器

此阶段才开始：

- `S0/S1/S3` 分类
- `TwoCandidate`
- `Suspicious`

目标：

- 优化前端计算复杂度
- 更接近最终硬件结构

## 14. 测试建议

### 14.1 单元测试

至少覆盖：

1. `build_tile_dispatch_plan(...)`
   - early-stop 命中行应被标成 `EarlyStopAction`
2. `run_hybrid_prepass(...)`
   - BCH 成功行应被标成 `HardFinish`
   - `kSiHoActiveList[t]` 小于候选数时，超预算行不能被调用 hard decode
3. `run_mux_on_soft_candidates(...)`
   - 非 soft 行不能被错误裁剪
4. `build_soft_only_mux_state(...)`
   - 只有 scheduled soft 行应被标成 `NeedSiso`
5. `decode_tile_with_plan(...)`
   - merge 后 full result 的行数必须等于 `rows_to_decode`

### 14.2 集成测试

建议至少比较三组结果：

1. hybrid 关闭
2. hybrid 开启，但全部 hard-finish 失败
3. hybrid 开启，部分行 hard-finish 成功

验证项：

- `tile_out` 是否可写回
- BER 是否无明显异常
- `rows_need_siso_after_dispatch` 是否下降
- `rows_soft_scheduled` 是否与 `SISO_ACTIVE_LIST` 口径一致
- `rows_hard_attempted` 是否与 `kSiHoActiveList` 口径一致

### 14.3 回归测试

必须覆盖：

- `MUX_GROUP_G = 1`
- `MUX_GROUP_G > 1`
- `MUX_ENABLE_RECONFIG = false`
- `MUX_ENABLE_RECONFIG = true`
- `EARLY_STOP_CONDITION_MODE = 1`
- `EARLY_STOP_CONDITION_MODE = 2`
- `use_hard_decode = true`

最后一项尤其重要。

### 14.4 `use_hard_decode = true` 的处理

方案三建议：

- 当当前 tile 已经在 `HARD_TILE_LIST` 中要求走硬判回退时
- 直接绕过 hybrid dispatch
- 保持原有 `perform_hard_decode(...)` 路径

不要让“软硬混合前端”与“整 tile 硬判回退”同时生效。

## 15. 风险点与开放问题

### 15.1 风险 1：后处理语义变化

方案三推荐把归一化限制到 `SoftDecode` 行。

这在结构上更合理，但它与当前“所有 produced rows 一起归一化”的行为不完全等价。

因此建议：

- 先加配置开关
- 先允许兼容旧行为

### 15.2 风险 2：hard-finish 输出到底是不是 extrinsic

当前 `perform_hard_decode(...)` 构造的是：

```text
Y2 = Lpost - Lin
```

这更像一条“基于硬译码后验的增量/外信息”路径。

但如果未来你们希望 `HardFinish` 表示“最终硬判收尾”，那它的输出语义可能还要再收敛。

因此方案三第一版建议：

- 先复用 `perform_hard_decode(...)`
- 暂不重新定义 hard-finish 输出公式

### 15.3 风险 3：plan 引入后统计口径变化

以前的统计只有：

- early-stop
- unscheduled

方案三之后会变成：

- early-stop
- hard-finish
- soft-candidate
- soft-scheduled
- soft-unscheduled

扫参脚本和汇总 CSV 需要同步升级。

## 16. 结论

方案三的核心不是“多加一个状态”，而是：

> 在 tile 级显式建立一份 `RowDispatchPlan`，先做 early-stop 和 hybrid pre-pass，再把真正需要 SISO 的行交给 MUX，最后只对保住预算的 soft rows 调用 Chase，并把所有分支重新合并回完整行域结果。

这套结构的最大价值是：

1. 不再让 `mux_state` 过载
2. 不会重复硬译码
3. `writeback_tile(...)` 基本可以不动
4. 后续加入 `Suspicious`、快速分类器、更多统计都比较自然

如果要按长期可维护性排序，方案三是最值得做的一版；  
如果要按第一版实现风险排序，它也确实比方案一和方案二更高。

因此最现实的建议是：

1. 先按本文把 `TileDispatchPlan` 框架搭起来，但阶段 0 不开 hybrid
2. 框架跑通后，再把 `HardFinish` 接进去
3. 最后再考虑 `S0/S1/S3` 的快速分类器
