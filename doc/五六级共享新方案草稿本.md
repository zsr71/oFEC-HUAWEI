# 五六级共享新方案草稿本

## 1. 当前目标

本草稿用于记录基于现有五六级共享方案的新方案。当前只记录已经确认的问题背景和目标，具体实现方案、调度规则和参数暂不预设，等待后续补充。

### 1.1 统一符号

后文统一使用两套符号，分别表示“批次身份”和“服务时刻”：

- `B0`、`B1`、`B2`……表示按照原始到达顺序编号的 64-code batch；
- `t=0`、`t=1`、`t=2`……表示连续的批次/调度时刻。

在 `t=i` 时刻，新的批次 `Bi` 到达。五、六级在该时刻获得一份基础服务预算，服务对象始终是 FIFO 队列中最早尚未完成的批次，不一定是刚到达的 `Bi`。一个全 EarlyStop 批次可以通过快路径立即完成；快路径不消耗普通 HISO/SISO 服务能力，预算有剩余时，同一个 `t` 内可以继续处理下一个队首批次。

### 1.2 讨论层次

当前先讨论方案的逻辑语义，不讨论硬件时钟、端口、流水线或具体代码结构：

- `t` 是批次/调度时刻；同一个 `t` 内允许的全 EarlyStop 快路径可以连续执行，不再细分为多个硬件周期；
- group-entry、HISO、SISO 只作为逻辑上的普通解码服务能力，用于表达“每个普通 batch 每个 `t` 最多 8 个 group-entry”和普通路径的服务边界；
- FIFO、pending、EarlyStop、完成、写回、`C_t`、窗口推进和吞吐匹配属于当前方案本体；
- 硬件资源映射以及软件如何实现这些状态，等逻辑方案确定后再单独讨论。

### 1.3 可调物理参数

buffer block-row 行数不是固定为 32 的方案常量。统一定义：

- `R_buf`：可调的非负整数，表示 buffer block-row 行数；
- `R_l6=22`、`R_l5=22`：Level 6/Level 5 在联合窗口中的固定相对行数；
- `R_win=44`：联合解码窗口宽度；
- `R_mem=R_buf+44`：连续 SRAM 总行数。

`R_buf` 在一次运行中作为已配置参数保持不变，不随 `t` 动态改变；不同实验或实现可以采用不同值。增大 `R_buf` 会线性增加连续 SRAM 容量和可吸收的短时缺口，但不改变普通调度能力，也不能处理长期平均超载。

本文大量时序示例使用 `R_buf=32`，因此总容量为 76 行、最多提供 `floor(32/2)=16` 个两行回退步长。这个数值是默认示例，不是方案限制；窗口公式的上界统一写成 `R_buf`，物理总行数统一写成 `R_mem`。

## 2. 待解决的问题

在某些时刻，五级和六级共享的 64 个 code 可能出现 EarlyStop 率突然降低的情况。

这意味着：

- 通过 EarlyStop 直接完成处理的 code 数量突然减少；
- 需要进入 Hybrid、HISO 或 SISO 正常处理路径的 code 数量突然增加；
- 当前时刻的译码需求形成突发的需求 burst；
- 突发需求可能超过当前五六级共享调度资源能够及时处理的数量。

## 3. 方案目标

新方案的目标是缓解上述低 EarlyStop 率导致的瞬时需求 burst 问题。

当前目标仅表述为：

> 在五六级共享的 64-code 处理过程中，针对某些时刻突然出现的低 EarlyStop 率和译码需求突增，设计一种能够缓解该突发压力的方案。

## 4. 当前范围

目前尚未确定以下内容，后续根据具体方案说明补充：

- burst 的检测方式；
- code 或 group 的负载度量方式；
- 队首批次内部的资源分配和调度细节；
- pending 状态在连续 block-row 内存中的承载方式和跨时刻窗口指针细节；
- 窗口到达第 0 行后的满载条件、输入承接和溢出策略；
- 窗口到达第 0 行后被强制顶出的 pending code 是否需要单独的内部状态和统计计数；该标记用于边界压力观测，不计入正常吞吐量，但其保留结果仍参与统一的 Post-FEC BER；
- 已确定不使用未来批次前瞻，调度只依据当前队首及其保存的分类/完成/pending 状态；
- HISO、SISO 以及 group entry 的具体调整方式；
- 方案的正确性约束、时延约束和验证方法。

## 5. 初步方案想法

设 `B0` 在 `t=0` 时刻到达：

- `B0` 的 64 个 code 中，EarlyStop 率突然降低；
- 因此需要正常解码处理的 code 数量增加；
- 受 `t=0` 可用资源限制，`B0` 中可能有一部分 code 没有解码完成，或者没有完成对应的写回。

初步想法是：

- `B0` 在 `t=0` 未完成的 code，可以带到 `t=1` 继续处理；
- 如果 `B0` 在 `t=1` 仍未完成，可以继续在 `t=2` 以及更后面的时刻处理；逻辑上不预设一两个时刻的延续上限，但物理上最多跟随到窗口起点为 0；
- 后续时刻继续按照 `B0` 对应的解码方式处理 `B0` 中前一时刻没有获得资源、仍处于 pending 的 code；
- 每次继续处理时，只处理前一个时刻没有获得 HISO/SISO 机会、仍处于 pending 的 code，不重复处理已经完成的部分。

物理上不为每个延后 batch 单独分配一块独立内存，而是维护一块连续的 block-row 内存。按当前示例，使用半开区间表示：

```text
[0, 32)      buffer 区，共 32 个 block row
[32, 54)     Level 6 解码区，共 22 个 block row
[54, 76)     Level 5 解码区，共 22 个 block row
```

每个 `t` 有两行新输入写入内存最底部的两个 row。与此同时，原有 row 整体向上顺移两行：原 `[2,76)` 移到 `[0,74)`，原 `[0,2)` 被顶出并作为 buffer 输出，新输入占据 `[74,76)`。`t=0` 的基准解码区域为 `[32,76)`；如果当前队首在本时刻没有完成，下一时刻为了继续跟随同一 batch，解码窗口向上移动两行，例如变为 `[30,74)`。如果当前时刻恰好完成一个 batch，下一队首 batch 经过同一次物理上推后进入当前解码位置，因此下一时刻窗口保持不动；只有一个时刻完成两个或更多 batch、完成速率超过每时刻一个 batch 的输入速率时，窗口才会逐步向 `[32,76)` 恢复。窗口起点最低为 0，Level 6 始终占窗口内前 22 行，Level 5 始终占后 22 行。

该想法的核心是让突发时刻未完成的 code 具备跨时刻延续处理的能力，而不是只能在原始时刻一次性完成或被跳过。

当窗口已经到达 `[0,44)` 后，方案改为吞吐优先：下一时刻仍照常输出顶部两行、上推全部 row 并写入底部两行。即使被顶出的 `B0` 内容仍有 pending，也不再等待或另存；这些 pending 被强制放弃，窗口继续保持 `[0,44)`，服务对象转为随上推进入该窗口的 `B1`。

被强制顶出的 pending code 沿用原五六级共享方案中“未分配到解码资源”的数据路径语义：没有产生新解码结果，不生成新的 extrinsic，不执行外信息写回，原有外信息保持不变。它与普通未分配 code 的区别只在后续控制上：普通 pending 下一时刻还可以重新调度，边界顶出的 pending 永久退出调度。

## 6. 需要满足的约束

上述延续处理需要同时保证总体吞吐量稳定。这里的吞吐量约束不是只看解码器内部每次处理了多少 code，而是要和整个流水线的固定产出节拍匹配：

- 前四级按照固定吞吐量持续输出待五、六级处理的 64-code batch；
- 五、六级需要按照匹配的吞吐量输出已经完成解码的 64-code batch；
- 中间引入跨时刻延续后，每个 `t` 都有新的 `Bi` 到达，但五、六级可能仍在处理更早的队首 `Bh`；
- 如果队首 `Bh` 持续占用多个时刻，后续 `Bi` 会按照 FIFO 顺序形成积压；
- 每个 `t` 仍有两行新输入进入连续内存；新输入接收优先于队首是否在本 `t` 完成，但新 batch 只能追加到 FIFO 尾部；
- 每个 `t` 边界上所有既有 row 固定向上顺移两行，顶部两行输出，底部写入两行新输入；窗口位置由这次固定物理上推和本时刻内部完成的 batch 数共同决定；
- 本时刻完成 0 个 batch 时窗口向上回退两行，完成 1 个 batch 时下一时刻窗口保持不动，完成超过 1 个 batch 时窗口才按超出的完成数逐步向基准位置恢复；
- `C_t` 只表示五、六级在本 `t` 内部正常完成并退休的 batch 数，不表示对外输出 batch 数；无论 `C_t` 是多少，顶部物理输出仍保持每个 `t` 两行的固定节拍；
- 当同一 `t` 内完成多个 batch 时，额外完成的 batch 保留在连续内存中，等待后续物理上推到顶部再输出；本方案的窗口追赶只表示解码窗口向基准位置恢复，不表示对外接口在一个 `t` 内输出多个 batch；
- 窗口起点的合法范围为 `[0, R_buf]`，达到 `0` 后不再向 buffer 方向回退；Level 6 和 Level 5 始终分别占据窗口内前 22 行和后 22 行；
- `S_t=0` 是吞吐优先边界：顶部内容即使仍有 pending 也按固定节拍输出，不阻塞上推和底部新输入；后续 batch 因此继续进入 `[0,44)`；
- 系统需要利用全 EarlyStop 等低负载批次的快路径，在同一个 `t` 内连续完成多个队首批次，从而降低积压并恢复批次节拍。

理论上的延续时长可以持续增加，但实际能否继续延后以及每个时刻允许处理多少遗留 code，都必须受到上述整体吞吐量约束：

> 后续时刻在继续处理前一时刻遗留 code 的同时，不能持续挤占新时刻的正常处理资源，导致系统整体吞吐量下降或积压不断扩大。

## 7. 可能需要的中间机制

当前方案需要一个按照 `B0 -> B1 -> B2 -> ...` 记录逻辑 batch 顺序的 FIFO，同时由一块连续 block-row 内存承载这些 batch 的输入、history/prior 和 per-code 调度状态。物理上不要求每个 batch 使用独立 RAM；队首 batch 的 44-row 解码窗口通过窗口起点指针映射到连续内存。

除 FIFO 缓冲本身外，还需要配套：

- 全 EarlyStop 批次的快速完成路径；
- 同一个 `t` 内从已完成 `Bh` 连续切换到下一队首批次的机制；
- 保存 pending code 的分类、调度、参数和 row 映射；输入/history 数据本体只保存在唯一连续 SRAM 中；
- 每个 `t` 将既有 row 整体上推两行、输出顶部两行并在底部写入两行新输入的移位机制；
- 窗口回退到 `[0, 44)` 附近后的边界处理；
- 表达每个普通 batch 每个 `t` 最多 8 个 group-entry 的抽象服务预算；
- 保证批次严格按序完成和提交的状态控制。

具体的吞吐量窗口参数、抽象服务能力、per-code 调度状态的最小保存内容、顶部输出与 pending 的边界关系以及超出有限 block-row 缓冲后的处理方式，待后续方案进一步明确。窗口由固定的每时刻两行物理上推和 batch 完成数共同更新；批次服务顺序和 pending 的跨时刻语义已经固定，不再作为独立的优先级选项。

## 8. 吞吐量约束的基本判断

后续设计需要区分瞬时 burst 和长期超载，并把有限 buffer 容量作为正式约束：

- 如果某个时刻的需求突然升高，但一段时间内的平均需求不超过五、六级可提供的平均服务能力，缓冲区或其他排队机制理论上可以吸收 burst，并在后续空闲时刻逐步消化；
- 如果需求长期高于抽象的平均服务能力，积压会持续增长，单靠缓冲区不能解决问题，只能在延迟、丢弃、降级处理、输入限流或提高服务能力之间做取舍。这里暂不讨论服务能力由什么硬件实现。

因此，“总体吞吐量稳定”需要进一步落成可测量的有限窗口约束，例如：

- 前四级的码字到达节拍；
- 五、六级每个时刻可提供的抽象 code/group-entry 服务量；
- 允许的最大积压量；
- 允许的最大延迟或最大延续时长；
- 当前示例中 32 个 buffer block row、16 个两行回退步长与 batch 积压量之间的映射；
- FIFO 队首批次在一个 `t` 内能够获得的服务量。

在这些量明确之前，缓冲区大小和调度策略都无法合理确定。

## 9. 低负载时刻的追赶机制

当前方案设想不仅允许在低 EarlyStop 率时把未完成 code 延后，还需要利用后续的低负载时刻把积压追回来。

设队首等待批次 `B1` 在服务时刻 `t=3` 被检查为 64 个 code 全部命中 EarlyStop：

- `B1` 没有需要进入正常 HISO/SISO 解码的 code；
- `B1` 通过快路径直接完成，外信息保持原值，不执行新的外信息写回；
- `B1` 的快路径不占用 `t=3` 的普通 HISO/SISO 服务能力；
- `B1` 离开队首后，`t=3` 的剩余服务能力立即继续处理下一个队首批次 `B2`；
- `B1` 完成后队首转为 `B2`；每个时刻固定的两行物理上推会抵消“正常完成一个 batch”带来的两行服务推进，因此一个时刻只完成一个 batch 时窗口保持不动，只有同一时刻额外完成后续 batch 才会把窗口逐步推回基准位置；
- 通过这种方式，让前面因需求 burst 延后的处理逐步赶回，而不是只允许积压持续向后传递。

该机制体现的是一种动态服务节拍：

```text
EarlyStop 率低  -> 当前需求 burst，允许部分 code 延后
EarlyStop 率高  -> 当前正常解码负载降低，利用空闲机会追赶遗留 code
```

当前已经确定全 EarlyStop 批次不运行普通 HISO/SISO，也不产生或写回新的外信息。是否还存在其他必须执行的 EarlyStop 控制动作，留在 P3 中进一步明确。

## 10. 当前整体方案总览

当前想法可以整理成以下闭环流程：

```text
每个 t 时刻，前四级产生新的批次 Bi 并按序入队
                    |
                    v
        五、六级选择最早未完成的队首批次 Bh
                    |
          +---------+---------+
          |                   |
          v                   v
 EarlyStop 率低、需求突发   EarlyStop 率高、需求较低
          |                   |
          v                   v
 当前资源处理 Bh 能完成的部分  Bh 少用或不用普通 HISO/SISO
          |                   |
          v                   v
 Bh 未完成 code 继续留在队首  Bh 完成后继续处理下一个队首
          |                   |
          +---------+---------+
                    |
                    v
 已完成 code 不再调度；正常路径结果只写一次，pending code 继续保留到后续时刻
                    |
                    v
 在总体吞吐量约束下持续延后、持续追赶，直到遗留被消化
```

其中：

- `Bi` 的延后不固定限制到后面一两个时刻，可以继续跨更多服务时刻；
- 物理延后通过连续内存的窗口起点移动实现：每个时刻内存固定向上推两行；若本时刻没有 batch 完成，窗口随同一队首向上回退两行；若完成一个 batch，下一队首被推到同一窗口位置；若完成多个 batch，窗口才按额外完成的 batch 数向基准位置恢复；
- 延后的对象只保留尚未获得资源、仍处于 pending 的 code；
- 已经完成的 code 不能重复执行；正常路径结果不能重复写回，全 EarlyStop code 不产生新的外信息写回；
- 全部 EarlyStop 的时刻是当前已经明确的一种追赶机会；
- 前四级输入节拍和五、六级输出节拍仍需要匹配；
- 缓冲和调度只能吸收有限 burst，不能消除长期平均需求超过抽象服务能力的问题；可承受的缺口和积压必须受有限 buffer 容量约束。
- `R_buf` 个 buffer block row 最多提供 `floor(R_buf/2)` 次完整两行回退；窗口起点触及 0 后保持 `[0,44)`，不能继续假设还有无限延后空间。默认 `R_buf=32` 时该值为 16。

## 11. 对方案的总体判断

这个思路在系统层面是合理的。它把 EarlyStop 波动造成的瞬时译码峰值转换成可跨时刻消化的积压：高负载时延后，低负载时追赶。长期平均译码需求低于五、六级的平均服务能力，是系统可能稳定运行的必要粗略条件；最终仍需满足基于 `C_t` 和有限 buffer 容量的缺口、最大积压和最大恢复范围约束。

这个方案的主要价值是：

- 不要求硬件资源按照最坏时刻的瞬时峰值配置；
- 可以利用 EarlyStop 率随时间变化产生的空闲能力；
- 能把偶发 burst 对单个时刻的冲击摊到后续时刻；
- 明确区分已经完成的内容和仍需继续处理的内容，避免重复解码与重复写入。

**当前逻辑状态：**正常流阶段的方案语义已经闭合。batch/FIFO 顺序、pending 延后、原五六级共享 group/mux 调度、全 EarlyStop 同一 `t` 快路径、`C_t` 内部完成计数、固定两行物理输出、buffer 回退/恢复、`S_t=0` 强制顶出、Level 5/Level 6 code 粒度联合完成、无未来 batch 前瞻以及无失败重试都已经确定。帧尾 drain、reset/flush 和具体状态字段暂不纳入本阶段讨论。

但它不是只增加一个普通 FIFO 就能完整定义。FIFO 只负责保存逻辑 batch 顺序和 per-code 状态；连续 block-row 内存和窗口指针负责唯一保存跨时刻输入/history 数据。一个 code 被延后以后，仍然需要遵循共享 SRAM 服务时读取、code 粒度完成、快路径转交、完成与提交区分、窗口边界和有限窗口吞吐量规则。当前阶段只讨论这些理论语义，不考虑现有代码结构如何承载；代码适配和实现改造留到方案定型以后。

## 12. 遗留问题清单

下面的问题按建议解决顺序排列。后续逐项形成结论，并把结论补回对应条目。

### P0：必须先确定的系统语义

P0 主要确定方案的基本语义，不展开 per-code 字段和连续内存的具体实现；当前已选定的 block-row 物理布局在 P1-9/P1-10 中统一定义，P0 这里只说明它与时刻、pending 和窗口移动的关系。为避免概念混用，先区分三个动作：

```text
解码完成：某个 code 已经获得最终解码结果
内部写入：结果已经写入该 code 对应的内部 LLR/history 状态
对外提交：该 code 或所属批次已经从五、六级接口交给下游
```

三个动作可以在同一个时刻发生，也可以被方案拆开。P0 的目的就是先确定是否允许拆开以及拆开后的规则。

#### P0-1：一个“时刻”具体代表什么？吞吐量用什么单位描述？

**当前已确定的方案语义**

- 方案中的 `t=0`、`t=1`、`t=2` 是批次时刻；
- 批次时刻和五、六级调度时刻视为同一个时刻；
- 每个时刻对应一个新的 64-code batch 到达，同时五、六级获得一份基础调度预算；当存在历史遗留时，预算优先服务最早的未完成批次，不一定服务本时刻刚到达的新批次；快路径完成队首批次后，预算有剩余时可以在同一 `t` 内继续服务后续队首批次；
- 物理内存每个 `t` 将既有 block-row 整体向上顺移两行，原 `[0,2)` 作为 buffer 输出，原 `[2,R_mem)` 移到 `[0,R_mem-2)`，新输入写入 `[R_mem-2,R_mem)`；当前联合解码窗口固定为 44 个 block row，正常基准布局为 buffer `[0,R_buf)`、Level 6 `[R_buf,R_buf+22)`、Level 5 `[R_buf+22,R_mem)`；窗口起点由固定上推和本时刻内部完成的 batch 数共同更新，最低到 0；这些物理动作都不改变 `C_t` 的内部完成计量；
- 吞吐量按每个时刻到达/完成多少个 64-code batch 衡量；
- 主要观察批次的输入/输出节拍，不用 group-entry 数量、HISO 数量或 SISO 数量定义总体吞吐量；
- group-entry/HISO/SISO 只属于批次内部的资源使用和调度约束，不改变吞吐量的计量单位。

**问题背景**

方案里使用了 `t=0`、`t=1`、`t=2`。如果“一个时刻”的物理含义不明确，就无法定义一次 burst、延后一个时刻、追回一个时刻分别意味着多少工作量。

需要区分：

- **批次时刻**：前四级每产生一批新的五六级输入，就进入下一个时刻；
- **调度时刻**：五六级每获得一次完整资源调度机会，就进入下一个时刻；
- **硬件周期**：真实电路的单个 clock cycle；一个批次时刻可能包含多个硬件周期；
- **滑动窗口时刻**：每移动一次窗口视为一个时刻。

它们可能一一对应，也可能不是同一个尺度。当前方案讨论 burst 时，更关心的是“每来一批新需求，五六级同时获得多少服务机会”，但这一点需要明确确认。

吞吐量也可以使用不同单位：

- 每时刻到达/完成多少个 `64-code batch`；
- 每时刻到达/完成多少个 code；
- 每时刻使用多少个 group entry；
- 每时刻使用多少个 HISO 和 SISO 解码机会；
- 每个硬件周期输出多少 bit。

这些量不能完全互换。例如，同样是 16 个待解 code，集中在少数组和分散在很多组时，需要的 group entry 可能不同。

**会影响的后续问题**

- burst 和追赶速度如何计算；
- 缓冲区深度使用“批次”还是“code”表示；
- 什么叫落后一个时刻、赶回一个时刻；
- 稳定性条件的到达率和服务率采用什么单位。

**状态：已解决**

批次内部怎样才算完成，以及多个时刻的批次怎样提交，分别留在 P0-4 和 P0-2 中讨论，不属于 P0-1 的吞吐量单位定义。

#### P0-2：不同原始时刻的批次是否必须按顺序对外输出？

**当前已确定的方案语义**

新方案采用严格的批次顺序。这里不仅要求对外按序提交，而且正常解码服务本身也按原始到达顺序进行：

- 每个 `t` 时刻都有新的 `Bi` 到达并进入 FIFO 等待队列；
- 五、六级始终处理最早到达且尚未完成的队首批次；
- 如果队首批次在当前 `t` 没有完成，下一时刻继续处理同一个批次中尚未完成的 code；
- 后续到达的新批次不能越过未完成的旧批次先行解码或先行提交；
- 一个批次完成以后，服务机会转向等待队列中的下一批次；
- 一个批次内部允许部分 code 已完成、其余 code 继续遗留；已经完成的 code 后续不再重复解码；
- 如果队首批次通过全 EarlyStop 快路径完成，则同一 `t` 的处理权立即转向下一个队首批次；这不是普通 HISO/SISO/group-entry 资源转交，因此一个 `t` 可以连续处理多个全 EarlyStop batch。
- 边界例外：当窗口起点已经为 0，顶部属于队首 `Bh` 的内容即使仍有 pending，也随固定两行输出被强制顶出；这些 pending 不再阻塞后续 batch，窗口继续保持 `[0,44)` 并转向已经上推进来的 `Bnext`。

因此，该方案正常区间不是“不同批次乱序执行、最后重新排序”，而是“严格 FIFO 的批次延续服务”；但在 `S_t=0` 的物理容量边界处采用吞吐优先的强制退休，不再要求队首 64 个 code 全部完成后才能转向下一 batch。这是容量耗尽时的受控例外，不是后续 batch 主动越过队首执行。

示例中，批次 `B0` 在 `t=0` 到达，批次 `B1` 在 `t=1` 到达，之后的批次依次为 `B2`、`B3`：

```text
服务时刻 t=0：处理 B0，B0 未完成
服务时刻 t=1：继续处理 B0 尚未完成的 code；B1 到达并等待
服务时刻 t=2：继续处理 B0；若本时刻完成 B0，则 B0 离开队首
服务时刻 t=3：开始处理等待最久的 B1
服务时刻 t=3：若 B1 全部 EarlyStop，B1 快速完成，并在 t=3 剩余能力中继续处理 B2
```

如果 `B1` 的 64 个 code 全部 EarlyStop，则：

- `B1` 不进入正常 HISO/SISO 解码；
- `B1` 的外信息保持原值；
- `B1` 不执行新的外信息写回；
- `B1` 可以直接标记为完成并离开待处理队列。

这里“外信息保持原值”表示不生成、也不覆盖新的 extrinsic；该批次在逻辑上完成，并按 FIFO 顺序完成必要的对外提交。

**问题背景**

最初需要在严格按序和允许乱序之间选择。当前已经选择正常区间严格 FIFO：旧批次未完成时，新批次不能越过它先行处理；只有窗口到达 `S_t=0` 后，旧批次才会因吞吐优先边界被强制退休。

该选择避免了乱序结果和下游重排问题，但会产生队首阻塞：一个 burst 批次连续占用多个服务时刻时，后续每个时刻仍然有新批次到达，因此等待队列会增长。

**关于“全 EarlyStop 时赶回节拍”的关键判断**

如果一个全 EarlyStop 批次虽然不运行 HISO/SISO，却仍独占一个完整服务时刻，那么它只能抵消该时刻新到达的一个批次：

```text
本时刻新到达 1 个 batch
本时刻队首完成 1 个全 EarlyStop batch
队列净变化 = 0
```

这种情况下可以阻止积压继续增加，但不能减少 burst 已经造成的历史积压，也就不能真正把落后的批次节拍赶回来。

当前已经确定采用“时刻内连续取队首”：全 EarlyStop 的 `B1` 快速退休后，不占用 `t=3` 普通 HISO/SISO 能力，`t=3` 的剩余能力立即处理 `B2`。因此低负载时刻允许完成多个批次，才能让积压真正下降并追回节拍。

**会影响的后续问题**

- 队首阻塞造成的最大积压和等待时间；
- 同一 `t` 内连续全 EarlyStop batch 的数量是否受理论上限约束（已确定：不设上限；直到 FIFO 为空或遇到第一个普通 batch）；
- 连续完成多个批次时，批次完成节拍和对外提交节拍如何同步；
- `B1` 快速完成后，`B2` 是否可以在同一 `t` 完成部分或全部 code。

**状态：已解决（批次服务顺序）**

已经确定正常区间采用严格 FIFO、旧批次连续处理、后续批次排队；全 EarlyStop 批次通过快路径完成且不进行新的外信息写回；快路径后的处理权转向下一个队首批次。当 `S_t=0` 时采用吞吐优先的强制退休：剩余 pending 随顶部输出离开，不再阻塞 `Bnext`。一个 `t` 能够正常完成多个批次；连续全 EarlyStop batch 的数量不设理论上限，只要当前队首是全 EarlyStop，就立即完成并检查下一个队首，持续到 FIFO 为空或遇到第一个需要普通 HISO/SISO 解码的 batch。具体实现承载问题后置，不为理论方案增加 batch 个数上限；强制退休必须与正常完成分开统计。

#### P0-3：方案所说的“延后”到底延后哪个动作？

**当前已确定的方案语义**

这里的“当前时刻没有处理完”只指资源调度没有覆盖到该 code，不指解码器内部已经开始执行但没有完成。

一个 64-code batch 在一个 `t` 时刻的处理过程是：

1. 对该 batch 的 64 个 code 完成 EarlyStop 和正常调度判断；
2. 本次调度最多使用 8 个 group-entry 机会；
3. 每个 group-entry 绑定一个选中的 4-code group，并最多为该 group 分配一个 HISO code 和一个 SISO code；
4. 获得 HISO 或 SISO 资源的 code，在本次服务机会中执行对应的完整解码；
5. 没有被分配到 HISO 或 SISO 的普通 code，在本次调度结束时保持未完成状态；
6. 这些未分配 code 不进入解码中途暂停状态，而是在下一个 `t` 对同一个队首 batch 重新参与资源分配；重新调度使用连续内存中新的 44-row 窗口映射，但只把 pending code 送入下一轮 8-entry mux。

因此，新方案中的“延后”准确含义是：

```text
本时刻没有获得 HISO/SISO 调度资源
    -> 本时刻不执行该 code 的正常解码
    -> 保留为当前 batch 的未完成 code
    -> 下一时刻继续参与该 batch 的调度
```

它不包含以下情况：

- 已经开始 HISO/SISO 后暂停到下一时刻；
- HISO/SISO 已经完成但因为写入带宽不足而单独排队；
- 已经完成并写入后，再等待另一个独立的批次输出队列。

在这个语义下，当前时刻的调度结果在调度结束后即可知道：哪些 code 已经获得 HISO/SISO，哪些 code 仍然未分配。只有未分配的 code 才进入下一时刻的遗留集合。

**会影响的后续问题**

- 8 个 group-entry 机会在下一个 `t` 如何继续分配给同一个 batch 的遗留 code；
- 一个 4-code group 已经部分完成后，下一时刻如何只对剩余 code 重新调度；
- 一个 batch 部分 code 已完成、部分 code 未完成时，批次提交条件如何定义；
- 未完成 code 需要保存完整输入，还是只保存重新调度所需的状态。

**状态：已解决（延后位置）**

延后发生在“本时刻 8 个 group-entry 调度完成之后、HISO/SISO 正常解码开始之前”。未获得资源的 code 延续到下一时刻重新调度；已获得资源的 code 在本次服务机会内完成，不存在解码中途暂停或独立写入队列。

#### P0-4：“只处理、只写入前面没做过的东西”以什么粒度判断？

**当前已确定的方案语义**

新方案采用 code 粒度记录完成状态。每个 code 是不可再拆分的最小调度和完成单位，不存在一个 code 内部只完成部分字段或部分 bit 的状态。

以 `B0` 为例：

```text
t=0：
    对 B0 的 64 个 code 进行调度
    获得 HISO/SISO 机会的 code 在 t=0 完成
    未获得 HISO/SISO 机会的 code 标记为 pending

t=1：
    仍然处理队首 B0
    只把 B0 中 pending 的 code 放回调度候选集合
    t=0 已完成的 code 不再参与 EarlyStop/调度/解码/写入

t=2 及以后：
    如果 B0 仍有 pending code，继续只调度剩余 pending code
    直到 B0 的 64 个 code 全部正常完成，或 B0 在 S_t=0 边界被强制退休
```

因此，一个 64-code batch 允许处于部分完成状态：

- 已完成 code：永久退出该 batch 后续时刻的调度；
- pending code：表示前一时刻没有获得 HISO/SISO 解码机会，下一时刻继续参与调度；
- batch 完成：64 个 code 均不再处于 pending 状态。

EarlyStop 命中的 code 也不属于后续待解集合；它按方案定义的 EarlyStop 快路径完成，不再在后续时刻重复处理。

**会影响的后续问题**

- 每个 batch 至少需要一份 64-code 完成/pending 状态；
- 遗留需求量只统计 pending code；
- 一个 4-code group 被部分完成后，下一时刻只统计和调度其中的 pending code；
- 已完成 code 必须保证不重复进入 EarlyStop、HISO、SISO 或写入路径。

**转移到后续处理的边界问题**

如果某个 code 已经获得 HISO/SISO 机会，但解码执行最终没有产生有效结果，需要另行确定它算“已完成”还是重新回到 pending。这个问题属于失败/重试策略，不影响 P0-4 已确定的 code 粒度语义，后续放到边界处理问题中解决。

**状态：已解决（完成粒度）**

每个 code 是最小完成单位。跨时刻继续处理 `B0` 时，只重新调度前一时刻没有获得 HISO/SISO 机会的 pending code；已经完成或通过 EarlyStop 快路径完成的 code 永久退出后续调度。`S_t=0` 时随顶部输出被强制顶出的 pending code 也永久退出后续调度，但其状态必须标记为 `forced-evicted`，不能伪装成正常解码完成或 EarlyStop 完成。

#### P0-5：延后 code 后续继续处理时，使用哪一份 SRAM 数据？

**当前已确定的方案语义：共享连续物理行（语义 B）**

Level 5/Level 6 的输入、prior 和 history 在物理上始终只有一份连续 SRAM 数据。FIFO batch 到达时不保存独立的完整 tile 快照；batch 只保存 FIFO 顺序、row 映射、任务参数和 64-code 分类/调度状态。对 `B0 -> B1` 而言：

```text
t=0：B0 成为队首，从当前 SRAM 读取 Level 5/Level 6；未获资源的 code 标记 pending
t=1：B0 仍是队首，继续从当前 SRAM 读取 B0 对应物理行；B1 只进入 FIFO，不开始五六级服务
t=2：B0 完成普通解码及 extrinsic/history 写回并退休
t=2：B1 才成为队首，从 B0 写回后的同一份 SRAM 读取自己的 Level 5/Level 6 区域
```

该语义依赖以下方案前提：

1. **单份数据本体**：相邻 batch 的重叠 Level 5/Level 6 行是同一份物理 SRAM 数据，不创建 B0/B1 两份 snapshot；
2. **正常区间严格 FIFO**：`B1`、`B2` 在 `B0` 退休前不能读取或处理自己的五六级服务窗口；
3. **写回先于下一队首读取**：B0 的所有必要写回完成后，B1 才读取更新后的共享 SRAM；
4. **逻辑状态保持**：EarlyStop/Hybrid 分类、资源资格、AlreadyDecoded/pending、任务参数和 code/group 身份按 batch 保存，不因等待重新定义。

在这组前提下，延后改变的是资源获得时刻和 FIFO 队首，不是为 batch 保存一份独立输入。pending code 下一次服务时从当前共享 SRAM 读取，但仍沿用原有分类和资源资格；AlreadyDecoded code 不再调度或重复写回。

**不采用的语义**

本方案不采用“每个 batch 到达时冻结一份独立 `tile_in5/tile_in6`，以后使用旧 snapshot 解码”的模式。也不因 SRAM 内容更新而重新进行 EarlyStop/Hybrid 分类；更新的是共享数据，分类和调度身份仍按 batch 保持。

**会影响的后续问题**

- 缓冲区不保存每个 batch 的完整 tile 数据副本，只保存逻辑状态和 row 映射；
- 必须保证 B0 写回完成后 B1 才从同一 SRAM 读取；
- 需要保持 batch 的任务参数、分类、code/group 身份和地址映射直到退休；
- 软件仿真必须避免混用“输入 snapshot”与“共享 SRAM 写回”两种语义。

**状态：已解决（共享 SRAM 语义）**

pending batch 不持有独立的完整 tile 快照。当前队首每次服务时从唯一连续 SRAM 读取；B0 完成全部写回并退休后，B1 才读取 B0 更新后的共享行。分类、资源资格、AlreadyDecoded/pending、参数和 row 映射按 batch 保持。`forced-evicted` code 永久退出，不再补解。

#### P0-6：延后结果晚到以后，对后续解码过程产生什么影响？

**问题背景**

在正常区间的严格 FIFO 语义下，`B0` 没有完成以前，`B1`、`B2` 只能等待，不能先行开始解码。因此不会出现“`B0` 晚到结果时，后续批次已经使用了不完整的 `B0` 结果并需要回放”的情况。`S_t=0` 时属于明确的吞吐优先例外：`B0` 剩余 pending 被强制顶出并停止产生晚到结果，随后 `B1` 才开始服务，所以同样不允许对已顶出的 `B0` 再做回放或补解。

确定的因果关系是：

- `B0` 可以跨多个 `t` 延续处理，直到正常完成或触及 `S_t=0` 的强制顶出边界；
- 正常情况下只有 `B0` 完成后队列才转向 `B1`；边界情况下 `B0` 的剩余 pending 被强制退休后转向 `B1`；
- `B1` 的解码使用的是 `B0` 已经完成并提交到下一阶段的状态；
- 同一个 `t` 内从 `B1` 转向 `B2` 时，也必须先完成 `B1` 的必要提交，再开始 `B2`；
- 不需要允许后续批次先行执行后，再等待或回放旧批次结果。

因此，新方案将“晚到结果对后续任务的影响”转化为 FIFO 队首等待，而不是乱序执行后的回放问题。

**会影响的后续问题**

- FIFO 队首等待造成的积压和延迟；
- 一个批次完成后，同一 `t` 内能否完成提交并转向下一个批次；
- 批次内部写入和对外提交是否必须在转向下一批次前完成；
- `B0` 的延迟是否会超过允许的最大批次等待时间。

**状态：已解决（因果顺序）**

后续批次不越过旧批次执行，不需要对已经开始的后续批次做回放或重算。剩余的写入/提交动作和最大等待时间，分别留给 P0-3、P0-7 及后续问题。

#### P0-7：“总体吞吐量稳定”具体要求平均速率稳定，还是逐时刻输出节拍固定？

**当前已确定的方案语义**

新方案采用**有限 buffer 约束下的吞吐匹配**，不要求每个 `t` 都严格完成一个 64-code batch，也不只用没有边界的长期平均值作为唯一约束。这里不再额外定义一个独立的统计窗口长度；可承受的缺口直接由连续 block-row buffer 的容量和窗口起点 `S_t` 的边界定义。

在 buffer 能够承受的回退范围内：

- 前四级到达的 64-code batch 数量和五、六级内部正常完成的 batch 数量 `C_t` 需要在有限窗口内保持匹配；
- 允许某个短时窗口内因为 burst 出现暂时的完成缺口；
- 后续全 EarlyStop 或其他低负载时刻可以在同一 `t` 内连续完成多个队首 batch，弥补之前的缺口；
- buffer 为可调的 `R_buf` 个 block row，按每次两行回退最多允许 `floor(R_buf/2)` 个完整回退步长；窗口到达 `[0,44)` 后不再后退；
- 因此允许的短期完成缺口和最长正常等待范围首先由 `floor(R_buf/2)` 个完整回退步长决定，而不是由另一个独立的 `W` 参数决定。默认 `R_buf=32` 时才等于 16。

**问题背景**

方案已经明确前四级持续产生新需求，五六级需要提供匹配的输出。理论上可以有三种速率匹配强度：

- **长期平均匹配**：允许短时间少输出或无输出，只要在后续追赶后，较长时间平均输出率等于输入率；
- **有限 buffer 匹配**：允许短期波动，但要求缺口不能把窗口起点推过 `S_t=0`；内部正常完成量 `C_t` 决定窗口恢复，顶部两行物理输出仍保持固定节拍，不作为 `C_t` 的替代计数；
- **逐时刻固定节拍**：每个时刻都必须对外提交一个完整批次，不能出现空拍。

如果要求逐时刻固定输出，那么初始必须已经有一定缓冲储备，否则第一次 burst 就可能没有完整批次可交付。当前方案不采用这种逐时刻固定节拍。

有限 buffer 匹配允许在 burst 时产生短期内部完成缺口，在低负载时刻通过较大的 `C_t` 一次追赶更多工作；buffer 本身同时提供最大回退深度和正常等待边界。超过 `S_t=0` 后不再继续等待，而是进入已经确定的强制顶出路径。

这里明确区分两个动作：

- **内部完成速率**：五六级每个 `t` 正常完成并退休多少个 batch，由 `C_t` 表示；
- **物理输出节拍**：每个 `t` 固定输出顶部两行，保持原五六级共享方案的两行节拍。

二者不要求相等。`C_t>1` 时，只表示内部解码窗口恢复得更快；额外完成的 batch 仍留在连续内存中，等待后续物理上推到顶部再输出。有限窗口吞吐量匹配以 `C_t` 作为定义和分析量，不要求运行时额外观察或反馈 `C_t`；强制顶出的两行不计入正常吞吐量，但其保留结果仍参与统一的 Post-FEC BER，不再设置“有效完成区域 BER”。

**会影响的后续问题**

- 是否需要启动阶段预填充；
- 已完成 batch 在连续内存中等待物理输出的空间如何表示；
- 全 EarlyStop 时刻怎样定义“赶回来”；
- 可调 `R_buf` 对应的最大回退缺口和最大正常恢复范围如何表达；
- 稳定性评价如何同时使用窗口内完成量、积压峰值和延迟。

**已确定与待确定**

1. 已确定：允许五六级在部分 `t` 暂时不能提交完整的新 batch；
2. 已确定：后续空闲时刻允许一个 `t` 完成或提交多个连续队首批次，例如依次完成 `B1`、`B2`；
3. 已确定：总体约束采用有限 buffer 匹配，而不是逐时刻严格一进一出；
4. 待确定：`R_buf` 个 buffer block row 与具体 batch 积压量、code 等待年龄之间的映射，以及基于该映射的评价阈值。

**状态：已解决（有限 buffer 匹配原则）**

匹配类型已经确定为由有限 buffer 容量定义的有限缺口匹配；不再单独引入窗口长度参数。具体 batch 积压、code 等待年龄和恢复评价阈值由可调 `R_buf`、两行推进粒度和 `S_t=0` 边界推导。

### P1：缓冲与调度机制

8. **遗留队列保存什么？**
   **已确认的状态语义：**队列按 batch 的原始到达顺序 FIFO；batch 内部按 code 记录完成/pending；pending code 保持原始任务参数、分类和地址映射，但服务输入从唯一连续 SRAM 读取。一次 batch 的当前调度完成规定的 8 次 group-entry 选择后，会经过 mux 为每个 code 形成一份完整的调度结果。

   这份 per-code 调度结果不是单独的路径分类，而是至少同时包含：

   - EarlyStop/Hybrid 等路径或分类结果；
   - HISO/SISO 资源资格和资源类型；
   - 本次 8-entry 调度中是否实际获得 HISO 或 SISO 资源；
   - 获得资源时对应的 group-entry、core 或其他资源映射；
   - 没有获得资源时的 `Unscheduled`/pending 结果；
   - 本次执行是否已经产生结果，以及相应的执行状态。

   获得 HISO/SISO 资源的 code 进入本次完整解码路径；没有获得资源的 code 由 mux 后结果直接标记为 pending。下一时刻只把这些 pending code 重新送入下一轮 8-entry 调度，已经完成的 code 不再重新进入调度。这个结论与现有实现中的 per-code dispatch entry 和 schedule sample 结构相互印证，但新方案只继承其状态语义，不把现有字段名或当前 temporal 实现方式视为最终硬件结构约束。

   **仍需具体确定的保存范围：**

   - 一个队列项是否至少包含 batch ID、原始到达时刻、Level、local/global row、group 和 code 索引；
   - 64 个 code 的 mux 调度结果、完成/pending 状态是用位图保存，还是用 code 项列表保存；
   - per-code 调度结果中的哪些字段是功能必需状态，哪些字段只用于调试、统计或 exactly-once 验证；
   - 共享 SRAM 的 row 映射、信道数据引用、地址和参数如何组织，才能在服务时重建当前 `Lin/Lch/history`；
   - alpha、beta、信道参数、量化参数等任务参数是否需要随 batch 保存；
   - 目标写回地址、history 地址和对外提交信息是否需要单独保存；
   - 由于采用完整 64-code batch 缓冲，已完成 code 的固定槽位和必要调度结果在 batch 回收前保留到什么程度；哪些数据可以只做逻辑无效标记；
   - 下一轮重新调度后，是覆盖该 code 的当前资源分配记录，还是额外保留历轮结果用于观测和 exactly-once 检查；
   - 执行完成、内部写回完成和对外提交完成是否需要独立状态位，还是可以由一个 batch 状态机统一表示。

   **边界情况：**如果一个 batch 在 `t=0` 完成 8 次 group-entry 调度后，结果为：48 个 code 已获得 HISO/SISO 并完成，16 个 code 没有获得资源并由 mux 结果标记为 pending，那么 `t=1` 的队列项必须准确恢复这 16 个 code 及其 `t=0` 的完整调度结果。`t=1` 不再把已经完成的 48 个 code 放回 mux，只把这 16 个 pending code 作为下一轮 8-entry 调度的输入；下一轮产生新的 per-code 调度结果后，更新这些 pending code 的当前资源分配和执行状态。

   **需要形成的结论：**队列中 per-code 调度结果的最小充分字段、batch 级和 code 级状态的组织方式，以及这些状态在 batch 完成、写回、提交和回收时分别何时释放。

   **当前状态：核心语义已解决，物理字段和回收细节待定。**已经确定队列保存完整 batch 内每个 code 的 8-entry/mux 调度结果，并据此识别 pending code；数据本体只保存在共享 SRAM。尚未确定的是这些结果的最小字段集合、row 映射字段、历轮结果是否保留，以及状态何时回收。
9. **缓冲区保存 code 还是保存完整 64-code 批次？**
   **逻辑上已确定采用完整 64-code batch 缓冲；物理上采用一块连续 block-row 内存。**每个 FIFO 逻辑队列项仍保留一个完整 batch 的固定 64 个 code 位置，不把 pending code 压缩成跨 batch 的独立 code 队列，也不因为部分 code 已完成就改变 batch 内的物理编号和 group 布局。但这些 batch 不要求各自占用独立 RAM 槽位，而是映射到统一的连续 block-row 内存中。

   通用物理布局为：

   ```text
   [0, R_buf)             buffer 区，共 R_buf 个 block row
   [R_buf, R_buf+22)      Level 6 解码区，共 22 个 block row
   [R_buf+22, R_mem)      Level 5 解码区，共 22 个 block row
   ```

   `[R_buf, R_mem)` 是基准位置上的 44-row 联合解码窗口；Level 6 和 Level 5 的相对位置保持不变，整个窗口可以通过起点指针向 buffer 方向移动。完整 batch 的 code、group、per-code mux 调度结果和状态需要能够映射到这块连续内存中的行位置。默认 `R_buf=32` 时该窗口为 `[32,76)`。

   完整 batch 缓冲至少包含：

   - batch 级 descriptor、batch ID 和 FIFO 顺序信息；
   - 固定的 64 个 code 位置及其原始 code/group 索引；
   - 每个 code 在 8 次 group-entry/mux 后形成的 per-code 调度结果；
   - 每个 code 的 completed/pending、资源分配、执行和写回状态；
   - P1-8 所要求的任务参数、分类/调度状态、地址映射和共享 SRAM row 引用。

   完成状态仍然是 code 粒度：已经完成的 code 不再进入后续调度，只有 pending code 在下一 `t` 重新进入 8-entry 调度。但这些已完成 code 的固定槽位和 batch 内位置在 batch 回收前仍然存在，以保持 64-code batch 的完整布局、group 索引和地址映射稳定。

   **因此不再讨论以下两种作为当前方案的候选组织：**

   - 只保存 pending code 的压缩队列；
   - 让 code 脱离原始 batch、跨 batch 重新排列的全局 code 队列。

   **仍需具体确定的保存细节：**

   - 完整 batch 的 64 个 code 如何保存共享 SRAM row 引用和可恢复参数，而不复制完整输入数据；
   - per-code 调度结果、completed/pending 位图、执行/写回状态分别如何布局；
   - 已完成 code 的数据是否只做逻辑无效标记，还是允许在 batch 尚未回收时复用其内部数据空间；
   - batch FIFO 指针、逻辑 batch 状态和连续内存 row 状态是否使用独立的存储结构；
   - batch 完成、必要提交完成后，何时正式释放整个 64-code 槽位；
   - 连续内存中每个 block row 对应的 batch/code/group 映射，以及一个完整 64-code batch 跨哪些 row 保存；
   - `R_buf` 个 buffer block row 对应最多 `floor(R_buf/2)` 个完整两行回退步长；它能承载多少种 batch/pending 组合仍转入 P1-10/P2 定量确定。默认 `R_buf=32` 时对应 16 个。

   **边界情况：**`B0` 只剩一个 pending code 时，仍然保留 `B0` 的完整 64-code 逻辑位置；下一轮只根据 pending 状态调度这一个 code。即使 `B0` 的其他 63 个 code 已完成，也不能因此让 `B1` 越过 `B0`，也不能改变 `B0` 原有的 code/group 编号。物理上是否回收某些已完成 row 的数据空间，要服从连续窗口的行映射和不覆盖 pending/history 的约束。

   **需要形成的结论：**完整 64-code batch 逻辑状态与连续 block-row 物理地址之间的映射、窗口起点变化时的状态保持方式、状态位组织和行空间回收时机；FIFO 的 batch 级组织和固定 code/group 位置不再作为待选方案。
10. **理论上的无限延后如何映射到有限硬件缓冲？**
    **问题背景：**逻辑上 pending 可以跨任意多个 `t` 延续；物理实现则用一块有限长度的连续 block-row 内存承载 buffer、Level 6 和 Level 5。基准窗口起点为 `S_0=R_buf`：

    ```text
    [0, R_buf)             buffer 区
    [R_buf, R_buf+22)      Level 6 解码区
    [R_buf+22, R_mem)      Level 5 解码区
    ```

    每个 `t` 有两行新输入写入内存底部。时刻边界上的物理 row 转移固定为：原 `[0,2)` 被顶出并作为 buffer 输出，原 `[2,R_mem)` 整体移动到 `[0,R_mem-2)`，新两行写入 `[R_mem-2,R_mem)`。设窗口起点为 `S_t`，联合解码窗口为 `[S_t,S_t+44)`，其中 Level 6 固定占据 `[S_t,S_t+22)`，Level 5 固定占据 `[S_t+22,S_t+44)`。初始 `S_0=R_buf`。

    **已确定的窗口状态转移：**

    - 物理内存每个时刻无条件上推两行，对窗口位置贡献 `-2`；本时刻内部每完成并退休一个 batch，服务对象向后续 batch 前进一步，对窗口位置贡献 `+2`；
    - 记 `C_t` 为时刻 `t` 内按 FIFO 正常完成并退休的 batch 数，则窗口起点候选更新为 `S_t-2+2*C_t`，并受物理边界限制：`S_{t+1}=clip(S_t-2+2*C_t,0,R_buf)`；`S_t=0` 时的强制退休另行计数，不伪装成正常完成；
    - 当 `C_t=0` 时，当前队首仍有 pending，下一时刻继续跟随同一个 batch，窗口起点回退两行；
    - 当 `C_t=1` 时，当前队首完成，但下一队首也随整块内存上推了两行，因此下一时刻仍使用同一个窗口位置，而不是恢复两行；
    - 只有当 `C_t>=2`，即同一时刻的完成速率超过每时刻一个 batch 的输入速率时，窗口才按 `2*(C_t-1)` 向基准位置恢复；这正是全 EarlyStop 快路径连续完成后续 batch 所产生的追赶效果；
    - `S_t` 的合法范围是 `[0,R_buf]`。当 `S_t=0` 且顶部所属 batch 仍有 pending 时，下一时刻仍执行固定两行输出和整体上推；这些 pending 不再保存或补解，所属 batch 被强制退休，窗口继续保持 `[0,44)`，服务对象转为上推进来的下一 batch；被强制顶出的两行不计入 `C_t`、吞吐量匹配或译码质量统计；
    - 无论窗口回退还是恢复，Level 6/Level 5 的 22+22 相对索引、batch FIFO 顺序、code ID、group ID 和地址映射都不改变。

    **已经确定的入队原则：**新到达 batch 的两行输入接收优先于队首是否在本 `t` 完成。新内容进入连续内存后仍追加到逻辑 FIFO 尾部，不能越过旧 batch 获得服务；窗口指针的移动只改变物理行映射，不改变 batch 服务顺序。

    **因此，原先的问题中以下语义已经不再悬而未决：**

    - buffer 的 `R_buf` 个 block row 提供最多 `floor(R_buf/2)` 个完整两行回退步长；默认 `R_buf=32` 时为 16 个；
    - row 每个时刻固定上推两行，窗口回退和恢复都只能按两行粒度进行；
    - 当前队首 pending 清空但本时刻只完成一个 batch 时，窗口保持不动；只有 `C_t>=2` 才逐步恢复；
    - Level 6 和 Level 5 始终保持窗口内固定的 22+22 相对布局；
    - 窗口起点最小为 0，不能再向前回退；到达边界后不通过背压保护旧 pending，而是按吞吐优先原则强制输出并转向下一 batch。

    **仍需具体定义的工程参数和边界策略：**

    - 已确定被强制顶出的 pending code 保持原外信息，不生成新的 extrinsic，不执行外信息写回；该数据路径行为与原方案未分配到解码资源的 code 相同；
    - 是否仍需要在内部 batch/code 状态或观测统计中单独标记强制顶出；该标记不改变外信息数据路径，也不进入吞吐量或译码质量统计；
    - 已确定强制顶出不计入正常完成数 `C_t`；控制逻辑直接由 `S_t=0 && pending` 触发，不需要额外引入 `E_t` 状态变量；仿真可选记录 `forced_evict_count`；
    - 窗口起点变化时 row 到 batch/code/group 的具体映射表，以及 batch 完成后哪些 row 可以复用；
    - 正常 batch 在完成、内部写回还是对外提交的哪一个节点计入 `C_t`；当前逻辑采用“64 个 code 完成且原五六级联合流程写回完成”作为计数节点，对外物理输出不影响 `C_t`；
    - `R_buf` 个 buffer row、FIFO 积压量和最大 pending 等待时刻之间的定量映射。

    **边界情况：**

    ```text
    t=0：解码窗口 [32, 76)，B0 产生 pending
    t=1：新两行进入，继续服务 B0，窗口回退到 [30, 74)
    t=2：B0 使用 [28, 72) 并在本时刻完成
         -> C_2=1；固定上推 -2 与完成 B0 的服务推进 +2 抵消
    t=3：B1 仍使用 [28, 72)，而不是 [30, 74)
         -> 如果 t=3 只完成 B1，则 t=4 的 B2 仍使用 [28, 72)
         -> 如果 t=3 同时完成 B1、B2，即 C_3=2，则 t=4 才恢复到 [30, 74)
    ...
    buffer 起点为 0：B0 仍有 pending
         -> 顶部两行仍按固定节拍输出，B0 剩余 pending 被强制放弃
         -> 窗口继续保持 [0, 44)，下一时刻改为服务上推进来的 B1
    ```

    这个例子说明：窗口恢复不是由“当前队首是否完成”单独决定，而是由本时刻正常完成量相对于每时刻一个 batch 的输入推进量决定。窗口已经触及 `[0,44)` 后，方案不再为旧 pending 停顿、扩容或背压；它按固定吞吐强制顶出旧内容并转向下一 batch。此时牺牲的是剩余 pending 的译码完整性，而不是输入/输出节拍。

    **需要形成的结论：**固定两行上推/输出/写入时序、`C_t` 的准确计数节点、`S_t` 的状态转移、row 到 batch/code 的映射，以及强制顶出的内部状态/统计方式。强制顶出 code 的外信息语义已经确定；`E_t` 不作为方案主状态。

    **当前状态：固定两行物理上推、顶部两行输出、底部两行写入、基于 `C_t` 的窗口更新、`S_t` 边界、边界强制退休、强制顶出时保持原外信息且不写回，以及 Level 5/Level 6 固定相对索引已确定；forced-evicted 是否单独设置内部状态只属于可选观测，不影响方案语义。`E_t` 已移除。**
11. **FIFO 队首批次在一个时刻内怎样持续获得资源？**
    **P0 已确定的前提：**正常区间采用严格 FIFO，当前最早未完成的 `Bh` 必须先获得服务；如果 `Bh` 没有完成，后续 batch 不能越过它。每个 batch 在每个 `t` 最多获得 8 个 group-entry 机会。普通 batch 提前完成后，剩余 group-entry/HISO/SISO 服务机会不再转给下一个 batch；全 EarlyStop batch 则作为零普通资源消耗的特殊快路径，可以在同一 `t` 内转交给下一个 batch。`S_t=0` 时，旧 batch 剩余 pending 被强制顶出并退休，下一 batch 随物理上推进场。

    当前代码对应的一个 `t` 内服务顺序是：

    ```text
    1. 使用当前窗口 [S_t,S_t+44)，先处理窗口前部的 Level 1-4；
       每个 tile 完成后立即写回 work_llr/history；
    2. 处理 Level 5/Level 6 共享窗口，读取前面阶段已经写回的当前输入；
    3. 对五、六级输入做 EarlyStop/Hybrid 分类；
    4. 运行 group-entry 调度，每个 batch 本 t 最多 8 个 entry；
    5. 执行获得 HISO/SISO 机会的 code；
    6. 完成 Level 5/Level 6 的 extrinsic/history 写回；
    7. 以 64 个 code 均完成且上述写回完成作为该 batch 的正常完成点；
    8. 当前 t 的窗口处理结束后，才进入顶部两行输出、全部 row 上推两行、底部写入两行新输入的边界推进。
    ```

    因此 `C_t` 只统计步骤 7 的正常完成 batch；步骤 8 的强制顶出不计入 `C_t`。窗口仍按 `S_{t+1}=clip(S_t-2+2*C_t,0,R_buf)` 更新。

    **已经确定的问题：**

    - 每个 batch 每个 `t` 最多 8 个 group-entry；
    - 64 个 code 全部完成，并且内部解码、extrinsic/history 写回已经完成时，视为该 batch 正常完成；这两个条件在当前同步调用模型下等价；
    - 普通 batch 提前完成后的剩余资源不用，不自动转给下一个 batch；
    - 跨 batch 追赶只允许全 64 个 code 都 EarlyStop 的快路径；连续全 EarlyStop batch 数量不设理论上限，直到 FIFO 为空或遇到第一个普通 batch；
    - 当前窗口先处理、写回，再进行两行物理推进；Level 5/Level 6 读取的是前面阶段已经写回后的输入。

    **当前状态：**逻辑先后关系已经确定为“当前窗口处理和必要写回完成后，再执行顶部两行输出、全部 row 上推和底部两行输入”；同一 batch 的 per-code 结果以逻辑 code ID 和原始 row 映射保持不变，窗口起点变化只改变物理位置。具体字段和地址表属于后续软件实现。

    **边界情况示例：**

    ```text
    情况 A：普通路径提前完成
        t=3：B1 使用 2 个 group-entry 后，64 个 code 全部完成并写回
             剩余 6 个 group-entry 不再使用
             B2 不在 t=3 获得普通服务
             C_3=1，窗口下一时刻保持当前位置

    情况 B：全 EarlyStop 快路径
        t=3：B1 全部 EarlyStop，不消耗普通 HISO/SISO 资源
             B2 可在 t=3 继续检查
             若 B2 也全 EarlyStop，则继续检查 B3
             若 B3 以及后续队首仍全 EarlyStop，则继续处理，不设理论上的连续 batch 数量上限；
             直到 FIFO 为空，或遇到第一个需要普通 HISO/SISO 解码的 batch
    ```

    **当前状态：已解决。**普通 batch 的服务预算和剩余资源规则、全 EarlyStop 的同一 `t` 快路径转交规则已经确定；连续全 EarlyStop batch 数量没有理论上限。本方案阶段不再追加硬件承载约束，不将实现细节写成理论 batch 数量上限。
12. **是否只在 64 个 code 全部 EarlyStop 时追赶？**
    **已经确定的规则：**跨 batch 追赶只允许发生在当前队首 batch 的 64 个 code 全部 EarlyStop 时。该 batch 走不占用普通 HISO/SISO 服务能力的快路径，并可在同一 `t` 内立即检查下一个队首；连续全 EarlyStop batch 的数量不设理论上限，直到 FIFO 为空或遇到第一个普通 batch。

    以下情况均不得把剩余资源转交给下一个 batch：

    - 当前 batch 只有部分 code EarlyStop，仍有 code 走普通 HISO/SISO 路径；
    - 普通 batch 提前完成后剩余的 group-entry；
    - HISO 或 SISO 单侧未用满形成的余量；
    - 普通路径产生的零散 group-entry 或单个 HISO/SISO 机会；
    - 当前 batch 仍有 pending code，但本 `t` 剩余资源不足以完成该 batch 的既定服务。

    这些余量统一视为本 `t` 未使用资源，不用于下一个 batch，也不改变严格 FIFO。普通路径因此不能依靠零散余量追赶窗口；窗口追赶只能依赖同一 `t` 内连续完成的全 EarlyStop batch。`S_t=0` 时的强制退休是固定吞吐边界行为，不属于资源转交或正常译码追赶。

    **当前状态：已解决。**跨 batch 追赶的唯一触发条件是“64 个 code 全部 EarlyStop”；普通路径的任何剩余资源都不跨 batch 转交。在软件仿真中，快路径的判定、完成登记和队列切换都属于同一 `t` 内的逻辑操作，不再额外引入控制、提交或内存端口预算。
13. **追赶时使用什么资源预算？**
    **软件仿真中的结论：**本方案不为全 EarlyStop 快路径建立额外的硬件资源预算模型。对当前 `t` 的队首 batch 完成全 64-code EarlyStop 判定后，直接将该 batch 标记为完成，并在同一 `t` 内继续检查下一个队首；可以连续执行任意多个全 EarlyStop batch。每个快路径 batch 都计入本 `t` 的 `C_t`。

    普通 batch 仍使用既定的服务规则：每个 batch 每个 `t` 最多 8 个 group-entry；普通解码提前完成后的 group-entry、HISO、SISO 余量不转交给下一个 batch。快路径与普通路径之间不共享或借用这些剩余资源，快路径只改变逻辑服务顺序和 `C_t` 计数。

    因此，软件仿真只需记录以下逻辑事件：

    1. 当前队首 batch 的 64 个 code 是否全部 EarlyStop；
    2. 若全部 EarlyStop，将其标记完成并保持外信息不变；
    3. 在同一 `t` 内继续检查下一个队首，直到 FIFO 为空或遇到普通 batch；
    4. 按同一 `t` 内实际完成的 batch 数累计 `C_t`，并在时刻边界统一更新窗口。

    控制周期、提交端口、内存端口以及快路径能否在具体硬件上承载任意长度的连续执行，不属于当前软件仿真的方案语义，留到后续硬件实现阶段单独评估。

    **当前状态：已解决。**软件仿真中不存在额外的快路径预算问题；全 EarlyStop batch 可以在同一 `t` 内连续执行，普通 batch 的 8 个 group-entry 和剩余资源规则保持不变。
14. **同一时刻连续处理多个批次时如何选择 group？**
    **P0 已确定的前提：**正常区间中批次之间严格 FIFO，不做跨 batch 全局负载排序；后续 batch 不能因为 EarlyStop 率更高或 pending 更少而越过未完成的 `Bh`。`S_t=0` 的强制退休是物理边界例外，不参与 group 优先级比较。因此本问题只讨论队首 batch 内部以及 batch 正常完成后的 group 组织。

    **已经确定的 batch 内调度规则：**

    当前普通 batch 的 group 选择和 8-entry 调度，尽量沿用原五六级共享方案的既有调度方式，不在新方案中另设固定顺序、轮询顺序或按 pending 数量排序的 group 策略。当前 44-row 解码窗口只负责提供原有调度器需要的 row 映射：Level 6 对应窗口内前 22 个 block row，Level 5 对应后 22 个 block row；窗口起点变化不改变逻辑 group、code 索引和物理 row 的一一对应关系。

    每个 `t` 仍完整沿用原五六级共享方案已有的 EarlyStop、Hybrid classify-only、资源资格、group 负载、mux 和 HISO/SISO 状态。新方案不把这些状态重新定义成另一套新的 mux 前状态，只在原流程进入 mux/scheduler 前叠加一个 64-bit `AlreadyDecoded` 完成位图：

    - `AlreadyDecoded[i]=true`：code i 已在更早的服务时刻完成，本轮从 EarlyStop/Hybrid、group 负载、mux、HISO/SISO 和写回中屏蔽；
    - `AlreadyDecoded[i]=false`：code i 尚未完成，继续按保存的原方案分类和资源资格处理。

    EarlyStop code 也属于后续的 `AlreadyDecoded` 完成集合：第一次处理时仍执行原 EarlyStop 路径，路径完成后从下一 `t` 开始以 `AlreadyDecoded=true` 屏蔽。若 64 个 code 全部 EarlyStop，则它们在同一 `t` 内全部完成，batch 直接退休。

    `AlreadyDecoded` 是覆盖在原状态之上的新增完成标记，不替代原 EarlyStop/Hybrid 分类。`pending` 也不是 mux 前新增的路径分类，而是上一次 mux 后产生的调度结果，表示该 code 没有实际获得 HISO/SISO 资源。到下一 `t` 时，只要它尚未完成且没有被强制顶出，就保持 `AlreadyDecoded=false`，并按照保存的原分类和资源资格重新进入原 scheduler。

    按照 P0-5 和 P1-8 已确定的共享 SRAM 语义，跨 `t` 后从当前共享行重建服务输入，但不重新计算 EarlyStop/Hybrid 分类。随后把应用 `AlreadyDecoded` 屏蔽后的未完成 code 送入原五六级共享方案的既有 8-entry/group scheduler。该 scheduler 仍按原方案执行 group 选择、mux 和 HISO/SISO 分配，并产生本轮 mux 后的完整 per-code 调度结果：

    - `AlreadyDecoded`：保持完成状态，不执行任何动作；
    - `EarlyStop`：按 EarlyStop 路径完成，外信息保持不变且不产生新写回；
    - 获得 HISO/SISO 资源：在本轮执行对应的完整普通解码；
    - 未获得 HISO/SISO 资源：本轮 mux 后标记为 `pending`，等待下一 `t`。

    P1-8 所说的“完整调度结果”就是上述 mux 后结果：它不仅包含原始路径分类，还记录本轮是否实际获得资源以及是否成为 pending。下一 `t` 直接由 completed 位图生成 `AlreadyDecoded` 屏蔽，并让其余 pending code 按保存的原分类和资源资格继续调度，不恢复或创建新的 mux 前分类状态。

    1. 已完成 code 在进入本轮 mux/scheduler 前标记为 `AlreadyDecoded` 并屏蔽，不再重复分类、重复分组或重复解码；
    2. 上一 `t` 的 pending code 按其原始 HISO/SISO 分类恢复为未完成候选，重新参与本轮调度；
    3. 原有 scheduler 按既有 group 选择、HISO/SISO 资格和 mux 规则分配最多 8 个 group-entry；
    4. 获得 HISO/SISO 的 code 执行普通解码并按原方案写回；
    5. 本轮仍未获得资源的 code 保持 pending，下一 `t` 只对这些 code 重新进入同一套调度流程。

    因此，新方案改变的是“哪些 code 进入本轮候选”和“pending 可以跨 `t` 保留”，不改变原有五六级共享 scheduler 的 group 选择和 mux 规则。

    **跨时刻示例：**

    ```text
    t=0，B0 的原始 64-code 分类：
        code 0~15   -> EarlyStop
        code 16~39  -> HISO 候选
        code 40~63  -> SISO 候选

    原有 8-entry/mux scheduler 完成后：
        code 0~15   -> EarlyStop 完成，外信息不写回
        code 16~27  -> 获得 HISO 并完成
        code 40~47  -> 获得 SISO 并完成
        其余 code   -> 未获得资源，标记 pending

    t=1 再次服务 B0 时，在原方案状态上应用 AlreadyDecoded 位图：
        code 0~15、16~27、40~47 -> AlreadyDecoded=true，屏蔽
        code 28~39              -> AlreadyDecoded=false，保持原 HISO 资格
        code 48~63              -> AlreadyDecoded=false，保持原 SISO 资格

    然后将整份 64-code 状态按原五六级共享方案送入 mux；
    AlreadyDecoded code 被屏蔽，实际候选是 code 28~39 和 code 48~63，
    再由原 scheduler 完成最多 8 个 group-entry 的调度。
    ```

    该例中的 code 编号和分配数量只用于说明状态覆盖关系；实际选中哪些 group、哪些 HISO/SISO code，仍完全由原五六级共享调度器决定。

    **batch 切换时的已确定规则：**

    - `Bh` 完成并完成必要写回/提交后，剩余 group-entry 不转给 `Bnext`；
    - 只有在进入 `Bnext` 前重新执行其全 64-code EarlyStop 判定时，才允许走无普通资源消耗的快路径；
    - 如果 `Bnext` 全 EarlyStop 并快速完成，则递归检查 `B2`、`B3` 及后续队首，连续数量不设理论上限；
    - 同一 `t` 完成多个 batch 时，逻辑上的完成、写回、batch 退休和 `C_t` 计数仍按 FIFO 顺序发生；窗口起点在时刻边界根据最终 `C_t` 一次更新；
    - 普通 batch 完成后不把原 scheduler 的剩余 group-entry 状态带给 `Bnext`；如果 `Bnext` 全 EarlyStop，则直接走快路径，否则等待下一 `t`，按 `Bnext` 自己的 pending/分类结果进入原有 scheduler。

    **边界情况：**`B1` 在一个 `t` 中完成最后一个 pending code 后还剩 2 个 group-entry，这 2 个机会不能直接用于普通路径的 `B2`。系统只能重新检查 `B2` 的 64 个 code：若全部 EarlyStop，则 `B2` 走快路径；否则 `B2` 留待后续 `t`，从自己的调度状态重新获得最多 8 个 group-entry。

    **当前状态：核心逻辑已解决。**队首 batch 内沿用原五六级共享方案的 group/mux 调度；每轮只把未完成候选送入 scheduler，已完成 code 永久剔除，未获资源 code 标记为 pending 并在下一 `t` 重新参与。batch 切换时普通资源不转交，只有全 EarlyStop 才能在同一 `t` 继续快路径。具体软件实现中的状态字段和调用组织留到后续实现阶段。
15. **已完成状态如何保证只执行、只写回一次？**
    **P0 已确定的前提：**code 是最小完成单位；已完成 code 永久退出后续调度；只有 pending code 可以在下一 `t` 重新进入候选集合；全 EarlyStop code 完成但不产生新的外信息写回。

    连续 block-row 内存下，还必须把逻辑状态与物理 row 地址解耦：每个时刻全部 row 固定上推两行，窗口起点再根据 `C_t` 在 `[0,R_buf]` 内更新；这些物理地址变化不应让同一个 code 再次执行或重复写回。

    **需要定义的状态转换：**

    ```text
    未进入当前 batch 调度
        -> 本次未获得 HISO/SISO，标记为 pending
        -> 获得 HISO/SISO，执行完整解码
        -> 解码成功，标记为 completed
        -> 正常路径结果完成一次内部写回
        -> 所属 batch 满足提交条件，完成一次对外提交
    ```

    全 EarlyStop code 使用单独的快路径：

    ```text
    EarlyStop
        -> 标记 code/batch 完成
        -> 外信息保持原值
        -> 不产生新的 extrinsic，不执行新的外信息写回
    ```

    `S_t=0` 时未完成 code 使用第三种边界状态：

    ```text
    pending
        -> 随顶部两行被强制顶出
        -> 标记为 forced-evicted
        -> 永久退出后续调度，不再补解或写回
    ```

    `forced-evicted` 与 `completed`、`EarlyStop` 必须区分；它表示为了维持固定吞吐而放弃未完成译码，不代表产生了有效的新解码结果。其外信息处理与原方案未分配资源 code 相同：保持原值，不产生新的 extrinsic，不执行外信息写回。

    **正常路径的逻辑状态已经确定：**

    - code 只有在获得普通资源并完成原五六级联合流程及必要内部写回后，才从 pending 进入 completed；
    - EarlyStop code 直接进入 completed，但保持外信息不变且不产生新写回；
    - completed/AlreadyDecoded code 永久退出后续 mux 和 scheduler；
    - 64 个 code 都完成且联合写回完成时，batch 正常完成并计入 `C_t`；额外完成的 batch 仍留在连续内存中，等待后续物理上推输出；
    - `S_t=0` 时被顶出的 pending code 进入 forced-evicted，所属 batch 作为吞吐优先的强制退休离开 FIFO，不计入 `C_t`、吞吐量或译码质量统计；
    - 正常完成、EarlyStop 和 forced-evicted 不得重复触发解码或新外信息写回。

    仍属于逻辑异常边界的问题只有：已经获得 HISO/SISO 资源但执行失败时是否回到 pending、是否重试，以及 reset/flush 时是否丢弃未完成 batch。这些不影响正常 burst 路径，分别留给 P4-31 和实现边界处理。

    **异常边界：**如果 code 已获得 HISO/SISO 资源但执行失败，是否回到 pending、允许重试几次、重试是否重新使用原始输入，属于 P4-31 的失败/重试策略；P1-15 需要保证无论采用哪种策略，都不会把一次失败尝试错误计为重复成功写回。

    **当前状态：正常路径的 code/batch 状态机和 exactly-once 语义已解决；异常失败/重试和 reset/flush 属于后续边界问题。**

### P2：吞吐量与稳定性

16. **逻辑方案中的抽象服务能力如何定义？**
    当前只定义每个 `t` 的抽象服务边界：普通 batch 每个 `t` 最多获得 8 个 group-entry，普通路径提前完成后的剩余机会不跨 batch 转交；全 EarlyStop 快路径不占用普通解码机会，可以在同一 `t` 内连续完成多个 batch。总体吞吐量匹配主要观察内部正常完成数 `C_t`；顶部物理输出仍固定为每个 `t` 两行，额外完成的 batch 留在连续内存中等待后续上推。具体服务能力由什么硬件提供、每个 group-entry 如何映射到 HISO/SISO，以及控制和端口开销如何实现，全部后置到软件/硬件实现阶段。
17. **稳定条件如何由 buffer 容量定义？**
    **当前结论：**不再单独设置“有限窗口长度”参数。可调的 `R_buf` 个 buffer block row 和每个 `t` 固定上推两行，直接定义最多 `floor(R_buf/2)` 个完整两行回退步长；`S_t` 从 `R_buf` 回退到 0 后，进入强制顶出边界。内部正常完成数 `C_t` 只用于窗口状态转移和事后分析，不要求调度器实时观察或反馈 `C_t`。因此，短期可承受缺口、正常等待范围和恢复能力都由 buffer 容量、`S_t` 边界以及后续实际出现的 `C_t>=2` 共同决定，不引入独立的 `W`。
18. **buffer 容量对应的最大积压和延迟是多少？**
    逻辑上 pending 可以跨多个 `t` 延后，但最多正常跟随窗口从 `S_t=R_buf` 回退到 `S_t=0`，即最多承受 `floor(R_buf/2)` 个完整两行回退步长。每出现一个 `C_t=0` 的时刻，窗口净回退两行；`C_t=1` 只能维持当前位置；`C_t>=2` 才能恢复。到达 `S_t=0` 后不再增加正常等待时间：仍未完成的顶部内容在下一次推进时强制退休。这里不再另设窗口长度或质量 deadline；需要进一步量化的只剩这些回退步长如何换算成具体 batch 积压和 code 等待年龄，这属于连续内存布局与 batch 行映射的参数推导。强制顶出的两行不计入吞吐量和译码质量统计。
19. **连续 burst 或长期超载时如何退化？**
    当连续多个时刻 `C_t=0`，窗口起点持续向 buffer 方向回退并最终到达 `[0,44)`。已确定采用吞吐优先退化：下一时刻仍输出顶部两行、上推全部 row 并接收底部两行；旧 batch 的剩余 pending 被强制放弃，窗口继续保持 `[0,44)` 并服务下一 batch。不采用为了保存旧 pending 而暂停输入或阻止内存推进的背压策略。强制顶出的两行保持原外信息且不执行外信息写回，不计入 `C_t`、吞吐量或译码质量统计；恢复条件仍表示为后续出现 `C_t>=2`。
20. **追赶是否真的能恢复对外节拍？**
    一个全 EarlyStop 队首批次本身不消耗普通 HISO/SISO 服务能力，并且已确定可以在同一 `t` 内继续转向下一个 batch。连续完成的全 EarlyStop batch 数量没有理论上限：只要 FIFO 仍有队首且该队首全 EarlyStop，就继续快路径；遇到普通 batch 或 FIFO 为空时停止。因此同一 `t` 完成多少个全 EarlyStop batch，直接按实际完成数计入 `C_t`，并按 `S_{t+1}=clip(S_t-2+2*C_t,0,R_buf)` 恢复窗口。`S_t=0` 的强制退休可以维持物理输出节拍，却不能算作正常译码完成或追赶。强制顶出只需作为可选观测计数，不引入 `E_t` 主变量。

### P3：EarlyStop、History 与跨时刻语义

21. **全 EarlyStop 时具体跳过哪些步骤？**
    P0 已确认全 EarlyStop 队首批次走快路径：不进入普通 Hybrid/HISO/SISO 解码，不生成新的 extrinsic，不执行新的外信息写回，外信息保持原值，并在同一 `t` 内立即标记批次完成。软件仿真把完成标记、队列切换和必要的逻辑提交视为该快路径的一部分，不单独建模硬件周期或带宽。
22. **延后期间 prior/history 如何保持？**
    P0 已确定输入、prior 和 history 数据只存在于连续 SRAM；pending code 等待期间不产生自己的新写回，下一次服务时按当前 row 映射读取共享 SRAM，并沿用冻结的任务参数和分类。连续 block-row 内存每个时刻固定上推两行，窗口起点再根据 `C_t` 在 `[0,R_buf]` 内更新。当 `S_t=0` 时不再补解被顶出的 pending code；这些 code 转为 forced-evicted，并沿用原方案未分配资源 code 的语义：原外信息保持不变，不生成新的 extrinsic，不执行外信息写回。
23. **Level 5 与 Level 6 的延后是否可以独立完成和写回？**
    两级使用不同 alpha、beta 和地址映射，且最终 history 由 Level 6 路径捕获。沿用原五六级共享方案，一次获得普通解码机会后，按原流程完整执行该 code 所需的 Level 5/Level 6 联合处理和写回；不在新方案中把两级拆成两个独立的跨 `t` 调度任务。只有该 code 的联合流程完成后，才标记为 `completed/AlreadyDecoded`，下一轮不再进入 mux。物理上 Level 6 始终占当前 44-row 窗口的前 22 个 block row，Level 5 始终占后 22 个 block row；窗口移动只改变两段的物理位置，不改变 code 粒度和联合完成语义。`S_t=0` 时未完成 code 按统一规则强制顶出。

    **当前状态：已解决。**Level 5 和 Level 6 在逻辑上沿用原方案作为一次完整联合流程，`AlreadyDecoded` 仍为 code 粒度；不定义 Level 5 已完成而 Level 6 独立 pending 的新状态。
24. **新方案是否需要前瞻信息？**
    **当前状态：已解决。**调度完全不看未来 batch 的 EarlyStop 率、pending 数量或负载信息。系统只根据当前 FIFO 队首 batch 的原始分类、completed/AlreadyDecoded 状态、pending 状态和当前 `t` 的服务规则进行处理；后续 batch 只有在成为队首后才进行分类检查。这样保持严格 FIFO，也不引入前瞻分支。
25. **EarlyStop/Hybrid 分类结果是否跨时刻保持有效？**
    在当前共享 SRAM 语义下，pending code 的服务输入会随前序 FIFO 写回自然更新，但其 8-entry/mux 调度结果、EarlyStop/Hybrid 分类和资源资格仍沿用该 batch 首次服务时的判定。下一轮只重新对 pending code 进行资源调度，并更新其当前调度结果；已完成 code 不重新分类、不重新调度。如果未来要根据更新后的 SRAM 重新分类，必须另立方案并重新定义分类变化和状态转换。

### P4：边界、验证与观测

26. **帧首和帧尾如何处理？**
    帧首时连续内存初始化为 buffer 区 `[0,R_buf)` 和解码窗口 `[R_buf,R_mem)`，即 `S_0=R_buf`，并按正常到达节拍接收 `B0`。默认 `R_buf=32` 时才对应 `[0,32)`、`[32,76)`。帧尾停止产生新 batch 后，仍需严格按 FIFO 继续服务队首 pending batch，进入 drain 阶段，直到所有已接收 batch 完成并提交；不能因为没有新的两行输入到达就让最后遗留 code 永远没有调度机会。正常流阶段每个时刻固定执行顶部两行输出、全体 row 上推和底部两行写入；仍需单独定义 drain 阶段在没有新两行输入时是否继续上推、`S_t` 公式中的基准 `-2` 是否仍然存在，以及帧尾完成判定。
27. **如何证明没有丢、重、错序和错地址？**
    每个原始 code 需要可追踪的唯一身份，并验证：每个 code 最终恰好进入 `completed`、`EarlyStop` 或 `forced-evicted` 之一；正常写回至多一次；批次按 `B0 -> B1 -> ...` 顺序正常完成或强制退休；目标地址与原始批次映射一致。连续内存还要验证：每次顶部两行输出、全体 row 上推和底部两行写入后，row 到 batch/code/group 的映射保持稳定；根据 `C_t` 更新窗口时，Level 6/Level 5 始终保持前 22 行/后 22 行的固定相对索引；`S_t=0` 时只有明确触发的强制退休可以放弃 pending，不能发生无标记丢失；同一 `t` 内多批次切换不会产生重复提交或错序。
28. **需要记录哪些运行指标？**
    至少应记录每时刻新到达 batch 数、正常完成并退休的 batch 数 `C_t`、净追赶量 `max(0,C_t-1)`、队列中的 batch 数、FIFO 队首 pending code 数、最老等待年龄、当前窗口起点 `S_t`、窗口净变化、buffer 已用 block row 数、距 `S_t=0` 的剩余回退步数、顶部两行输出量、底部两行输入量以及 HISO/SISO/group-entry 使用量。`forced_evict_count` 可以作为可选控制观测，但强制顶出的两行不计入吞吐量和译码质量统计。
29. **方案效果用什么标准评价？**
    需要比较 buffer 可承受范围内的 batch 到达量、内部正常完成量 `C_t`、平均/峰值 backlog、平均/最大延迟、队首最大 pending 持续时间、窗口恢复时间、资源利用率和缓冲成本。强制顶出的两行不纳入吞吐量匹配，也不纳入译码质量统计；如需记录其数量，只作为可选边界观测。评价仍应覆盖短时 burst、可恢复 burst、触及 `S_t=0` 的 burst 和持续超载。
30. **第一版仿真的边界是什么？**
    第一版应先验证逻辑语义：FIFO/pending/快路径调度、code 粒度完成、正常区间严格 FIFO、同一 `t` 内多批次转交、`C_t=0/1/2+` 三类窗口更新、Level 6/Level 5 固定相对索引、`S_t=0` 强制退休和帧尾 drain。帧尾 drain 尚未落地前，BER 统一固定裁掉前 4 个 warm-up window 和后 2 个 window；该范围根据 `R_buf=32` 时未 drain FIFO 尾部的最早影响位置确定，且必须对所有 R_buf 使用同一分母。连续内存模型应按 `[0,R_buf)` buffer、`[R_buf,R_buf+22)` Level 6、`[R_buf+22,R_mem)` Level 5 参数化验证；`R_buf=32` 只是 `[0,32)`、`[32,54)`、`[54,76)` 的默认案例。固定端口带宽、硬件周期等实现细节不属于当前第一阶段方案验证。
31. **已获得资源但解码失败的 code 如何处理？**
    **当前状态：已解决并关闭该异常分支。**沿用原五六级共享方案的逻辑假设：code 一旦获得 HISO/SISO 普通解码机会，就按原流程完成本次联合解码和写回；新方案不定义“获得资源后失败并重新进入 pending”的重试状态，也不引入 `decode-failed` batch 状态。没有获得资源的 code 才是 pending，下一 `t` 按原调度流程重新参与。

    原实现中可以记录某次 action 是否 `produced`，并存在 `ActionFailed` 这样的执行结果状态；这属于执行结果/诊断信息，不改变 pending 语义，也不会自动触发下一 `t` 的重调度。HISO executor 发生异常时沿用原实现直接报错，不转换为普通 pending。当前理论方案不进一步展开这类实现异常。
