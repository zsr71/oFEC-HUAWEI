# 软硬混合方案三两拍版说明

本文说明方案三的一个硬件友好变体：`TwoCandidate` 不再进入 BCH hard decoder 或 two-error confirm，而是直接送入 Chase / 软解码。这样可以避免两错确认带来的额外一拍延迟，使前置分流和 MUX 调度在两拍内完成。

## 1. 设计动机

标准方案三中，`S0/S1/S3` 快速分类后会得到一类特殊行：

```text
TwoCandidate
```

它表示 syndrome 看起来像 BCH 主体 2 位错误候选，但还不能直接判定为 `HardFinish`。标准三拍版需要把这类行送入 BCH hard decoder，或者 two-error locator + Chien search 进行确认。

这会带来一个硬件时序问题：

```text
第 2 拍 fast classification 结束后，TwoCandidate 仍未最终确定。
必须等第 3 拍 confirm 返回，才能知道它是 HardFinish 还是 Chase candidate。
```

因此完整的 Chase candidate mask 要等第三拍才能生成，MUX / SISO 调度也要等第三拍。

两拍版的思路是：

> 放弃在前端硬完成 TwoCandidate，直接把所有 TwoCandidate 送入 Chase。

这样 fast classification 结束后，所有行的去向都已经确定，不需要等待额外 confirm。

## 2. 两拍版的核心原则

两拍版保留方案三的主体结构：

- early-stop 行仍然提前移出 Chase 资源池。
- clean / parity-only / single-error 类行仍然可以前端 hard-finish。
- MUX 仍然只对真正需要 soft decode 的行分配 SISO 资源。
- 不同类型行最后仍然合并成完整 tile 输出。

变化只有一个：

```text
TwoCandidate 不再尝试 hard confirm。
TwoCandidate 直接归入 Chase candidate。
```

因此两拍版中，前端可以直接 hard-finish 的类别只有：

- `Clean`
- `ParityOnly`
- `OneMain`
- `OneMainPlusParity`

需要进入 Chase 的类别是：

- `TwoCandidate`
- `HardFailCandidate`

## 3. 判断表

基于 `S0/S1/S3` 的两拍版判断表如下。

| 条件 | 分类 | 两拍版处理 |
| --- | --- | --- |
| `S0=0, S1=0, S3=0` | `Clean` | 直接 `HardFinish` |
| `S0=1, S1=0, S3=0` | `ParityOnly` | 修正 parity 后 `HardFinish` |
| `S1!=0, S3=S1^3, S0=1` | `OneMain` | 修正 1 个 BCH 主体位后 `HardFinish` |
| `S1!=0, S3=S1^3, S0=0` | `OneMainPlusParity` | 修正 1 个 BCH 主体位和 parity 后 `HardFinish` |
| `S0=0, S1!=0, S3!=S1^3` | `TwoCandidate` | 直接进入 Chase candidate |
| 其他情况 | `HardFailCandidate` | 直接进入 Chase candidate |

这个表里最重要的变化是：

```text
TwoCandidate 不再是待确认队列，而是直接进入 Chase 队列。
```

## 4. 两拍硬件时序

两拍版可以按下面时序实现。

第 1 拍：计算 syndrome。

```text
输入 32 个码字
并行计算每个码字的 S0 / S1 / S3
```

第 2 拍：快速分类并生成完整调度 mask。

```text
Clean / ParityOnly / OneMain / OneMainPlusParity
  -> 进入 hard_finish_mask

TwoCandidate / HardFailCandidate
  -> 进入 chase_candidate_mask

MUX 可以直接基于 chase_candidate_mask 做 SISO 调度
```

两拍版的 mask 生成关系为：

```text
hard_finish_mask =
    clean_mask
  | parity_only_mask
  | one_main_mask
  | one_main_plus_parity_mask

chase_candidate_mask =
    two_candidate_mask
  | hard_fail_candidate_mask
```

因为没有等待 confirm 的中间队列，所以第二拍就能得到完整的 Chase 候选集合。

## 5. 与三拍版的区别

两拍版和三拍版的关键区别如下。

| 对比项 | 两拍版 | 三拍版 |
| --- | --- | --- |
| `TwoCandidate` 处理 | 直接送 Chase | 送 BCH / locator confirm |
| Chase candidate mask | 第 2 拍完整生成 | 第 3 拍完整生成 |
| MUX 调度 | 第 2 拍即可开始 | 等 confirm 返回后统一调度 |
| 控制复杂度 | 低 | 较高 |
| Chase 负载 | 更高 | 更低 |
| HardFinish 数量 | 更少 | 更多 |
| 是否需要 two-error confirm 模块 | 不需要 | 需要 |
| 是否存在 third-pulse 回流调度问题 | 不存在 | 需要处理或等待 |

两拍版牺牲了一部分可硬完成的 2-error 行，换来更短的调度时序和更简单的硬件控制。

## 6. 对 MUX / SISO 调度的影响

两拍版中，MUX 看到的 Chase 候选集合已经是完整集合，不存在第三拍又新增 two-fail 行的问题。

因此 MUX 逻辑可以保持简单：

```text
输入 chase_candidate_mask
根据 SISO_ACTIVE 预算选择进入 Chase 的行
未获得预算的行标记为 Unscheduled
```

这避免了三拍版中的复杂问题：

```text
第 2 拍已经分配完 SISO 预算
第 3 拍 TwoCandidate confirm 失败，又产生新的 Chase 候选
```

两拍版不会产生这种跨拍补充候选，因此不需要抢占、重排或额外缓存策略。

## 7. 对性能和资源的影响

两拍版的优点：

- 前置分类和 MUX 调度时序更短。
- 不需要 two-error confirm 模块。
- 不需要处理第三拍返回候选导致的调度重排。
- 硬件控制更简单，适合作为第一版实现。
- 保留了方案三最重要的结构收益：把 clean、parity-only、single-error 行提前移出 Chase 池。

两拍版的代价：

- 所有真实可纠的 two-error 行都会进入 Chase。
- Chase 候选数量会比三拍版更多。
- SISO 资源压力会比三拍版更高。
- 如果 `TwoCandidate` 比例较高，可能影响软解码资源利用率和未调度比例。

因此两拍版更偏向“时序优先、控制简单”，三拍版更偏向“减少 Chase 负载、提升前端硬完成比例”。

## 8. 推荐使用场景

两拍版适合以下场景：

- 第一版硬件实现，需要尽量降低控制复杂度。
- 目标是先验证方案三的主体结构，而不是最大化 hard-finish 数量。
- 当前 `TwoCandidate` 比例不高，直接送 Chase 的额外负载可以接受。
- MUX / SISO 调度暂时不希望支持跨拍候选回流。

三拍版适合以下场景：

- 需要进一步降低 Chase 负载。
- 硬件中已经有可用 BCH hard decoder 或 two-error confirm 模块。
- 可以接受 MUX 等第三拍统一调度，或者有能力处理跨拍重排。

## 9. PPT 可用总结

两拍版可以总结为：

> 为了避免 `TwoCandidate` 确认带来的第三拍延迟，两拍版不在前端硬纠疑似两错行，而是直接把所有 `TwoCandidate` 送入 Chase。这样第二拍 fast classification 后即可生成完整的 `hard_finish_mask` 和 `chase_candidate_mask`，MUX 可以立即基于完整 Chase 候选集合做 SISO 调度。代价是部分本可硬完成的两错行会进入 Chase，换来更短时序和更简单的硬件控制。

一句话版本：

> 两拍版用更多 Chase 负载换更简单的硬件时序：`TwoCandidate` 不确认，直接进 Chase。
