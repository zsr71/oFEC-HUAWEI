# 0414 会议任务

根据会议记录，解码早停算法层面可以做的任务主要包括以下几个方面。这些任务主要关注：

- 如何判断早停
- 如何更新外信息
- 如何调度未译码的码字

这里暂不展开硬件实现细节。

## 一、早停判据的设计与优化

### 1.1 不同粒度的早停判据

- 行早停（单 code 早停）

  - 每个 code 的伴随式为零时，该 code 即可早停。
  - 适用于早停率较低（如大于 10%）的场景。
- 块早停（多 code 联合早停）

  - 连续多个 code（如 32 个或 4 个）同时满足伴随式为零时，整块早停。
  - 适用于早停率很高的末级迭代。
- 32 行块早停

  - 当前 32 并行架构下可直接支持。
- 4 行块早停

  - 因 SRAM 交织问题难以实现，优先级降低，但算法上仍可探讨。

### 1.2 动态门限调整

- 针对不同迭代级数设置不同的早停门限。
  - 例如第 6 级门限设为 `2.15` 或 `2.2`。
- 目标是匹配该级的实际早停率。
- 需要扫描不同门限下的：
  - 早停率
  - 性能损失曲线
- 最终找到最优折中点。

### 1.3 早停判据的组合使用

在同一个译码器中混合使用多种早停策略，例如：

- 前几级（早停率低）
  - 行早停
- 中间级（早停率中等）
  - 行早停 + 半减值 MAX
- 最后一级（早停率高）
  - 32 行块早停

需要通过算法仿真验证不同组合下的：

- 性能
- 早停率提升效果

## 二、外信息更新策略的简化与优化

### 2.1 伴随式为零时的极简更新

当前算法：

- 早停后仍读取 VN
- 加 LLR
- 过 CSO
- 加 β
- 再写回

这一流程较复杂，硬件代价较大。

建议的简化方向：

- 当伴随式为零时，直接根据当前比特的硬判结果（HD）
- 给外信息赋值一个固定符号的 `β`
- 不再做额外计算

待仿真任务：

- 扫描 `β` 的大小，例如：
  - `β = 1, 2, 4, 8, ...`
- 观察 FER 性能损失
- 确定一个在精度损失可接受范围内（如 `< 0.02 dB`）的最大简化方案
- 研究 `β` 是否可随迭代级数自适应增大
  - 越往后，`β` 越大

### 2.2 外信息不更新

极端简化方案：

- 当伴随式为零时，外信息保持不变
- 不加 `β`

需要评估的问题：

- 这种方案是否会导致后续迭代收敛变慢
- 性能损失有多大

### 2.3 外信息的符号与绝对值拆分

将外信息表示为：

```text
sign * value
```

其中：

- `sign` 与当前比特的硬判结果一致
- 早停时只更新 `value` 部分
  - 例如直接设为 `β`
- `sign` 从 HD 直接获得

这一拆分对算法本身无影响，但有利于硬件实现简化。

## 三、未译到码字的调度与补偿

### 3.1 问题描述

当只放置少量 CSO（如 16 个）时：

- 大部分码字能译到
- 但仍有一小部分无法译到

这部分码字的外信息得不到更新，可能影响整体收敛。

### 3.2 算法层面的解决思路

- 缓存未译码字

  - 将本轮未译到的码字信息（LLR、当前外信息等）缓存起来
  - 下一轮或后续空闲时重新调度译码
- 优先级排队

  - 维护一个待译码字队列
  - 每次译码前先处理缓存中未完成的码字
- 动态调整译码顺序

  - 不严格按照固定时序
  - 根据码字的“紧迫程度”提前调度
  - 例如连续几次未译到的码字优先

### 3.3 与硬件的协同

这些算法思路需要硬件支持，例如：

- 额外缓存
- 调度器

这可能带来面积和复杂度增加。

因此需要评估：

- 算法性能提升
- 硬件代价
- 是否值得实现

## 四、针对不同早停率的设计原子

### 4.1 目标

不局限于 OFAC 一种码字，而是为任意 FEC 码字提供一个：

```text
早停率 -> 推荐方案
```

的映射表。

例如：

- 早停率 `10% ~ 30%`
  - 行早停 + 小 MAX
- 早停率 `40% ~ 70%`
  - 半减值 MAX + 分组
- 早停率 `80% ~ 99%`
  - 32 行块早停 + 外信息极简更新

### 4.2 需要算法仿真完成的任务

- 对目标码字（OFAC 或其他）进行多级迭代仿真
- 统计每级的：
  - 逐 code 早停率
  - 逐块早停率（块大小 32/16/8/4）
- 绘制早停率随迭代级数变化的曲线
  - 通常为指数衰减或近似线性
- 针对不同早停率区间
  - 仿真上述推荐方案的性能损失
  - 验证其可行性

## 五、性能评估指标

### 5.1 主要指标

- FER/BER 性能损失

  - 相对于基线（无早停或全精确更新）
  - 损失应控制在 `0.01 ~ 0.02 dB` 以内
- 平均迭代次数减少

  - 衡量早停带来的收敛加速效果
- 资源节省

  - 与早停率直接相关
  - 需进一步折算成面积或功耗收益

### 5.2 基线选择

建议采用简化基线：

- 伴随式为零时，外信息返回 `±β`

这样更容易凸显硬件优化收益。

另外也可以采用当前实现的精确算法作为基线，但可能会导致：

- 硬件优化后的性能损失显得更大

## 六、总结：算法层任务清单

| 任务             | 具体内容                                | 优先级 |
| ---------------- | --------------------------------------- | ------ |
| 早停门限扫描     | 对不同级数寻找最优早停门限              | 高     |
| 块早停判据验证   | 仿真 32 行 / 4 行块早停的早停率与性能   | 高     |
| 极简外信息更新   | 伴随式为零返回 `±β`，扫描 `β` 值 | 高     |
| 外信息不更新评估 | 测试完全不更新外信息的性能损失          | 中     |
| 未译码字调度算法 | 设计缓存与重调度策略，仿真性能提升      | 中     |
| 不同早停率方案库 | 绘制早停率曲线，提供设计原子            | 高     |
| 基线简化         | 选用简化算法作为新基线                  | 中     |

## 说明

这些算法任务与硬件设计紧密耦合，需要协同推进。

### 7.1 早停判据相关

#### 任务：行早停（单 code 早停）

- 状态：已支持
- 现状说明：
  - 当前已经支持逐 `row` 的 early-stop。
  - 条件 1：
    - BCH syndrome 为零
    - overall parity 正确
  - 条件 2：
    - 基于 `|LLR|` 阈值和不可靠 bit 数判断
  - 支持按 tile 开关 early-stop。

#### 任务：32 行块早停 / 4 行块早停

- 状态：可部分支持
- 现状说明：
  - 当前已经支持“分组绑定 early-stop”机制。
  - 可以通过 `EARLY_STOP_BIND_GROUP_SIZE` 设置：
    - `1`：逐 row 早停
    - `4`：每 4 个 row 绑定
    - 其它 `>1`：按对应组大小绑定
  - 也就是说，算法层面已经能做“多 row 联合通过才早停”的实验。
- 当前不足：
  - 这还不是完全独立的“块早停判据体系”，而是在现有条件 1 后面加了一层组绑定。
  - 目前主要服务于条件 1。
  - 32 行整块和 4 行整块都能模拟，但还没有专门针对这些块模式设计单独统计、专门输出和系统性 sweep 入口。

#### 任务：动态门限调整

- 状态：可部分支持
- 现状说明：
  - 对条件 2，已经支持门限参数扫描：
    - `EARLY_STOP_V2_LLR_ABS_THRESHOLD`
    - `EARLY_STOP_V2_MAX_UNRELIABLE_BITS`
  - `ofec_sweep` 里也已经暴露了对应 candidates，可直接扫。
- 当前不足：
  - 会议里提到的“不同迭代级数设置不同早停门限”，当前还不支持按 tile 或按迭代级数分别设置不同门限列表。
  - 现在是全局一个条件 2 门限，而不是每一级不同门限。

#### 任务：多种早停判据组合使用

- 状态：当前缺少功能
- 现状说明：
  - 当前全局只支持一个 `EARLY_STOP_CONDITION_MODE`。
  - 不能做到：
    - 前几级用一种判据
    - 中间级再加别的逻辑
    - 最后一级切另一种块判据
- 当前缺少：
  - 按 tile 单独选择 early-stop 条件模式
  - 按 tile 单独配置不同组合策略

## 九、针对当前缺失功能的代码改造思路

这一节只讨论“当前还不能直接做”的任务，以及后续如果要在现有代码库上继续推进，大致应该从哪里下手。

### 9.1 外信息完全不更新的独立动作

#### 目标

在 early-stop 命中后，不写新的外信息，直接保持当前外信息不变。

#### 当前现状

- 当前代码里不一定需要新增独立动作。
- 现有实现中，使用：
  - `EARLY_STOP_ACTION_MODE = 4`
  - `beta = 0`
- 最终写回值会等于：
  - `lin - lch`
- 这正好等于当前进入 decoder 时的旧外信息，因此从数值效果上已经可以实现“保持原外信息不变”。

#### 推荐改法

- 第一阶段不新增新动作，直接复用：

  - 动作 4
  - `beta = 0`
- 这样就能先完成算法实验和 BER 对比。
- 只有在后面确实需要更清晰的代码语义时，再考虑是否新增一个真正独立的：

  - `no-update` 动作模式

#### 推荐落点

- 当前阶段无需改动底层动作实现，主要是在实验配置层使用：

  - `EARLY_STOP_ACTION_MODE = 4`
  - `EARLY_STOP_ACTION_SIGN_BETA = 0`
- 如果后续决定为了代码语义单独拆一个动作，再考虑修改：

  - `include/newcode/params.hpp`
  - `src/rx/ofec/earlystop/row_early_stop_action.ipp`

#### 风险点

- 需要明确区分两层含义：

  - 数值效果上的“不更新”
  - 代码语义上的“独立 no-update 动作”
- 当前方案属于前者：

  - 从最终写回值看，与保持旧外信息一致
  - 但执行路径上仍然是复用现有 early-stop 动作 4

### 9.2 按 tile 混合多种 early-stop 判据组合

#### 目标

做到类似：

- 前几级 tile 用条件 1
- 中间级 tile 用条件 2
- 最后一级 tile 用条件 1 + 组绑定

#### 当前缺口

- 当前只有一个全局 `EARLY_STOP_CONDITION_MODE`
- 不能按 tile 单独配置不同判据

#### 推荐改法

- 新增按 tile 的条件模式列表，例如：
  - `EARLY_STOP_CONDITION_MODE_LIST`
- 如有需要，再继续扩：
  - `EARLY_STOP_ACTION_MODE_LIST`
  - `EARLY_STOP_BIND_GROUP_SIZE_LIST`

这样就能让每个 tile 独立选择：

- 用哪个 early-stop 判据
- 用哪个动作
- 是否启用组绑定

#### 推荐落点

- `include/newcode/params.hpp`
  - 新增 per-tile 配置列表
- `src/ofec_single/ofec_single_params.cpp`
  - 接线并校验长度
- `src/ofec_sweep/ofec_sweep_runner.cpp`
  - 接 sweep 入口
- `src/rx/ofec/detail/ofec_window_impl.ipp`
  - 像现在处理 `ALPHA_LIST`、`EARLY_STOP_ENABLE_LIST` 一样
  - 为每个 tile 选本轮生效的条件模式

#### 风险点

- 一旦条件、动作、绑定大小都允许按 tile 独立配置
- 顶层参数会变多
- `ofec_sweep` 的组合数也会明显增加
