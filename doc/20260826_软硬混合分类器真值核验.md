# HISO 分类与真实发送 BCH 码字一致性核验（2026-08-26）

## 目的

前面在 Level 5/6 的 HISO/SISO 消融中观察到：禁止 `TwoMain` 进入 HISO（mask 从 `0xF` 改为 `0x7`）后，固定 seed 的 Post-FEC error 从 159 降到 9。

这说明 `TwoMain-HISO` 是最高优先级嫌疑对象，但它本身还不能证明“每一个 TwoMain 改为 SISO 都必然变好”，因为禁用一个类别会同时改变同组内的资源竞争与其他类别的调度结果。

本核验把问题从完整 Level 5/6 调度中拆出，只检查下面的命题：

> 当前 `FriendS1S3WithS0Classifier` 给出的 `OneMain` / `TwoMain` 标签，是否等价于“当前硬判 word 相对本帧真实发送 eBCH(256,239) 码字恰有 1 / 2 个错误”；以及 HISO hard-finish 输出是否一定恢复到真实发送码字。

## 测试程序与复用模块

新增只读测试：[ofec_hybrid_class_truth_check.cpp](/home/zsr71/projects/newcode_level56_buffered_fifo/apps/ofec_hybrid_class_truth_check.cpp)。CMake target 为 `ofec_hybrid_class_truth_check`。

它不进入 oFEC 帧、Level 5/6、FIFO 或调度逻辑，因此不会改变正式解码流程。程序只复用现有工程模块：

- `bch::bch_255_239_encode()`：生成一个固定、非全零、且经合法性检查的真实发送 eBCH(256,239) word；
- `run_selected_hybrid_classifier_classify_only()`：当前实际使用的 `FriendS1S3WithS0Classifier` 分类入口；
- `run_selected_hybrid_classifier_hard_finish()`：与 HISO hard-finish 相同的分类与 `materialize_hard_finish_lout()` 路径；
- `bch::bch_255_239_decode_hiho_cw_255()`：仅在 `TwoMain` 时再次直接调用，用来确认它与 HISO executor 所得硬码字完全相同。

对这个已知发送码字，程序构造硬判输入 `received = tx XOR error_pattern`。每一个硬判 bit 变成正/负固定幅度的 `lin`。再比较：

```text
真实发送 tx
    -> 注入错误，得到 received / lin
    -> 当前分类器（OneMain / TwoMain / ...）
    -> 当前 HISO hard-finish
    -> 输出硬判 out
    -> 统计 HammingDistance(received, tx) 与 HammingDistance(out, tx)
```

本次扫描条件：错误 weight 为 0 到 32；weight 0 一个样本，其他每个 weight 使用 25,000 个确定性随机、无重复位置图样；随机种子固定为 `20260826`。同样的程序和种子应产生同样的反例。

运行命令：

```bash
cmake -S . -B build
cmake --build build -j2 --target ofec_hybrid_class_truth_check
build/ofec_hybrid_class_truth_check
```

## 分类结果与 BCH/HISO 输出错误数分布

测试程序现在对每个 `(输入相对 tx 的错误数, 分类结果)` 同时输出：该类样本数、是否进入 hard-finish，以及 `输出相对 tx 的错误数:样本数`。最后一列中的 `6:12331` 表示“12,331 个样本的 HISO/BCH 输出相对真实 tx 都有 6 个错误”。

以下列出从输入真实错误数 4 开始的关键部分：

| 输入相对 tx 的错误数 | 分类结果 | 样本数 | 进入 HISO hard-finish | HISO/BCH 输出相对 tx 的错误数分布 |
|---:|---|---:|---:|---|
| 4 | OneMainPlusParity | 90 | 90 | `6:90` |
| 4 | TwoMain | 12,331 | 12,331 | `6:12,331` |
| 4 | HardFail | 12,579 | 0 | — |
| 5 | ParityOnly | 1 | 1 | `6:1` |
| 5 | OneMain | 107 | 107 | `6:107` |
| 5 | HardFail | 24,892 | 0 | — |
| 6 | OneMainPlusParity | 103 | 103 | `6:5, 8:98` |
| 6 | TwoMain | 12,391 | 12,391 | `6:585, 8:11,806` |
| 6 | HardFail | 12,506 | 0 | — |
| 7 | OneMain | 85 | 85 | `6:3, 8:82` |
| 7 | HardFail | 24,915 | 0 | — |
| 8 | Clean | 1 | 1 | `8:1` |
| 8 | OneMainPlusParity | 110 | 110 | `8:5, 10:105` |
| 8 | TwoMain | 12,357 | 12,357 | `6:6, 8:770, 10:11,581` |
| 8 | HardFail | 12,532 | 0 | — |

这张表把两件事分开了：

- `TwoMain`、`OneMain` 等是当前 hard word 的 syndrome 分类，而不是 tx-relative 的错误数标签；
- 对真实错误数超过 BCH 半径的样本，hard-finish 可以输出一个 BCH 合法 word，但其相对 tx 的错误数经常是 6、8、10……，并非零。

特别地，输入恰有 4 个真实错误时，被分类为 `TwoMain` 的 12,331 个样本全部输出为 6 错；这正是“硬纠成功/合法”与“恢复本帧发送码字”分离的最直观统计证据。

## 低错误数时的基线结果

| 输入相对 tx 的错误数 | 分类结果 | 样本数 | hard-finish 成功数 | 输出等于 tx | 输出不等于 tx |
|---:|---|---:|---:|---:|---:|
| 0 | Clean | 1 | 1 | 1 | 0 |
| 1 | ParityOnly | 93 | 93 | 93 | 0 |
| 1 | OneMain | 24,907 | 24,907 | 24,907 | 0 |
| 2 | OneMainPlusParity | 181 | 181 | 181 | 0 |
| 2 | TwoMain | 24,819 | 24,819 | 24,819 | 0 |
| 3 | HardFail | 25,000 | 0 | 0 | 0 |

这部分确认了正常纠错半径内的预期：

- 真正的单主体错误会被分类为 `OneMain` 并恢复到 tx；整体 parity 位单错走 `ParityOnly`；
- 真正的两个主体错误会被分类为 `TwoMain`，现有 BCH 模块报告 `corrected_errors = 2`，并恢复到 tx；
- 输入恰有三错误时，本扫描样本均为 `HardFail`，不会进入 HISO hard-finish。

因此，问题不在“真实 1/2 错时的基本 BCH 动作”。

## 已确认的 TwoMain 反例

来自同一次测试的一个具体输入：

| 项目 | 数值 |
|---|---|
| 输入相对真实 tx 的错误数 | 4 |
| 输入错误位置 | `[1,15,18,118]` |
| 当前分类器输出 | `TwoMain` |
| `bch_255_239_decode_hiho_cw_255()` 返回 | 成功，`corrected_errors = 2` |
| HISO hard-finish 输出相对 tx 的错误数 | 6 |
| HISO / BCH 输出错误位置 | `[1,15,18,46,118,208]` |

这里 BCH 例程并没有失败：它找到了一个使 BCH syndrome 为零的两位修改，并输出了一个合法 eBCH word。但该 word 不是本帧发送的 `tx`。从真实 tx 视角看，输入有 4 错，输出有 6 错。

因此：

```text
TwoMain 分类 / BCH reported corrected_errors=2
不等价于
当前硬判相对本帧真实发送 BCH 码字恰好有 2 错，或输出一定等于 tx。
```

这是 BCH 纠错半径以外的 syndrome 混叠（miscorrection）现象；分类器和 BCH 硬解码器都不知道该帧真实发送的码字，只能从当前 hard word 的 syndrome 出发。

## 已确认的 OneMain 反例

同一程序也已经否定“只要判为 OneMain，输出就一定与原始发送比特一致”的假设。

| 项目 | 数值 |
|---|---|
| 输入相对真实 tx 的错误数 | 5 |
| 输入错误位置 | `[29,40,54,177,202]` |
| 当前分类器输出 | `OneMain` |
| OneMain 动作 | 由 `S1` 定位并翻转位置 63 |
| HISO hard-finish 输出相对 tx 的错误数 | 6 |
| HISO 输出错误位置 | `[29,40,54,63,177,202]` |

所以：

```text
“被分类为 OneMain”只表示该 received word 的 S1/S3/S0 组合符合当前 OneMain 判据；
它不访问真实发送 tx，也不能从逻辑上保证它相对 tx 真的只错 1 位。
```

不过，两类反例在风险形态上仍有区别：本次扫描中 `TwoMain` 从输入真实 4 错开始就大量命中并进入 BCH t=2 路径；`OneMain` 的第一个命中反例出现在真实 5 错。这并不证明 OneMain 永远安全，只说明在本扫描范围中 TwoMain 更早、更频繁地承担超过 t=2 的错误图样，因此它与当前 BER 劣化的关联更值得优先追踪。

## 对先前 HISO/SISO 实验的含义

可以确认的结论如下。

1. `0xF -> 0x7` 的 BER 明显改善，足以把 `TwoMain-HISO` 列为最高优先级问题；但由于调度会随 mask 改变，尚不能说成“仅仅把同一批 TwoMain 改走 SISO 的唯一因果结果”。
2. HISO 分支确实可能把一个超过 BCH 纠错半径的 hard word 硬完成为**错误但合法**的 BCH codeword，并写回一个高置信度硬外信息。该动作会替代原本可能继续利用软信息的 SISO 路径，因而具备造成最终 BER 恶化的机制。
3. OneMain 不是绝对安全例外。真实单错时它正确；但在高错误图样的 syndrome 混叠下，也可能将错误合法化。因此后续不能只检查 `TwoMain` 的分类名，而应在完整帧 trace 中同时记录“分类时 lin 相对 tx 的真实 hard-error weight”和“hard-finish 输出相对 tx 的错误数”。
4. 本文只验证硬判分类/BCH/HISO executor 的语义，不替代完整 Level 5/6 BER 对照。下一步仍应做同 seed 的 pair-run trace：让同一 row 一次走 HISO、一次走 SISO，追踪该 row 的 `lin`、分类、HISO 输出、SISO 输出、实际写回位置及其后续传播。

## 完整帧中：错误合法 HISO 输出与最终 Post-FEC 错误位置的直接关联

为回答“最终解码完成后的错误比特位置是否与错误合法硬输出位置一致/有关联”，在 equivalence observation 中新增了**只读**字段：

- `hiso_corrected_hard_error_positions`：BCH hard word 内相对真实发送 word 的错误 bit 位置；
- `hiso_corrected_error_info_positions`：上述错误 bit 按现有 `writeback_tile()` 映射后，能够落在最终 `rx_info_from_bit_llr()` 信息流中的位置；
- `hiso_error_info_positions_in_final_post_fec_count`：这些信息位位置中，最终仍是 Post-FEC 错误的位置数。

这不是另写一套映射：观测函数使用 `writeback_tile()` 中已经在用的 Level 5/6 `k -> (global row, global col)` 公式；它不参与调度、HISO、SISO、写回或 BER 判定。

完整帧条件保持先前消融的全类别基线不变：

```text
Eb/N0 = 3.065 dB
bitgen/channel seed = 20260319 / 3182026
FIFO ON, R_buf = 16000, drain ON, forced eviction = 0
8 HISO + 8 SISO, Group4 = 8 entry
HISO class mask = 0xF
```

运行复现结果：`Post-FEC = 159 / 58,608,000 = 2.71294e-6`，与先前该条件的 159 errors 完全一致。

| 项目 | 数量 | 含义 |
|---|---:|---|
| 错误但合法的 HISO hard-output code | 343 | `hiso_corrected_hard_bit_errors_vs_expected > 0` |
| 这些 code 中 TwoMain / OneMain / OneMainPlusParity | 334 / 7 / 2 | TwoMain 占绝大多数 |
| BCH hard-output 相对 tx 的错误 bit 总数 | 2,162 | 包含 BCH word 内所有 256 bit，且允许不同 code 重复覆盖同一物理位置 |
| 可映射到最终信息流的错误写回记录 | 1,883 | BCH parity / overall 等非信息位置不会进入最终 BER 流 |
| 发生至少一次直接重合的错误 HISO code | 43 | 41 TwoMain、1 OneMain、1 OneMainPlusParity |
| 直接重合记录数 | 115 | 同一最终错误位可被多个 HISO code 的错误写回命中 |
| 159 个最终错误中，被至少一个错误 HISO 输出直接命中的不同位置数 | **73** | 占最终错误位的 **45.9%** |
| 未被上述“直接写入同一信息位置”覆盖的最终错误位 | 86 | 不能仅凭此表判断为与 HISO 无关，仍可能是传播结果或其他原因 |

一个可复核的直接样例：

```text
B2589 / Level 5 / code 24 / global row 83543
class = TwoMain
HISO 输入相对真实 BCH word = 6 错
BCH/HISO 输出相对真实 BCH word = 8 错

错误输出写入的信息流位置之一 = 9001663
9001663 也在完整帧最终 Post-FEC error position 集合中
```

因此可以确认：错误合法 HISO 输出与最终 BER 错误并非只有“统计相关”，在当前完整帧中至少有 73 个最终错误位能追溯到某一次错误 HISO word 对同一信息位置的直接错误写回；其中 72 个最终错误位至少有一个 TwoMain 来源。

但也必须保留边界：这仍不是“73 个 bit 的唯一因果证明”。同一位置可能在后续被其他 tile/code 再写入；其余 86 个最终错误也可能来自错误 HISO 输出沿后续约束传播、来自 SISO/早停/其他解码行为，或多个因素组合。若要证明每个最终 bit 的完整因果链，下一步需要针对这 73 个直接命中位置及其附近的 86 个未命中位置，记录后续每次读写和最终判决来源。
