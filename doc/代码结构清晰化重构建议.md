# 代码结构清晰化重构建议

本文讨论的不是“为了功能正确性必须做什么”，而是：

> 如果希望后续代码和文档都更容易理解、更容易维护，当前仓库最值得优先做哪些结构重构。

这份文档的判断基于当前仓库的实际形态：

- 主干架构已经存在，并不属于无序堆代码。
- 但 `oFEC + hybrid + early-stop + MUX + sweep` 的复杂性已经开始外溢到参数组织、状态语义和目录结构里。
- 目前很多内容“可以讲清楚”，但需要依赖较多背景知识、交叉看多份文档、以及在 `detail/*.ipp` 中来回跳转。

因此，本文的目标不是推翻现有结构，而是找出：

1. 哪些重构最能提高“读代码时的一眼清晰度”。
2. 哪些重构最能降低文档编写和同步成本。
3. 哪些重构做完以后，后续新增策略不容易继续把结构拖乱。

## 1. 当前结构的总体评价

当前仓库的结构可以概括为：

```text
apps
  -> single / sweep runner
  -> pipeline
  -> decoder registry / decoder variant
  -> ofec window / tile / row core
  -> common tx/channel/rx/utils
```

这条主链并不混乱，主问题也不是“找不到入口”，而是下面 4 类结构压力已经比较明显：

- 参数中心过大，`Params` 承担了过多领域职责。
- tile 级主流程虽然被拆成多个 `.ipp` 文件，但状态语义和阶段边界仍然偏密。
- 新旧路径、实验路径、兼容路径并存，导致“主路径”需要额外解释。
- 文档很多，但“哪份文档描述的是当前生效代码”不够一眼明确。

因此，这份文档给出的建议是：

- 不做大拆大建。
- 优先做“能显著提高清晰度、但不强迫大面积改行为”的重构。
- 优先收敛“命名、边界、状态、配置”这四类复杂度。

## 2. 最值得优先做的 5 个重构点

### 2.1 拆分 `Params`：按领域分组，而不是继续堆字段

当前 [params.hpp](/home/zsr71/projects/newcode/include/newcode/params.hpp:1) 已经同时承载：

- 编码结构参数
- 仿真运行参数
- tile/window 几何参数
- LLR 量化参数
- Chase 参数
- early-stop 参数
- MUX 参数
- hybrid 参数
- debug trace 参数

这会带来几个问题：

- 读者很难迅速判断“当前改动影响的是哪个子系统”。
- 新增功能时，最省事的路径总是“继续往 `Params` 里塞字段”。
- 文档在描述某条功能链路时，往往必须跳着列参数，缺少天然分组。

建议把 `Params` 拆成“顶层聚合 + 子配置结构”：

```cpp
struct GeometryConfig { ... };
struct LlrConfig { ... };
struct ChaseConfig { ... };
struct EarlyStopConfig { ... };
struct MuxConfig { ... };
struct HybridConfig { ... };
struct DebugTraceConfig { ... };

struct Params {
  GeometryConfig geometry;
  LlrConfig llr;
  ChaseConfig chase;
  EarlyStopConfig early_stop;
  MuxConfig mux;
  HybridConfig hybrid;
  DebugTraceConfig debug_trace;
  ...
};
```

第一阶段不一定要一次改完全部调用点。可以先做两步：

1. 先在 `Params` 内部新增逻辑分组注释和 type alias，保持行为不变。
2. 再把最重的几组字段逐步抽成子结构，优先从 `Hybrid`、`Mux`、`EarlyStop` 开始。

预期收益：

- 参数语义会立刻清楚很多。
- 文档可以天然按 config 结构展开。
- 以后做 CLI、配置文件、sweep 参数映射时更容易自动组织。

### 2.2 给 tile 主流程建立显式阶段边界，减少 `.ipp` 之间的“隐式跳转感”

���前 tile 主流程已经拆成：

- `prepare_tile_inputs`
- `detect_tile_early_stop`
- `build_tile_dispatch_plan`
- `decode_tile_with_plan`
- `writeback_tile`

这是好事，说明主流程不是无结构的。但目前的问题是：

- 真实状态转移分散在多个 `.ipp` 内。
- 阅读者经常要在 `dispatch / decode / impl` 三层来回跳。
- “某个阶段的输入输出是什么”更多靠脑补，而不是靠结构显式表达。

建议引入更明确的阶段数据对象，把“流程步骤”从“实现细节文件”里再抬高一层。

例如：

```cpp
struct TileInputs { ... };
struct TileEarlyStopView { ... };
struct TileDispatchPlan { ... };
struct TileDecodedOutputs { ... };
```

并给每个阶段统一函数签名：

```cpp
TileInputs prepare_tile_inputs(...);
TileEarlyStopView evaluate_tile_early_stop(const TileInputs&, ...);
TileDispatchPlan build_tile_dispatch_plan(const TileInputs&, const TileEarlyStopView&, ...);
TileDecodedOutputs decode_tile_with_plan(const TileInputs&, const TileDispatchPlan&, ...);
void writeback_tile(...);
```

重点不是“再多加几层类”，而是让每一阶段回答清楚：

- 输入是什么。
- 输出是什么。
- 这一层允许改哪些状态。

这样做以后，即使 `.ipp` 还保留，文档也能直接画出稳定的阶段图，而不用解释内部实现文件之间的关系。

### 2.3 收敛 row 状态语义：明确区分“调度状态”和“算法分类”

当前系统里同时存在几组语义：

- `SoftDecode / HardFinish / EarlyStopAction / Unscheduled`
- `NeedSiso / EarlyStopped / Unscheduled`
- `Clean / OneMain / TwoMain / HardFail`

这些概念各自都合理，但混在一起时，读者很容易困惑：

- 这是算法判断结果，还是调度状态？
- 这是本轮输出动作，还是 MUX 前的候选身份？
- `HardFail` 是失败后结束，还是失败后继续 soft path？

建议从类型上把这几类语义显式拆开：

```cpp
enum class HybridClassification { Clean, ParityOnly, OneMain, OneMainPlusParity, TwoMain, HardFail, ... };
enum class RowDispatchTag { SoftDecode, HardFinish, EarlyStopAction, Unscheduled };
enum class SoftSchedulingState { NeedSiso, Scheduled, Unscheduled };
```

同时在代码约束上明确：

- `HybridClassification` 只表达 classifier 判断。
- `RowDispatchTag` 只表达本轮行最终怎么处理。
- `SoftSchedulingState` 只表达 soft path 内部调度结果。

如果再进一步，可以把这些字段分别放进不同结构层，而不是堆在同一个 entry 里。

预期收益：

- 读 `run_hybrid_prepass`、`run_mux_on_soft_candidates`、`decode_tile_with_plan` 时更不容易串义。
- 文档里可以明确地说“分类结果不等于调度结果”。
- 后续继续加 hybrid 策略时，不容易再发明新的“半算法半调度”状态。

### 2.4 固化“当前主路径”，把 legacy / regression / experiment 明确标注成旁路

当前代码中并存这些路径：

- legacy hard decode
- fast classifier 路径
- hybrid on/off
- disabled match legacy 回归路径
- 不同 backfill 模式

这些路径本身不是问题，问题在于：

- 它们现在更像“同一层里同时活着”
- 而不是“主路径 + 旁路保护”

建议在代码和文档上都明确一个原则：

> 当前仓库只应该有一条默认解释路径，其他路径都当作兼容、实验或校验路径来命名和摆放。

具体可以做：

- 在 `ofec_tile_impl` 顶部补一小段主路径注释。
- 在 `HYBRID_VERIFY_DISABLED_MATCH_LEGACY` 这种逻辑周围统一加“regression-only”标识。
- 在 summary / CLI 帮助里把默认模式和实验模式区分开。
- 在文档中增加“当前主链路图”和“兼容旁路表”。

如果后面再做一步目录整理，还可以考虑把明显的兼容或回归逻辑集中到更明确的位置，例如：

- `detail/legacy_*`
- `detail/regression_*`

这样做不会改变算法行为，但会极大降低“新人不知道哪条才是主线”的认知成本。

### 2.5 给文档建立“当前生效文档索引”，避免方案文档与现状文档并列

当前 `doc/` 目录信息量很大，但也有一个典型问题：

- 方案文档很多
- 对比文档很多
- 落地文档也有
- 但“当前有效说明”需要靠经验判断

例如同一主题下，可能同时存在：

- 初始方案
- 方案总结
- 当前代码落地设计
- 某个特定分支策略设计

这在研发推进期很正常，但长期会增加文档阅读成本。

建议在 `doc/` 增加一个轻量级索引，例如：

- `doc/CURRENT_ARCHITECTURE_GUIDE.md`
- 或者直接增强 [doc/README.md](/home/zsr71/projects/newcode/doc/README.md:1)

内容不需要长，重点是给出三类清单：

1. 当前主架构说明看哪几篇。
2. 历史方案 / 对比方案看哪几篇。
3. 实验或专题文档看哪几篇。

例如：

```text
当前有效：
- 仓库结构说明
- oFEC 软硬混合当前代码落地设计
- 代码结构清晰化重构建议

历史演进：
- 软硬混合方案
- 软硬混合方案总结

专题设计：
- hybrid SISO backfill priority
- friend s1s3 with s0 classifier
```

这项工作本身不改代码，但会显著提高“文档入口清晰度”，而且能减少后续重复写总览文档的次数。

## 3. 如果只能先做 3 件事，优先级怎么排

如果只能先做最关键的 3 项，我建议顺序如下。

### 第一优先级：拆分 `Params`

这是最值得尽快做的，因为：

- 改动面虽然广，但大多是机械重构。
- 一旦完成，后续所有功能和文档都会更清楚。
- 它能直接抑制“继续往全局参数里堆字段”的惯性。

建议第一波先拆：

- `HybridConfig`
- `MuxConfig`
- `EarlyStopConfig`

因为这三块是当前复杂度最高、最容易互相影响的区域。

### 第二优先级：显式化 tile 阶段接口

这是主流程可读性的核心。  
如果把 tile 主链上的阶段输入输出整理清楚，后面不管是做文档、调试、加 trace，还是给别人讲逻辑，都会省很多力气。

这一步完成后，系统最复杂的那段逻辑会从“很多细节都要口头补充”变成“流程结构本身已经在说话”。

### 第三优先级：状态语义拆分

这一步会明显改善 hybrid / MUX / early-stop 的理解成本。

尤其当项目继续增加：

- 新 classifier
- 新 backfill 规则
- 新 unscheduled 统计
- 新 hard-finish 保护

如果状态语义不先收敛，后面每加一个策略，文档解释成本都会继续上升。

## 4. 暂时不建议优先做的重构

有些方向也有价值，但我不建议现在优先做。

### 4.1 不建议先全面改目录树

例如把 `src/rx/ofec/detail`、`plain`、`mux`、`hybrid` 全部重排。  
这种改动影响面太大，而且如果上面的边界和语义没先理顺，目录重排只会把复杂度换个位置继续存在。

### 4.2 不建议先追求“所有文档合并成一篇”

当前文档多，不是因为文档太差，而是因为项目演进快。  
真正需要先解决的是“索引和有效性标识”，而不是强行把所有文档压缩成一篇超长总文档。

### 4.3 不建议先抽象过度的统一策略框架

比如把 classifier、backfill、hard confirm、reliability gating 一次性做成特别通用的插件框架。  
当前还没有必要走到那一步，过早抽象可能反而让结构更重。

更合适的做法是先把现有三四套策略收敛清楚，再看哪些抽象是真正稳定的。

## 5. 一个建议的落地顺序

如果按低风险、易落地的顺序推进，我建议：

1. 增强 `doc/README.md`，补“当前有效文档索引”。
2. 给 tile 主路径补一份单独的 current flow 文档或注释图。
3. 拆 `Params` 中的 `Hybrid / Mux / EarlyStop` 子配置。
4. 收敛 row 状态命名和类型边界。
5. 再考虑是否需要继续整理 `detail/*.ipp` 的目录和命名。

这个顺序的好处是：

- 第 1 步和第 2 步能立即改善阅读体验。
- 第 3 步和第 4 步能逐步改善代码结构。
- 第 5 步放到后面做，避免一开始就做高风险、大范围文件移动。

## 6. 总结

当前仓库的结构问题，不在于“完全没有设计”，而在于：

- 设计已经形成，但复杂度开始压到代码组织和文档组织上。

如果希望结构清晰度从“可以讲清楚”提升到“看代码就能比较快看清楚”，最值得优先做的不是大改算法，而是：

- 拆参数
- 明确阶段边界
- 拆状态语义
- 固化主路径
- 给文档加有效索引

这几件事的共同作用是：

- 让代码更像在表达结构，而不是只表达逻辑。
- 让文档更像在解释系统，而不是在替代码补上下文。
- 让后续新增策略时，不会继续把复杂度无上限地推到 `Params`、`detail/*.ipp` 和零散文档里。
