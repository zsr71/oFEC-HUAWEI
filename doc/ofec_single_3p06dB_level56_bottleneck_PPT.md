## 第 2 页：问题背景与分析目标

### 页面标题

**问题背景与分析目标**

### 页面内容

当前五六级共享方案的基本流程为：

1. Level 5 和 Level 6 共输入 64 个 code。
2. 64 个 code 固定划分为 16 个组，每组 4 个 code。
3. 先执行 EarlyStop 判断和混合分类。
4. 统计每组的 `remaining_unscheduled_count`。
5. 最多为 8 个 group entry 分配共享 SISO/HISO 资源。
6. 未获得资源的非 EarlyStop code 保持不变。

本次需要回答四个问题：

- 3.06 dB 下的误码是否由原始信道 BER 直接决定？
- 未调度 code 主要来自哪个调度分支？
- `K>8` 是否在时间上集中出现，并与未调度高峰对应？
- 当前瓶颈是排序问题、资源碎片，还是资源总容量不足？

术语定义：

- `K`：一次 Level 5/6 共享调用中，16 个组里初始 `remaining_unscheduled_count` 非零的组数，即当前存在待调度 code 的非空组数。
- `GT`：`Greater Than` 的缩写，表示“大于”；本文中的 GT 分支就是 `K>8` 分支。
- `LT`：`Less Than` 的缩写，表示“小于”；本文中的 LT 分支就是 `K<8` 分支。
- `EQ`：`Equal To` 的缩写，表示“等于”；本文中的 EQ 分支就是 `K=8` 分支。

本文后续统一使用“`K>8（GT）分支`”或简称“GT 分支”。不使用“GT>8”，因为 GT 本身已经包含“大于”的含义。

### 建议图示

```text
64 code
   -> EarlyStop + Hybrid 分类
   -> 16组负载统计
   -> 最多8个group entry
   -> SISO/HISO译码或Unscheduled
```

### 页面结论

分析重点是从最终 BER 向前追溯，判断错误压力是否集中在共享调度的过载阶段。

### 讲解词

这里的 K 表示 16 个组中初始 `remaining_unscheduled_count` 非零的组数。由于系统最多只有 8 个 group entry，因此 K 是否超过 8 是判断共享调度是否进入组级过载状态的关键指标。


时间定义：

- 本文将 `invocation` 作为共享译码调用的时间顺序。

### 讲解词

## 第 7 页：误码非线性放大机制

### 页面标题

**从信道小幅变化到译码结果大幅变化**

### 页面内容

建议将以下内容绘制为纵向流程图：

```text
Eb/N0小幅变化
        ↓
输入LLR和硬判错误小幅变化
        ↓
EarlyStop命中与Hybrid分类结果变化
        ↓
16个组的remaining_unscheduled_count变化
        ↓
非空组数K跨越8组门限
        ↓
8个group entry连续饱和
        ↓
大量code保持Unscheduled
        ↓
重叠窗口中的困难状态持续
        ↓
Post-FEC错误发生非线性变化
```

页面右侧给出门限说明：

- `K <= 8`：所有初始非空组原则上都能获得第一次 entry。
- `K > 8`：至少 `K - 8` 个组第一次就无法进入。
- 每个 entry 最多只有一个 SISO 输出和一个 HISO 输出。

### 页面结论

3.06 dB 的高误码应理解为“信道条件触发调度负载跨越资源门限后的放大结果”，而不是简单的信道 BER 偏高。

### 讲解词

这里的关键门限不是某个单独 code 是否难解，而是同一时刻有多少组同时需要资源。一旦 K 超过 8，系统由可覆盖状态进入必然存在组级竞争的状态。

## 第 9 页：K>8 分支的资源总账

### 页面标题

**K>8（GT，Greater Than 8）分支首先面临绝对容量不足**

### 页面内容

1,008 次 K>8 调用的累计资源账：

| 指标 | 数量 |
|---|---:|
| 总待调度需求 | 20,712 code |
| Group entry | 8,064 |
| SISO 输出 | 8,064 |
| HISO 输出 | 5,721 |
| 实际译码输出 | 13,785 |
| 最终未调度 | 6,927 |

折算到每次 GT 调用：

```text
平均需求       = 20.55 code/次
理论最大输出   = 16.00 code/次
实际平均输出   = 13.68 code/次
平均未调度     =  6.87 code/次
```

GT 未调度分解：

| 原因 | 数量 | 占 GT 未调度 |
|---|---:|---:|
| 需求超过 16-output 理论上限 | 4,584 | 66.2% |
| HISO 未填满造成的额外损失 | 2,343 | 33.8% |
| 合计 | 6,927 | 100% |

### 页面结论

GT 未调度中至少 66.2% 属于绝对容量缺口，即使调度和 HISO 填充达到理想状态也无法消除；因此单独优化排序不能根治问题。

### 讲解词

8 个 entry 最多提供 8 个 SISO 和 8 个 HISO，总共 16 个输出。但 GT 平均需求为 20.55 个，所以容量矛盾在数学上已经成立。剩余三分之一才是可以通过提高资源利用率争取改善的部分。

## 第 10 页：未调度发生在组间还是组内

### 页面标题

**组间准入不足与组内吞吐不足同时存在**

### 页面内容

GT 分支的 6,927 个未调度 code 按位置分解：

| 未调度位置 | 数量 | 占比 |
|---|---:|---:|
| 位于未被选中的组 | 3,621 | 52.3% |
| 位于已经入选的重载组 | 3,306 | 47.7% |

机制说明：

```text
组间问题：K>8
  -> 只有8个组能够获得entry
  -> 其他非空组本轮完全没有SISO/HISO

组内问题：入选组可能有3到4个待调度code
  -> 一个entry最多输出1个SISO和1个HISO
  -> 第3、第4个code仍然未调度

GT第一轮已经占满8个entry
  -> 未选中组和重载组都无法在后续轮次再次进入
```

### 建议图示

画两个四行组：一个组完全未入选；另一个组入选但只有两个 code 获得输出，剩余两个标为 Unscheduled。

### 页面结论

当前 GT 瓶颈不是单一的“第九组进不来”，而是约一半来自组级准入不足，另一半来自重载组一次 entry 的两路输出上限。

### 讲解词

当前按组负载排序会优先选择重载组，这有利于提高单个 entry 的产出，但当重载组含 3 至 4 个 code 时，它仍然只能处理两个。GT 又没有剩余 entry 让这个组再次进入。

## 第 11 页：HISO 利用率与固定分组碎片

### 页面标题

**固定四行组造成 HISO 资源碎片**

### 页面内容

GT 分支资源利用情况：

```text
已使用group entry       = 8,064
HISO实际输出            = 5,721
entry内空闲HISO         = 2,343
GT HISO利用率           = 70.95%
GT未调度HisoOrSiso      = 5,769
GT未调度SisoOnly        = 1,158
```

资源碎片形成方式：

```text
组A进入一个entry
  SISO有输出
  HISO因组内没有剩余合格code而空闲

组B未获得entry
  仍有HisoOrSiso code等待资源

当前规则不允许组B借用组A的空闲HISO
```

理想化上限：

- 如果允许完全跨组 HISO backfill，理论最多额外处理 1,705 个 code。
- GT 未调度最多可从 6,927 降至约 5,222。
- 这仍不能消除由总容量造成的基本缺口。

### 页面结论

跨组 HISO backfill 有明确改善空间，但它解决的是资源碎片，不是总容量不足；其潜在改善上限小于 GT 总未调度的四分之一。

### 讲解词

不能把全部 2,343 个空闲 HISO 都直接视为可回收，因为同一次调用中不一定都有可匹配的灵活 code。按 invocation 做数量匹配后，较合理的理论上限是 1,705。

## 第 12 页：Level 5 与 Level 6 的资源分配差异

### 页面标题

**Level5First 将过载压力主要转移给 Level 6**

### 页面内容

| Level | 非 EarlyStop 需求 | HISO | SISO | 未调度 | 未调度率 |
|---|---:|---:|---:|---:|---:|
| Level 5 | 66,552 | 17,885 | 43,917 | 4,750 | 7.14% |
| Level 6 | 7,221 | 1,003 | 2,851 | 3,367 | 46.63% |

需求与未调度份额：

```text
Level 6需求占比       = 9.79%
Level 6未调度占比     = 41.48%
Level 6未调度发生在GT = 3,358 / 3,367 = 99.73%
```

按固定组观察：

- Level 5：G1-G8，未调度率为 6.24% 至 7.90%。
- Level 6：G9-G16，未调度率为 37.97% 至 52.74%。

原因：

- 组负载较高者优先；
- 负载相同时，组号较小者优先；
- G1-G8 属于 Level 5，G9-G16 属于 Level 6。

### 页面结论

Level5First 不是总容量缺口的根源，但它显著决定了资源不足由哪一级承担，使 Level 6 在 GT 过载阶段出现严重资源饥饿。

### 讲解词

将优先级改成更公平的规则，可以显著改善 Level 6 的未调度率，但如果资源数量不变，总体未调度未必同比下降。公平性优化与吞吐能力优化应分开评价。

## 第 14 页：当前证据能证明什么

### 页面标题

## 第 15 页：最终结论与优化优先级

### 页面标题

**最终结论与下一步工作**

### 页面内容

建议将以下结论放在页面中央：

> 3.06 dB 工作点的高误码主要表现为译码瀑布区内的共享调度过载。K>8 只占 11.93% 的调用，却产生 85.34% 的未调度 code。GT 时段平均有 20.55 个 code 竞争最多 16 个译码输出，因此资源总容量是首要瓶颈；固定四行分组进一步造成 HISO 碎片，Level5First 则将资源不足主要转移给 Level 6。

优化优先级：

1. 评估增加 group entry 或总输出容量，建立资源数量与 BER 的关系曲线。
2. 研究 GT 下重载组重复进入或更灵活的 entry 分配方式。
3. 测试受控的跨组 HISO backfill，回收组内空闲 HISO。
4. 引入 Level 5/6 交替、aging 或配额机制，改善 Level 6 公平性。
5. 增加 code 级译码前后正确性监测，完成最终误码来源分账。
6. 使用多个随机种子重复 3.05/3.06 dB 仿真，确认结论的统计稳定性。

### 页面结论

当前方案的主要矛盾不是“组排序得是否足够精细”，而是过载簇中平均 20.55 个需求竞争最多 16 个输出。排序与公平性只能优化有限资源的分配，总吞吐改善仍需要资源结构或 entry 使用方式发生变化。

### 讲解词

下一步建议把实验分成三类：第一类改变总容量，判断理论上限；第二类保持容量不变、提高 HISO 利用率；第三类保持吞吐不变、调整 Level 5/6 公平性。三类实验应分别报告总体 BER、两级未调度率、GT 次数和资源利用率，避免把吞吐改善与公平性改善混为一谈。
