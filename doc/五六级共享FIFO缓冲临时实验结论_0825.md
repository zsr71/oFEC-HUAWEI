# 五六级共享 Buffered FIFO：2026-08-25 临时实验结论

> 本文记录截至 2026-08-25 已实际运行并核对完成的实验结论。已验证表示已有运行日志、调度统计或错误位置文件支持；对 HISO 导致 BER 变差的根本因果，本文只记录已经证实的动作层结论，不将尚未逐 code 定位的解释写成定论。

## 1. 本轮目标与统一条件

本轮验证两个问题：

1. 当五、六级共享的单时刻资源有限、一个 64-code batch 出现 non-EarlyStop code burst 时，Buffered FIFO 是否能在后续时刻补解 pending code，而不丢失译码机会；
2. 在无 forced eviction、帧尾 FIFO 也完成服务时，分时 FIFO 服务能否达到即时充足资源方案的最终 BER；加入 HISO 后又会产生什么影响。

除特别说明外，长帧实验均使用：

| 项目 | 固定条件 |
|---|---|
| Eb/N0 | 3.065 dB |
| 总信息 bit | 60,014,592 |
| bitgen / channel seed | 20260319 / 3182026 |
| 量化 | qfloat<6> |
| 五六级共享 | ON |
| EarlyStop、Hybrid、Chase、Level 1--4、信道输入 | 相同 |

因此各组差异来自五六级资源容量、调度和 FIFO 行为，而不是随机输入不同。

## 2. BER 统计口径与 R_buf 无关

当前 ofec_single 的 Post-FEC BER 固定裁掉前 4 个 window 和后 2 个 window。

| 项目 | 数值 |
|---|---:|
| 总信息 bit | 60,014,592 |
| 固定裁剪 bit | 1,406,592 = 6 × 234,432 |
| 实际比较 bit | 58,608,000 |

### 已验证结论

R_buf 不参与 BER 裁剪长度的计算。不同缓冲区长度下的 BER 使用同一段 58,608,000 bit 有效区间；不能把 BER 差异解释成“长 buffer 多裁掉了帧尾数据”。

## 3. frame-end drain 的含义

frame-end drain=ON 是离线全帧 BER 验证开关。最后一个正常 batch 到达后：

    不再引入新的 batch
    不再执行 Level 1--4 的新窗口处理
    只继续服务已经在 Level 5/6 FIFO 中的 batch
    直到 FIFO 为空

其作用是让帧尾已经进入 FIFO、但仍 pending 的 code 获得后续服务机会。

### 已验证结论与边界

- drain 不改变帧内正常的 FIFO、Group4、HISO/SISO 调度；
- drain 不属于在线固定吞吐方案的定义；
- drain 仅避免“仿真先结束、尾部 pending 尚未补解”污染最终 BER 对比。

## 4. 长缓冲区已消除本轮 forced eviction

在 R_buf=16000、frame-end drain=ON、共 16,897 个 arrival batch 的两组长帧 FIFO 实验中：

| FIFO 配置 | FIFO 清空时刻 t | 最大 FIFO 深度 | completed | forced eviction |
|---|---:|---:|---:|---:|
| 0 HISO / 8 SISO | 22,971 | 4,476 | 16,897 | 0 |
| 8 HISO / 8 SISO | 19,109 | 1,888 | 16,897 | 0 |

### 已验证结论

1. 两组所有 batch 都完成；
2. 没有 batch 因 FIFO 容量到顶被强制顶出；
3. 两组 BER 的差异不能归因于 forced eviction 或帧尾未完成。

该结论只覆盖当前样本、当前 SNR 和 R_buf=16000，不代表短 buffer 或所有 SNR 都没有 forced eviction。

## 5. shared 容量语义：SISO=32 是 64-code 共用总容量

当前五六级 shared 路径中，LEVEL56_SHARED_SISO_ACTIVE=N 表示一个合并的 64-code batch 总共可分配 N 个 SISO；并不是 Level 5 有 N 个、Level 6 再有 N 个。

### 5.1 0/32 是受限参考，不能作为充足资源基线

已运行：

    FIFO OFF
    HISO / SISO = 0 / 32
    GlobalPriority

结果：

    Post-FEC = 36 / 58,608,000
    BER      = 6.14251e-7

burst batch B2590 有 35 个 non-EarlyStop code，但只得到：

    29 × EarlyStopAction
    32 × SisoDecode
     3 × Unscheduled

未被调度的三个 code：

    Level 5: code 21、code 32
    Level 6: code 41

所以 0/32 只说明共享总 SISO 资源不足时会漏掉 code；它不能代表“五六级各 32 个 SISO”，也不能作为所有 non-EarlyStop 都应完成的基线。

### 5.2 0/64 是正确的纯 SISO 充足资源参考

改为：

    FIFO OFF
    HISO / SISO = 0 / 64
    GlobalPriority

同一 B2590 的最终动作为：

    29 × EarlyStopAction
    35 × SisoDecode
     0 × Unscheduled

全帧统计也确认 Level 5、Level 6 的 Unscheduled 都为 0。

## 6. 最重要结论：纯 SISO FIFO 与即时 64-SISO 完全一致

### 6.1 对比配置

| 角色 | FIFO | HISO / SISO | 调度 | R_buf | drain | 含义 |
|---|---:|---:|---|---:|---:|---|
| 即时充足资源参考 | OFF | 0 / 64 | GlobalPriority | — | — | 同 batch 内所有 non-EarlyStop 立即 SISO |
| Buffered FIFO | ON | 0 / 8 | Group4 LoadSorted Multiround | 16,000 | ON | 每次最多 8 个 SISO；其他 code pending 后补解 |

### 6.2 最终结果

| 配置 | Post-FEC errors / compared bits | BER |
|---|---:|---:|
| FIFO OFF，0/64 | 11 / 58,608,000 | 1.87688e-7 |
| FIFO ON，0/8，R_buf=16000，drain | 11 / 58,608,000 | 1.87688e-7 |

两组最终 Post-FEC 错误位置文件已逐字节比较，完全一致。

### 已验证结论

在当前样本中，只要 R_buf 足够长、forced_evicted=0、帧尾 FIFO 通过 drain 清空，则：

> 0 HISO / 8 SISO + Buffered FIFO 能让当前时刻没有资源的 non-EarlyStop code 在后续 t 补解，最终得到与 0 HISO / 64 SISO 即时充足资源方案完全相同的最终译码比特和 BER。

这直接验证了新 FIFO 方案解决 burst 漏解的核心目标。

## 7. 观测代码与 FIFO history 写回语义

### 7.1 逐 code 观测不会改变结果

为定位差异，曾打开 LEVEL56_EQUIVALENCE_OBSERVATION=1，记录 channel input、decoder input/output、tile writeback 与 Level 6 history 的 hash。

已验证参考组和 FIFO 组各自的“带观测 / 不带观测”错误位置完全一致。因此观测只读，不参与调度或译码。

### 7.2 FIFO 多次服务中的无结果 history 覆盖已经修正

早期 FIFO 路径中，pending 或 AlreadyDecoded code 在后续服务时即使没有新输出，也可能以 prior 覆盖此前写好的 Level 6 history。这不符合“同一份连续 SRAM；已完成写回不得被无结果服务覆盖”的语义。

当前 Buffered FIFO 语义为：

    本次 produced 的 Level 6 code
        → 写回 tile，并更新 history

    pending / AlreadyDecoded 且本次未 produced
        → 保持已有 history，不以 prior 覆盖

第 6 节纯 SISO 的完全一致结果是在该修正后取得的。

## 8. 加入 HISO 后：吞吐改善，但本测试点 BER 恶化

### 8.1 FIFO 组对比

| 配置 | FIFO | HISO / SISO | 调度 | errors / 58,608,000 | BER |
|---|---:|---:|---|---:|---:|
| 纯 SISO FIFO | ON | 0 / 8 | Group4 | 11 | 1.87688e-7 |
| 加 HISO FIFO | ON | 8 / 8 | Group4 | 159 | 2.71294e-6 |

错误数从 11 变为 159。本次样本中 BER 约为纯 SISO FIFO 的 14.5 倍。

### 8.2 已验证结论

HISO 一方面提高服务能力：

    FIFO 清空时刻：22,971 → 19,109
    最大 FIFO 深度：4,476 → 1,888
    forced eviction：两组均为 0

另一方面最终 BER 明显变差。因此：

> 本轮 8/8 FIFO 的 BER 变差不是吞吐不足、FIFO 溢出、forced eviction 或帧尾未完成造成。

## 9. 当前 8HISO/8SISO + Group4 中的 HISO 动作

### 9.1 一个 Group4 entry 如何使用 HISO 和 SISO

64 个 code 固定分为 16 个 4-code group。一个被选中的 group-entry 最多服务两个不同 code：

    最多 1 个 SISO code
    最多 1 个 HISO code

当前选择逻辑：

1. SISO 优先选择同组 HardFail；若没有 HardFail，选择一个 flexible code；
2. 若同组还剩 flexible code，则再选择一个给 HISO；
3. 未获得资源的 non-EarlyStop code 保持 pending，后续 FIFO t 重新进入 scheduler。

因此 HISO 不是让同一个 code 再多译一次；一个 flexible code 被 HISO 后即完成、写回并变为 AlreadyDecoded，不会之后再跑 SISO。

### 9.2 HISO 可用分类与具体动作

| Hybrid 分类 | HISO 可用 | HISO 动作 |
|---|---:|---|
| ParityOnly | 是 | 翻转 overall parity |
| OneMain | 是 | syndrome 定位并修正一个 BCH 主位 |
| OneMainPlusParity | 是 | 修正一个主位并翻转 parity |
| TwoMain | 是 | BCH t=2 硬译码并重算 parity |
| HardFail | 否 | 只能走 SISO |
| EarlyStop | 不需要 | 走 EarlyStopAction，不占资源 |

HISO 对当前 lin 先硬判决并作相应 BCH 硬纠错，生成硬纠错型 lout 后按正常 writeback 写入；SISO 运行 Chase soft decoder 并写回 soft extrinsic。两种输出语义不同。

### 9.3 实际动作统计

8/8 FIFO 在 16,897 个 batch 的唯一 (batch, code) 最终动作聚合结果：

| 最终实际动作 | 次数 |
|---|---:|
| EarlyStopAction | 954,714 |
| HisoDecode | 32,208 |
| SisoDecode | 94,486 |
| 合计 | 1,081,408 = 16,897 × 64 |

因此所有 batch 的全部 64 个 code 都有最终完成动作。

HISO 来源级分布：

| 来源级 | HISO 次数 | 占比 |
|---|---:|---:|
| Level 5 | 31,506 | 97.8% |
| Level 6 | 702 | 2.2% |

HISO Hybrid 分类分布：

| 分类 | HISO 次数 | 占 HISO 比例 |
|---|---:|---:|
| OneMain | 28,999 | 90.0% |
| TwoMain | 2,851 | 8.9% |
| ParityOnly | 318 | 1.0% |
| OneMainPlusParity | 40 | 0.1% |
| HardFail | 0 | 0% |

这表明当前 BER 恶化主要伴随大量、特别是 OneMain code 从 SISO 改走 HISO，并非少量 TwoMain 个例造成。

### 9.4 与纯 SISO FIFO 的动作差异

| 分类 | 0/8 中 SISO | 8/8 中 HISO | 8/8 中 SISO |
|---|---:|---:|---:|
| ParityOnly | 781 | 318 | 464 |
| OneMain | 103,280 | 28,999 | 74,681 |
| OneMainPlusParity | 228 | 40 | 186 |
| TwoMain | 16,036 | 2,851 | 13,576 |
| HardFail | 5,175 | 0 | 5,579 |

因为 HISO 写回会改变后续 batch 的输入、EarlyStop 和 Hybrid 分类，这些类别计数在两种配置中不要求逐项守恒；此表用于展示 HISO 在 8/8 中实际承担的类别。

## 10. 为什么 64/64 GlobalPriority 不能作为 HISO 等价参考

已运行：

    FIFO OFF
    HISO / SISO = 64 / 64
    GlobalPriority

最终结果仍为 11 / 58,608,000 = 1.87688e-7，但实际动作统计：

    HISO = 0
    SISO = 125,500
    Unscheduled = 0

原因是当前 GlobalPriority 只有在 SISO 容量不够时，才把 flexible code 分流给 HISO。SISO=64 已覆盖一个 batch 的全部 non-EarlyStop code，因此 reclaim_needed=0，HISO 分配也为 0。

### 已验证结论

64HISO/64SISO + GlobalPriority 在本实验中实际仍是全 SISO 参考，不能作为“和 8/8 Group4 具有相同 HISO/SISO 动作集合”的即时参考。

## 11. 目前可严格确定的 HISO 结论

1. 8/8 FIFO 无 forced eviction，drain 后所有 batch 都完成；
2. 8/8 FIFO 服务速度更快、FIFO 积压更小；
3. 8/8 FIFO 实际执行 32,208 次 HISO，不是仅配置但未使用；
4. 97.8% 的 HISO 在 Level 5，90.0% 的 HISO 分类为 OneMain；
5. flexible code 被 HISO 后不再走 SISO，而是以 HISO 输出完成写回；
6. HISO 与 SISO 输出机制不同；写回会影响之后的 SRAM / Level 6 history 输入；
7. 当前测试点中，加入 HISO 后 BER 从 11 errors 上升到 159 errors；
8. 已建立“即时完成且 HISO/SISO 动作与 Group4 匹配”的充足资源参考；在本测试帧中，它与 8/8 FIFO 的最终 BER 和错误位置逐字节一致（第 12 节）。

因此目前最准确的表述是：

> 本轮 8HISO/8SISO + Group4 + FIFO 的 BER 恶化，不是缓冲区容量、forced eviction、帧尾未完成或 FIFO 跨时刻补解造成；它发生在大量 flexible code 由 SISO soft decode 改走 HISO hard decode 并写回之后，进而改变后续外信息/history 演化的条件下。

这描述已验证的动作差异与传播途径；尚未证明哪一个具体 HISO code 是最终 BER 首次分叉的直接触发点。

## 13. Group4 动作匹配的即时充足资源参考：已完成验证

### 13.1 验证目的

第 9 节的 `8HISO/8SISO + Group4 + FIFO` 虽然已经确认没有 forced eviction，
但还需要排除一种可能：同一 batch 被 FIFO 分成多个服务时刻处理，是否会因为
跨时刻的读写顺序而额外改变 BER。

为隔离这个变量，本节构造一个**不启用 FIFO**、但保持 Group4 选路规则不变的
软件即时参考。参考组在一次 shared 调用内给出足够的 entry，使一个 64-code batch
中的全部非 EarlyStop code 都能立即获得动作；FIFO 组仍保持实际硬件节拍的 8 entry。

两组共同条件如下：

| 条件 | 取值 |
|---|---|
| Eb/N0 | 3.065 dB |
| 总信息 bit | 60,014,592 |
| 比较 bit | 58,608,000（固定截前 4、截后 2 个 window） |
| bitgen/channel seeds | 20260319 / 3182026 |
| 调度规则 | Group4 LoadSortedMultiround，组内 SISO 优先、剩余 flexible code 走 HISO |
| 早停动作 | 原 `EarlyStopAction` 写回语义 |

### 13.2 为什么即时参考必须为 64 entry，而不是 32 entry

一开始尝试 `32 HISO / 32 SISO + 32 entry`。这个版本**不是**充足资源参考：
Group4 的一个 entry 最多可放一个 SISO 和一个 HISO；但 `HardFail` 是 `SisoOnly`，
不能占用同 entry 的 HISO 槽。最坏情况下一个 64-code batch 的全部待译码 code
都可能需要 SISO，因此需要最多 64 个 SISO entry。

实测 32-entry 尝试中共有：

| 项目 | 数量 |
|---|---:|
| Unscheduled | 13,195 |
| 其中 SisoOnly / HardFail | 2,094 |
| 其中 flexible（HisoOrSiso） | 11,101 |
| 受影响 batch invocation | 2,583 |
| Post-FEC errors | 6,068 / 58,608,000 |

该尝试的高 BER 仅说明资源仍不足，不能与 FIFO 作机制比较，后续不作为性能结论。

### 13.3 有效对比配置

| 组别 | FIFO | Group4 entry | HISO/SISO | 缓冲/尾部 | 目的 |
|---|---:|---:|---:|---|---|
| 即时充足资源参考 | OFF | 64 | 64 / 64 | 无 FIFO | 每 batch 一次性完成全部非早停 code |
| 实际 FIFO 方案 | ON | 8 | 8 / 8 | `R_buf=16000`、drain ON | 每个服务时刻最多 8 个 entry，FIFO 补解 |

`64/64` 是**仅用于软件参考**的容量；硬件/FIFO 正常时刻宽度仍固定为 8，未被修改。

### 13.4 资源覆盖与动作守恒

即时参考的最终动作统计：

| 动作 | 次数 |
|---|---:|
| EarlyStopAction | 954,714 |
| HisoDecode | 32,208 |
| SisoDecode | 94,486 |
| Unscheduled | 0 |
| 合计 | 1,081,408 = 16,897 × 64 |

按 Level 分解：

| Level | EarlyStop | HISO | SISO | Unscheduled |
|---|---:|---:|---:|---:|
| 5 | 420,184 | 31,506 | 89,014 | 0 |
| 6 | 534,530 | 702 | 5,472 | 0 |

这与第 9 节按最终 `(batch_id, code)` 聚合得到的 `8/8 FIFO` 动作统计完全一致。
因此该对比不是“不同 HISO 比例”的对比，而是同一最终动作集合在即时完成与 FIFO
跨时刻服务之间的对比。

### 13.5 最终 BER 与错误位置对比

| 组别 | Post-FEC errors / compared bits | BER |
|---|---:|---:|
| 即时充足资源参考（OFF，64 entry，64/64） | 159 / 58,608,000 | 2.71294e-6 |
| 实际 FIFO（ON，8 entry，8/8，`R_buf=16000`，drain） | 159 / 58,608,000 | 2.71294e-6 |

更强的逐位置检查结果：

| 项目 | 数量 |
|---|---:|
| 即时参考错误位置数 | 159 |
| FIFO 错误位置数 | 159 |
| 两组共有位置 | 159 |
| 仅即时参考有 | 0 |
| 仅 FIFO 有 | 0 |

即两个 Post-FEC 错误位置文件逐字节完全相同。

### 13.6 可严格得出的结论

在上述固定帧、固定种子和当前实现语义下：

> 当 FIFO 深度足够、无 forced eviction、帧尾 drain 完成，并且每个 non-EarlyStop
> code 最终都获得与即时参考相同的 HISO/SISO/EarlyStop 动作时，8-entry FIFO 的
> 跨时刻补解与 64-entry 即时完成在最终 BER 上完全等价。

所以当前 `8HISO/8SISO + Group4` 相对于纯 SISO 的 BER 变差，**不是 FIFO 延后造成**；
后续应集中验证 HISO（尤其 OneMain）相对 SISO 的输出与写回语义。

## 14. FIFO 与即时参考的逐 code hash 对齐（2026-08-26）

### 14.1 目的与观测方式

为继续确认第 13 节的 BER 等价不是偶然，本节打开已有的只读开关：

```bash
LEVEL56_EQUIVALENCE_OBSERVATION=1
```

比较组仍是第 13.3 节的两组：

1. FIFO OFF、Group4 64 entry、HISO/SISO=64/64 的即时充足资源参考；
2. FIFO ON、Group4 8 entry、HISO/SISO=8/8、`R_buf=16000`、drain ON 的实际方案。

观测开关回归通过：两组各自的 observation ON/OFF Post-FEC 错误位置均逐字节一致，
均为 159 个错误。因此下面的 hash 仅用于读出既有执行结果，不参与译码。

每个观测 code 包含 channel input、decoder input/output、tile 行写回以及
Level 6 history 的 FNV-1a-64 指纹。FIFO 组按每个 `(B<batch_id>, code)` 的
**首次非 `Unscheduled` 实际完成动作**归约；后续 `AlreadyDecoded` 快照不作为新动作。

### 14.2 最终动作与译码数据完全对齐

| 对齐项 | 结果 |
|---|---:|
| 即时参考 code 数 | 1,081,408 |
| FIFO 实际完成动作数 | 1,081,408 |
| 漏失 / 多余 / 重复完成 code | 0 / 0 / 0 |
| EarlyStop/HISO/SISO final action 不同 | 0 |
| 分类或资源资格不同 | 0 |
| channel input hash 不同 | 0 |
| decoder input hash 不同 | 0 |
| decoder output hash 不同 | 0 |
| tile row hash after writeback 不同 | 0 |

这说明对所有 `(batch, code)`，FIFO 不只是最终 BER 对齐，而且真正进入 decoder 的
输入、HISO/SISO/EarlyStop 的输出、以及 tile 中的写回结果均与即时参考相同。

### 14.3 首次完成时刻的 Level 6 history 中间态差异

按“首次完成动作”快照比较时，有 1,699 条 Level 6 history hash 不同；它们的
其它六个 hash 均相同，且全部来自 Level 6：

| 项目 | 数量 |
|---|---:|
| history hash 不同 | 1,699 |
| Level 5 差异 | 0 |
| Level 6 差异 | 1,699 |
| EarlyStopAction | 1,592 |
| HisoDecode | 53 |
| SisoDecode | 54 |

这不是最终 history 差异，而是**观测时刻不同**：即时参考一次调用内完成整批写回；
FIFO 则在 code 首次完成的服务时刻取样，此时同 batch 的其余 pending code 可能还未写回。

`B159` 是首个例子。FIFO 在 `t=170` 完成部分 code，code 50--64 当时的 history
hash 是半批次状态；`t=171` 完成剩余 code 后，code 50--64 的 history hash 全部与
即时参考逐项相同。并且在 `t=170` 和 `t=171` 中，这些 code 的 channel input、
decoder input/output 和 tile writeback 都始终相同。

因此，1,699 条记录说明现有 observation CSV 的 history 字段是“本次服务后”的
中间状态读数，而不表示 FIFO 与即时参考的最终 history 有分叉；它也没有传播到任何
后续 decoder 输入。

### 14.4 本轮可严格确定的结论

在固定帧、足够大的 `R_buf` 和 drain 条件下，FIFO 的跨时刻服务满足：

```text
每个 code 的最终动作一致
→ channel / decoder 输入一致
→ decoder 输出一致
→ tile 写回一致
→ 每 batch 完成后 Level 6 history 一致
→ 最终错误位置一致
```

所以 FIFO 服务分时本身没有引入隐藏的动作或状态差异。第 8 节中 8/8 相对纯 SISO
的 BER 恶化，应继续归因并定位到**HISO 替代 SISO**的动作/输出/写回语义，而不是
缓冲与 FIFO 调度流程。

## 16. HISO 相对纯 SISO 的精确机制定位（2026-08-26）

### 16.1 目的：将问题从 FIFO/资源调度收敛到 HISO 动作本身

第 13--14 节已经证明：对于同一组最终 HISO/SISO/EarlyStop 动作，FIFO 与
64-entry 即时参考逐 code 的输入、输出、写回和最终 BER 完全一致。因此本节固定使用
**非 FIFO、Group4 64-entry、HISO/SISO=64/64、同一长帧和同一随机种子**的
即时充足资源参考，直接检查实际 HISO 的硬判输入与 BCH 硬纠输出。

共同条件：

```text
Eb/N0                 = 3.065 dB
NUM_INFO_BITS         = 60,014,592
BER compared bits     = 58,608,000（固定截去开头 1,406,592 bit）
bit/channel seed      = 20260319 / 3182026
LLR                   = qfloat<6>
FIFO                  = OFF
Group4 entries        = 64
Level5/6 HISO/SISO    = 64 / 64
调度                  = Group4 LoadSortedMultiround
```

新增的 `LEVEL56_EQUIVALENCE_OBSERVATION=1` 只读观测对每个**实际 HISO** code
记录：

```text
进入 HISO 前 lin 硬判相对发送 BCH+overall 码字的 bit error 数
→ 以同一个 hard-class 重放 BCH/overall 硬纠
→ 硬纠输出相对发送码字的 bit error 数
```

该观测只读取 `prep.lin_matrix`、分类结果和发送参考 bits；其位置在真实 HISO 执行和
writeback 均完成之后，输出仅写入 CSV。其不会影响 scheduler、HISO/SISO、writeback、
history 或 BER。打开观测后的 BER 与对应无观测基线严格复现。

### 16.2 首先修正一个旧假设：主要敏感类别不是 OneMain

此前第 9 节仅按动作总数观察到 OneMain 占多数，曾暂时写成“BER 恶化主要伴随大量
OneMain”。这个表述不足以说明因果，现已由类别消融推翻：

| HISO 准入类别 | `LEVEL56_HISO_CLASS_MASK` | 实际 HISO 数 | Post-FEC errors | BER |
|---|---:|---:|---:|---:|
| 无 HISO，纯 SISO | `0x0` | 0 | 11 | `1.87688e-7` |
| 仅 OneMain | `0x2` | 30,244 | 12 | `2.04750e-7` |
| 仅 TwoMain | `0x8` | 10,126 | 355 | `6.05719e-6` |
| 全类别 | `0xF` | 32,208 | 159 | `2.71294e-6` |

因此，在本固定帧和工作点中，**OneMain 单独走 HISO 几乎不造成 BER 劣化；高度敏感的
类别是 TwoMain。** 不同 mask 会改变后续 LLR、EarlyStop 和分类，所以 355 与 159
不能线性相减或相加。

### 16.3 TwoMain-only 的全量硬判/硬纠统计：错误合法码字确实存在

对 `mask=0x8`（仅 TwoMain 走 HISO）的 10,126 次实际 HISO 统计如下：

| HISO 前相对发送码字错误数 | BCH 硬纠后错误数 | 次数 | 解释 |
|---:|---:|---:|---|
| 2 | 0 | 9,343 | t=2 正常纠正到真实发送码字 |
| 4 | 6 | 654 | 超出纠错半径；输出另一合法码字 |
| 6 | 6 | 3 | 超出纠错半径；错误合法码字 |
| 6 | 8 | 113 | 超出纠错半径；错误合法码字 |
| 8 | 8 | 1 | 超出纠错半径；错误合法码字 |
| 8 | 10 | 10 | 超出纠错半径；错误合法码字 |
| 10 | 12 | 2 | 超出纠错半径；错误合法码字 |

汇总为：

| 指标 | 数量 |
|---|---:|
| 实际 TwoMain-HISO | 10,126 |
| 正常 `2 → 0` 硬纠 | 9,343 |
| HISO 前真实错误数大于 2 | 783 |
| BCH/overall 合法、但硬纠后仍相对真实码字错误的输出 | 783 |
| 这些错误硬输出累计的错误 bit | 4,978 |
| Level 5 / Level 6 错误 HISO 数 | 712 / 71 |

这里需要严格区分两个概念：

```text
TwoMain 分类
  = 当前 lin 硬判的 BCH 综合满足“两主错误”型的代数判据；

真实错误数恰为 2
  = 当前硬判与本帧真实发送码字逐位比较后的结果。
```

前者不蕴含后者。对于真实错误数大于 2 的输入，t=2 BCH 解码器仍可能输出一个
**BCH + overall parity 合法**的码字；但它可以是不同于发送码字的另一个合法码字。
因此“`hard_word_valid_256()` 为真”仅验证代数合法性，不能验证该码字的真伪。

### 16.4 最早的实际误纠例子：`B153 / L5 / C17`

最早的错误 TwoMain-HISO 稳定 ID 为：

```text
logical batch / invocation = 153
Level                        = 5
code                         = 17
source global row            = 5584
```

其完整 trace：

```text
data/level56_target_trace/
  ofec_single_ebn03.065_nbits60014592_fifo0_hisomask8_hiso64_siso64_g4entries64_schedgroup4_traceB153L5C17_level56_target_trace.txt
```

逐 bit 比较结果：

| 位置 | 发送 bit | HISO 前 `lin` 硬判 | TwoMain BCH 输出 | 说明 |
|---:|---:|---:|---:|---|
| 31 | 1 | 0 | 0 | 原有错误，未被纠正 |
| 69 | 1 | 1 | 0 | 原本正确，却被 BCH 翻错 |
| 170 | 0 | 1 | 1 | 原有错误，未被纠正 |
| 177 | 0 | 1 | 1 | 原有错误，未被纠正 |
| 240 | 0 | 1 | 1 | 原有错误，未被纠正 |
| 246 | 1 | 1 | 0 | 原本正确，却被 BCH 翻错 |

也就是：

```text
输入错误集合        = {31, 170, 177, 240}，共 4 bit
TwoMain 翻转的位置  = {69, 246}
输出错误集合        = {31, 69, 170, 177, 240, 246}，共 6 bit
```

trace 中对应的直接证据为：

```text
lin_hard_decision_bit_errors_vs_expected=4
hiso_bch_flipped_positions_from_lin_hard_decision=69,246
hiso_bch_corrected_hard_word_bit_errors_vs_expected=6
```

HISO 随后不会把此结果标为失败，而是按当前既定语义：

```text
错误但代数合法的 BCH 硬码字
→ lpost = ±99
→ lout = ALPHA × (lpost - lin)，其中 ALPHA = 0.581902027
→ qfloat<6> 量化
→ 按原 Level 5 writeback 映射写回 SRAM
```

因此这不是 writeback 地址错误，也不是“未写回”；而是**向正确地址写回了以错误合法
码字为符号依据、且强度很高的外信息**。若发生在 Level 6，则同样会按既有语义更新
last-tile history。

### 16.5 同一逻辑位置的 SISO 对照

对 `B153/L5/C17` 再运行纯 SISO (`mask=0x0, HISO/SISO=0/64`)。由于此前 HISO/SISO
写回已经可能使两条完整轨迹在更早时间轻微分叉，这不是数学上“完全相同状态”的强制
反事实；但在该点实测两条 trace 的 `lin`/发送 bits 只有 6/256 个量化值不同，并且
硬判相对真实码字同为 4 错，故是一个足够接近的动作输出对照。

| 项目 | TwoMain-HISO | SISO |
|---|---:|---:|
| HISO/SISO 前硬判错误数 | 4 | 4 |
| 本 code `lout` 平均绝对值 | 0.903621 | 0.532471 |
| `|lout|` 打到 qfloat 上限 1.002535 的位置 | 137 / 256 | 3 / 256 |
| 在上述 6 个关键位置中，HISO 指向错误硬码字的位置 | 6 | 不适用（SISO 无单一强制硬码字） |

特别地，HISO 在位置 31/69/170/177/240/246 的 `lout` 分别为
`+1.002535, +1.002535, -1.002535, -1.002535, -1.002535, +1.002535`，
都接近量化饱和并服从错误硬码字的符号；SISO 在同六处输出为
`-0.420418, +0.161699, +0.873176, +0.776156, +0.840836, +0.064680`。

这说明 HISO 与 SISO 的差异不仅是“是否纠正了两位”，还包括后续传播的外信息强度：
当 HISO 误纠时，它会高置信地固化错误方向；SISO 则保留显著更多的软可靠度差异。

### 16.6 回到原始全类别 HISO 配置（`mask=0xF`）

同样的全量只读观测在原始全类别即时参考中复现：

```text
Post-FEC = 159 / 58,608,000 = 2.71294e-6
实际 HISO = 32,208
```

| HISO 类别 | 实际 HISO | 错误合法硬输出次数 | 此类错误输出累计错误 bit |
|---|---:|---:|---:|
| ParityOnly | 318 | 0 | 0 |
| OneMain | 28,999 | 7 | 44 |
| OneMainPlusParity | 40 | 2 | 14 |
| TwoMain | 2,851 | 334 | 2,104 |

TwoMain 是全类别 HISO 中错误合法硬输出的绝对主项。OneMain 也存在极少数超出其
1-error 假设的误纠，但其数量和错误 bit 都远小于 TwoMain。

### 16.7 关键消融：只禁止 TwoMain 走 HISO

保持帧、seed、Eb/N0、64-entry、64/64 资源、Group4 调度与其他 HISO 类别完全不变，
仅把 HISO 准入掩码从 `0xF` 改为 `0x7`，使 TwoMain 改走 SISO：

| 配置 | TwoMain 动作 | Post-FEC errors | BER |
|---|---|---:|---:|
| 纯 SISO `0x0` | SISO | 11 | `1.87688e-7` |
| 全 HISO `0xF` | HISO | 159 | `2.71294e-6` |
| 禁止 TwoMain-HISO `0x7` | SISO | 9 | `1.53563e-7` |

这是一项强因果消融：在本固定帧上，保留 ParityOnly/OneMain/OneMainPlusParity 的 HISO，
只撤掉 TwoMain-HISO，就将 159 个最终错误降为 9 个。故可确定：

> 当前全类别 HISO 相对纯 SISO 的 BER 恶化，主导机制是 TwoMain 分类偶尔覆盖了
> 真实错误数大于 2 的输入；t=2 硬译码在这些输入上生成错误但合法的码字，再以强
> 硬外信息写回并向后传播。它不是 FIFO、缓冲区、资源不足或 writeback 地址冲突。

### 16.8 结论边界与下一步

以上结论严格针对本节固定的帧、种子和 Eb/N0 工作点。已经证明的是“此固定样本中
存在并主导的机制”，不是“所有工作点 TwoMain-HISO 一定变差”。同时，当前结果并不
意味着应该立即改动正式译码算法；下一轮应在保持算法不变的前提下优先完成：

1. 多 seed / 多 Eb/N0 重复 `mask=0x0 / 0x7 / 0x8 / 0xF`，确认机制的统计稳定性；
2. 统计错误 TwoMain-HISO 的首次发生位置与最终 BER error cluster 的时间/空间关系，
   量化一次错误强写回如何经 Level 5/6 和 history 扩散；
3. 在明确性能-吞吐取舍后，再讨论候选设计：TwoMain 默认 SISO、对 TwoMain 增加可靠度
   门限、或为硬输出引入不同的置信度/写回语义。
